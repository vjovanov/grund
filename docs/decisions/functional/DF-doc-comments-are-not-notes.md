# DF-doc-comments-are-not-notes: a doc comment is documentation, not a note, and is never an inline citation site

**Status:** Accepted
**Date:** 2026-08-27

## 1. Context

`[reference] inline_style` and the `inline_note_*` budgets ([§FS-inline-citation-style](../../functional-spec/FS-inline-citation-style.md#fs-inline-citation-style-configurable-shape-of-inline-code-comment-citations)) judge an **inline citation site**, and until this decision [§FS-inline-citation-style.1](../../functional-spec/FS-inline-citation-style.md#1-scope) defined that as *any* comment block carrying a citation — `///`, `//!`, `/** … */` and a Python docstring were named among the recognized forms. A class Javadoc, a Rust module doc, or a package doc that mentions the spec point it implements was therefore measured as a *note*, and the default three-line cap rejected it: `inline note exceeds 3-line maximum`.

That is what a GraalVM adoption hit on grund 0.12.2 ([issue #118](https://github.com/vjovanov/grund/issues/118)). The offending comment was an ordinary class Javadoc — documentation that named its ground in the sentence that needed it — and the only fix the tool leaves is to move the citation into a detached `//` line above the doc comment. That is a worse repository than the one that started: the citation drops out of the generated documentation, and it is severed from the sentence it supported, which is the whole of what a grounded comment is for ([§GRUND-understanding](../../grund.md#grund-understanding-the-why-stays-known)). The managed entrypoint block asks for the opposite in as many words — cite "on the doc-comment for a whole behavior, inline beside the clause it enforces" ([§FS-init.2.3](../../functional-spec/FS-init.md#23-generated-agent-entrypoints)) — so the gate was rejecting the shape the guidance asks an agent to write.

It is not one adoption's edge case. Run against *this* repository under the default caps, the rule reports 790 findings, and 63% of them are in a `///`, `//!`, or docstring block. grund's own `grund.toml` carries `inline_note_max_lines = 25` and `inline_note_max_columns = 180` — the same workaround in a wider spelling: caps raised until they stopped hitting documentation, which also stopped them bounding the notes they exist to bound. A cap that has to be set eight times its default to survive contact with a repository's own doc comments is measuring the wrong thing.

One cause sits under both symptoms. A *note* is a rationale beside a clause; the budgets, the `citation-only` style, and the layout are all statements about notes. Documentation is not a note, and the spec was applying a note's rules to a category they were never written for.

## 2. Decision

### 2.1 The site is an inline comment; a doc comment is not a site

An inline citation site is an **inline comment** block that carries a citation, and a **doc comment** block is not a site at all ([§FS-inline-citation-style.1.1](../../functional-spec/FS-inline-citation-style.md#11-doc-comments-are-not-sites)). A doc comment documents the definition that follows it, or the file it opens; an inline comment is every other comment — one among statements, a detached block, a note beside the clause it grounds. The positive definition is not new: it is the distinction the managed block already draws when it tells an agent where to put a citation ([§FS-init.2.3](../../functional-spec/FS-init.md#23-generated-agent-entrypoints)).

Nothing in [§FS-inline-citation-style](../../functional-spec/FS-inline-citation-style.md#fs-inline-citation-style-configurable-shape-of-inline-code-comment-citations) reaches a citation inside a doc comment — not `citation-only` ([§FS-inline-citation-style.3.1](../../functional-spec/FS-inline-citation-style.md#31-citation-only)), not the line and column budgets ([§FS-inline-citation-style.2.3](../../functional-spec/FS-inline-citation-style.md#23-counting-lines-and-columns), [§FS-inline-citation-style.4.1](../../functional-spec/FS-inline-citation-style.md#41-errors--hard-caps)), not the layout ([§FS-inline-citation-style.3.3](../../functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit), [§FS-inline-citation-style.4.4](../../functional-spec/FS-inline-citation-style.md#44-warnings-and-errors--opt-in-layout-deviations)). Everything outside that spec still does: the citation resolves, is dangling when its ID does not ([§FS-check.3.1](../../functional-spec/FS-check.md#31-dangling-citation)), counts for the grounding floor ([§FS-check.3.6](../../functional-spec/FS-check.md#36-ungrounded-source-file-opt-in)) and the citation directions ([§FS-check.3.11](../../functional-spec/FS-check.md#311-missing-required-citation)), is refused as a persisted shorthand ([§FS-check.3.13](../../functional-spec/FS-check.md#313-number-only-shorthand-citation)), and is linkified by `grund fmt` ([§FS-fmt.6](../../functional-spec/FS-fmt.md#6-cross-reference-emission)). Only the *shape* rules stop at the boundary.

This generalizes an exemption the spec already grants rather than inventing one. A doc comment that **declares** an ID has been outside the form since the rule shipped — "a declaration body is spec text whose shape this spec does not govern" ([§FS-inline-citation-style.3.3](../../functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit), [§FS-inline-citation-style.5](../../functional-spec/FS-inline-citation-style.md#5-agent-facing-rendering)). The doc comment beside it is documentation by exactly the same argument; the declaration was never the special case, documentation was.

### 2.2 Two recognizers, chosen by file type, never by parsing

Which kind a block is, is read from the file's extension and one test on the block ([§FS-inline-citation-style.1.1](../../functional-spec/FS-inline-citation-style.md#11-doc-comments-are-not-sites)). **Marker languages** spell a doc comment with a marker of their own — Rust and C-family `///` / `//!` / `/**` / `/*!`, a Python docstring, Lua `---`, Haddock `-- |`, roxygen2 `#'` — so the marker is the language's own answer to the question and no other evidence is needed. **Position languages** spell a doc comment like every other comment (Go `//`, Ruby `#`, shell `#`, SQL `--`), so the block is a doc comment when the line immediately below it is a definition-starter for that language. **Any other extension** has no doc-comment notion, so every block in it is inline — today's behavior, which is what keeps the change from touching a tree that already passes.

Both tests are line-local: a prefix comparison, or one look at one line. That is recognition, not parsing ([§FS-non-goals.3](../../functional-spec/FS-non-goals.md#3-code-ast-parsing)), and it is the same discipline the declaration and citation recognizers already hold to. The test is made once per block, and only for a block that carries a citation — the classification happens where the scanner already has the block in hand — so the cost is one comparison per site ([§FS-inline-citation-style.7](../../functional-spec/FS-inline-citation-style.md#7-architecture-impact)) and the default path of [§GOAL-fast-feedback](../../goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible) is unmoved.

### 2.3 A leading comment block is a module doc

In a position language the block is *also* a doc comment when it is the file's leading comment: every line above it is blank, or is line 1 and a `#!` shebang. Where a marker exists, a module doc has its own spelling — `//!`, a module docstring — and is recognized for free; where none does, a header comment at the top of a Ruby, shell, SQL, or Go file is the same thing without a marker to prove it. Without this half, the exemption would hold for a `#` block above a `def` and break for the file header three lines above it, which is a distinction no author draws.

### 2.4 No knob

What a site *is* is not configurable. Two correctly-configured installs must agree on whether a tree is well-formed ([§FS-non-goals.13](../../functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)), and a project that could redefine "site" would move the meaning of every `inline_note_*` key underneath it. The language table is built in for the same reason; it can widen later without a `grund_config_version` bump ([§FS-config.5](../../functional-spec/FS-config.md#5-schema-versioning)), the way the layout enums can.

The change also needs no deprecation ramp. It only ever *removes* findings: a block that was measured may stop being measured, and no block that was unmeasured starts. No repository that passes `grund check` today can fail after it, so it is outside the risk [§GOAL-no-silent-breakage](../../goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path) guards, exactly as [§DF-note-columns-are-characters](DF-note-columns-are-characters.md#df-note-columns-are-characters-a-note-column-is-one-character-not-one-byte-and-not-one-display-cell) was.

### 2.5 One rendered sentence, and no version bump

The agent-facing copy gains one sentence at every `inline_style`, so the author and the linter agree about where the gate stops ([§FS-inline-citation-style.5](../../functional-spec/FS-inline-citation-style.md#5-agent-facing-rendering)). Without it the agent reads a budget, sees a Javadoc that cites, and performs the detached-`//` workaround of §1 to satisfy a rule that no longer applies.

The managed-block version does **not** move. That is the call the layout keys made and for the same reason: a bump turns a silent staleness into an `agents-init` error for every repository, including the ones the sentence only ever widens. A block that predates the sentence teaches a narrower rule than the gate enforces, which costs an over-careful comment and never a finding, and the sentence arrives on the repository's next `grund init`.

### 2.6 The corners it accepts

Four are stated in the spec rather than repaired ([§FS-inline-citation-style.1.1](../../functional-spec/FS-inline-citation-style.md#11-doc-comments-are-not-sites)). A **dangling doc comment** inside a method body is a doc comment by its marker and is not measured — `javac -Xlint:dangling-doc-comments` and `rustc`'s `unused_doc_comments` already own that diagnosis. **Position recognition is recognition**: a Go `var` in a function body reads as documentation and a Ruby `private def` does not, and a miss either way only changes whether a block is measured, never what a citation resolves to. A comment **trailing code** stays what it was, not a site. And **blank-line adjacency is adjacency** — a `#` block, a blank line, then a `def` is an inline comment, because the blank line already breaks one block into two.

Accepting them is the price of not parsing, and the price is small because every one of them is a false *negative* of the exemption: the worst outcome is a block measured that need not be, which is the behavior of the release before this one.

## 3. Alternatives considered

| Option | Why rejected |
|---|---|
| Exempt only file-level and module docs (`//!`, a module docstring, a file header) | Leaves every class, method, and package doc under the cap. The failure in §1 was a *class* Javadoc, so the narrow exemption does not fix the report that motivated it. |
| Measure only the paragraph that carries the citation | A four-line documentation paragraph still fails, Javadoc paragraphs are `<p>`-separated rather than blank-line separated so the paragraph is not even findable line-locally, and the "note" concept still does not fit the prose it would be measuring. |
| Exempt doc comments from the budgets only, keeping style and layout | `citation-only` would still reject every Javadoc that cites, because a Javadoc cannot be a pure pointer; and the layout rule only judges sites that carry a note ([§FS-inline-citation-style.3.3](../../functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit)), so "documentation prose is not a note" collapses to "not a site" anyway. Two axes off and one on is the same decision, spelled inconsistently. |
| A separate configurable doc-comment budget | A knob for a category error. It concedes that documentation is a kind of note and then asks each project to pick how long a kind of note may be, so two projects disagree about what a site is ([§FS-non-goals.13](../../functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)) instead of agreeing that documentation is not one. |
| Parse the host language to find definitions | Ruled out by [§FS-non-goals.3](../../functional-spec/FS-non-goals.md#3-code-ast-parsing), and unnecessary: the marker languages need no position at all, and the position languages are served by one line-local test whose misses cost nothing (§2.6). |

## 4. Consequences

- Every spec example and test fixture that used `///` *as an inline site* now reads `//`: the examples in [§FS-inline-citation-style.2.3](../../functional-spec/FS-inline-citation-style.md#23-counting-lines-and-columns), [§FS-inline-citation-style.3.2](../../functional-spec/FS-inline-citation-style.md#32-citation-with-note) and [§FS-inline-citation-style.3.3](../../functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit), and the e2e fixtures that assert the caps. The rewrite is mechanical, and a fixture that keeps `///` is asserting the new exemption rather than the old cap.
- The classifier is one module, `crates/grund-core/src/comment_block.rs`, and it is shared. [§RM-doc-comment-declarations](../../roadmap.md#rm-doc-comment-declarations-declarations-only-in-classmethod-doc-comments) planned the same marker/position split for the *declaration* recognizer; it reuses this one rather than growing a second, so the two gates cannot come to disagree about what documentation is.
- A position language outside the table keeps every comment inline until its starters are added. That is a false negative of the exemption, not a false positive of the gate: such a file is measured exactly as it is measured today, and widening the table later needs no config-schema change (§2.4).
- grund's own `grund.toml` can return its caps toward the defaults once the doc comments stop being measured, and the number the repository configures becomes a statement about notes again rather than a bandage over documentation.
