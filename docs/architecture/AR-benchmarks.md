# AR-benchmarks: instruction-counting benchmarks for the hot CLI commands

How `grund` turns the [§GOAL-fast-feedback.1](../goals.md#1-performance-targets) targets into a number CI records on every commit. The goal-meter map points here from [§AR-goal-measurement.2](AR-goal-measurement.md#2-goal-meters); this spec pins what is measured, with what tool, and why the meter counts CPU instructions rather than wall-clock seconds. The synthetic large fixture, the committed baseline and the build-failing CI gate shipped in 0.4.1 (`docs/changelog/0.4.1.md`); the decision that picks instruction counting over a wall-clock harness is [§DA-benchmark-instruction-counting](../decisions/architectural/DA-benchmark-instruction-counting.md#da-benchmark-instruction-counting-the-performance-harness-counts-instructions-not-wall-clock-seconds).

## 1. What is benched

A `cargo bench` harness at `crates/grund-cli/benches/instructions.rs`, gated behind the `grund` package's `bench` Cargo feature so a plain `cargo test --all-targets` compiles only a no-op bench target and never tries to run the Callgrind body (it needs Valgrind). Each benchmark runs the **freshly built `grund` binary** as a subprocess under Callgrind — not a library call — because the figure we care about is the cost of an invocation an agent or a CI step actually makes, including process start-up, argument parsing, the walk, and output formatting.

Every benchmark scans a **generated conformant fixture**, never this repository's own tree. Benchmarking the live repo conflates the two things the regression gate must keep apart: a genuine code slowdown, and the repo simply doing more work because its own docs or `grund.toml` evolved (the case in point: enabling `[citations]` direction checks on itself makes `grund check` validate more, which is not a code regression). A fixed, generated input isolates the first — the only thing the gate should fail on — so the baseline is stable across commits regardless of how the repo's content evolves. All fixtures are regenerated by `scripts/generate_large_benchmark_fixture.py` before each benchmark command is built (so a cached `target/` cannot hide generator changes), under `target/bench-fixtures/`:

- a **canonical** 1.5k-file fixture for the per-command suite — representative, but small enough to keep the suite quick;
- a **10k-file** fixture for the large-repo budget benchmark, backing the large-repo promise ([§GOAL-small-and-large.2](../goals.md#2-large-repo-promise)) and fast-feedback target ([§GOAL-fast-feedback.1](../goals.md#1-performance-targets));
- a **citations-enabled** fixture (`--citations`) so one benchmark exercises the citing-side classification and direction passes ([§FS-config.3.9](../functional-spec/FS-config.md#39-citations--citation-direction-rules)), which the other fixtures (no `[citations]`) deliberately skip.

The benched subcommands are the ones the agent loop and the CI/pre-commit gate run most:

| Benchmark | Invocation | Who runs it, how often |
|---|---|---|
| `check` | `grund check <fixture>` | Every save (watch / LSP), every commit (pre-commit), every push (CI). The headline operation [§GOAL-fast-feedback](../goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible) exists for. |
| `check_large_10k` | `grund check <10k-file fixture>` | The large-repo budget input from [§GOAL-fast-feedback.1](../goals.md#1-performance-targets). |
| `check_citations` | `grund check <citations-enabled fixture>` | The citation-direction code path ([§FS-config.3.9](../functional-spec/FS-config.md#39-citations--citation-direction-rules)); its delta against `check` (same file count) is the direction-checking overhead. |
| `list` | `grund list <fixture>` | An agent discovering the right `<ID>` before it cites one. |
| `show --brief` | `grund <ID> --brief <fixture>` | An agent or LSP hover checking the title plus first paragraph. |
| `show` | `grund <ID> <fixture>` | An agent grounding itself on a bare citation — the lead-default read AGENTS.md / CLAUDE.md tell it to do first, before editing the code that realizes a cited ID. |
| `show --full` | `grund <ID> --full <fixture>` | An agent escalating to the full declaration body when the narrower slices are not enough. |
| `refs` | `grund refs <ID> <fixture>` | An agent checking a declaration's blast radius before changing or moving it. |
| `cover` | `grund cover <fixture>` | What the diff-aware co-change recipe ([§RM-cochange-gate](../roadmap.md#rm-cochange-gate-a-pre-commit--ci-recipe--no-impl-change-without-spec-and-test)) and CI consume. |
| `fmt --check` | `grund fmt --check <fixture>` | The pre-commit / CI normalization gate. |

`check`, `check_large_10k`, `check_citations`, `list`, `cover`, and `fmt --check` walk a whole scanned tree; `show --brief`, `show`, `show --full`, and `refs` do the same walk plus a per-ID extraction or filter — so the set spans the engine's two cost shapes (full report vs. single-ID query), and the show ladder spans the short hover preview, the cheap lead default, and the full recursive body over realistic inputs. Each command exits 0 on its conformant input (which keeps iai-callgrind's default `ExitWith::Success` happy); on a broken tree `check` / `fmt --check` exit non-zero and the bench fails — intentionally, since a baseline recorded against a broken tree is worthless.

The hot command list is also the training run for the profile-guided-optimization build of the distributed release binary (`scripts/pgo-build.sh`, [§DA-pgo-release](../decisions/architectural/DA-pgo-release.md#da-pgo-release-distributed-binaries-are-pgo-built-trained-on-the-benchmark-workload)): the everyday operations we benchmark are the ones we profile against, so "the operations that matter" has one definition. The PGO run trains on this repository's own tree (a representative real workload, where profiling input *should* reflect reality), while the benchmarks run the same commands against the generated fixtures (where the gate needs a *stable* input) — the shared invariant is the command list, kept in sync by the cross-pointing comments in `crates/grund-cli/benches/instructions.rs` and `scripts/pgo-build.sh`. `check_large_10k` is deliberately excluded from PGO training because it is a CI budget input, not a representative release invocation. PGO stays out of the normal development build and push/PR CI loop; it is run by the release pipeline, and by explicit benchmark work when comparing the optimized release artifact. The self-repo command list is duplicated in two forms — the `#[binary_benchmark]` set in `crates/grund-cli/benches/instructions.rs` and the shell loop in `scripts/pgo-build.sh` — each with a comment pointing at the other.

## 2. Why instruction counts, not wall-clock

Callgrind reports the number of CPU instructions executed (plus cache-miss estimates), and that number is **deterministic** for a given binary and input — it does not move when the CI runner is loaded, when a neighbour VM is noisy, or when the kernel reschedules. A wall-clock harness (criterion and friends) measures the thing the [§GOAL-fast-feedback.1](../goals.md#1-performance-targets) budget is literally written in (milliseconds), but its variance on shared CI is large enough that "fail on regression" either flakes (tight threshold) or misses real regressions (loose threshold). Instruction count is the proxy that makes the [§AR-ci.5](AR-ci.md#5-benchmark-job) regression gate implementable: a quadratic walk or an accidental second read pass moves the instruction count by a margin no scheduling noise can mask. The full rationale, and the alternatives weighed, is [§DA-benchmark-instruction-counting](../decisions/architectural/DA-benchmark-instruction-counting.md#da-benchmark-instruction-counting-the-performance-harness-counts-instructions-not-wall-clock-seconds).

The millisecond budget itself is still backstopped by the cheap wall-clock guard in [§AR-ci.4](AR-ci.md#4-performance-smoke-guard) (the built `grund .` self-check under a generous `timeout`); the instruction-count harness is the precise regression meter, the timeout is the catastrophic-blowup floor. The two are complementary, not redundant.

## 3. How it runs

- Locally: `cargo bench -p grund --features bench --bench instructions` (requires `valgrind`, `python3`, and `iai-callgrind-runner` on `PATH`). With no prior run, iai-callgrind records the counts and exits clean; on a later run in the same `target/` it prints the delta against the previous run. Every fixture is regenerated on each harness run so cached `target/` contents cannot hide fixture-generator changes.
- In CI: a dedicated `bench` job installs `valgrind` and `cargo install iai-callgrind-runner` (version-pinned to the `iai-callgrind` dev-dependency), then runs the harness — see [§AR-ci.5](AR-ci.md#5-benchmark-job). Pull requests first save a `main` baseline from the base branch, then rerun the PR with `--baseline=main --callgrind-limits=ir=5.0%`, so an instruction-count regression fails the build. Pushes to `main` record the current counts and save JSON summaries for inspection.

- [§AR-goal-measurement.2](AR-goal-measurement.md#2-goal-meters) — this harness is the fast-feedback meter; [§GOAL-fast-feedback.1](../goals.md#1-performance-targets)'s targets are pinned by the committed baseline and the PR regression gate.
- [§DA-benchmark-instruction-counting](../decisions/architectural/DA-benchmark-instruction-counting.md#da-benchmark-instruction-counting-the-performance-harness-counts-instructions-not-wall-clock-seconds) — the architectural decision record for choosing Callgrind/iai-callgrind over a wall-clock criterion harness, and for benchmarking the binary rather than the library.
- [§AR-ci.4](AR-ci.md#4-performance-smoke-guard) / [§AR-ci.5](AR-ci.md#5-benchmark-job) — the interim wall-clock smoke guard and the benchmark CI job, respectively.
- [§AR-bindings](AR-bindings.md#ar-bindings-target-shape-for-exposing-the-rust-engine-on-three-platforms) / [§RM-distribution](../roadmap.md#rm-distribution-cargo--npm--pypi-from-one-engine) — the harness is deliberately established before the workspace split and bindings work move the engine around, so any slowdown shows up as a diff against a known-good instruction count rather than going unnoticed.
- [§DA-pgo-release](../decisions/architectural/DA-pgo-release.md#da-pgo-release-distributed-binaries-are-pgo-built-trained-on-the-benchmark-workload) — reuses the self-repo hot command list as the PGO training corpus for the distributed release binary; the release pipeline that runs `scripts/pgo-build.sh` is owned by [§RM-distribution](../roadmap.md#rm-distribution-cargo--npm--pypi-from-one-engine), the release contract is [§FS-distribution.4](../functional-spec/FS-distribution.md#4-release-process), and normal development CI does not run PGO ([§AR-ci.6](AR-ci.md#6-pgo-stays-out-of-development-ci)).

## 5. Comparing two revisions

The counts are deterministic for a given **binary**, not for a given source tree, and two checkouts have their own `target/` directories — one of which may hold a differently-built binary. A PGO build from `scripts/pgo-build.sh` ([§DA-pgo-release](../decisions/architectural/DA-pgo-release.md#da-pgo-release-distributed-binaries-are-pgo-built-trained-on-the-benchmark-workload)) is the case to watch, because it is trained on this very workload and reads several percent faster on it.

So benching a branch in one checkout against `main` in another measures the build as much as the change, and it fails by producing a plausible number rather than an error. Take both numbers in **one worktree**, switching the source under a single `target/`, and against the branch's **merge base** rather than whatever `main` has since become.

## 6. Scope

This is a build-and-CI tool, not a CLI surface: it adds no subcommand, no flag, no output shape, so the `tests/e2e/cases/*` corpus is unchanged and nothing here is covered by the [§GOAL-no-silent-breakage](../goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path) user-visible-surface contract. The benched commands are described above by reference to their functional specs ([§FS-check](../functional-spec/FS-check.md#fs-check-grund-validates-every-reference-in-a-repo), [§FS-cli](../functional-spec/FS-cli.md#fs-cli-grunds-command-line-surface-conventions)) rather than re-specified here.
