# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

## Unreleased

### Added

- [§DF-repo-conversation-opinion](decisions/functional/DF-repo-conversation-opinion.md#df-repo-conversation-opinion-repositories-may-commit-a-link-only-conversation-rendering-opinion) / [§DISC-conversation-rendering-layers](discussions/proposals/2026-07-21-conversation-rendering-layers.md#disc-conversation-rendering-layers-layered-ownership-of-local-conversation-citation-rendering): repositories may commit a `link`-only conversation-rendering opinion via `[reference] conversation` ([§FS-config.3.1](functional-spec/FS-config.md#31-reference--citation-form)). When set, the generated agent entrypoint teaches linked local-conversation citations — the declaration location as plain `path:line` text beside the citation, never a Markdown link (recorded non-working in terminal TUIs by the [§DF-neural-link-generation](decisions/functional/DF-neural-link-generation.md#df-neural-link-generation-agents-compose-clickable-citation-links-themselves-grund-does-not-grow-a-link-command) matrix). The `grund integrations` global block texts become self-scoping (inert outside grund repositories) and carry the precedence rule: repository opinion > user preference > `plain`. A repo-local uncommitted instruction file was researched across the supported-agent set and deferred (portable to Codex alone). PR #45.

- [§DF-neural-link-generation](decisions/functional/DF-neural-link-generation.md#df-neural-link-generation-agents-compose-clickable-citation-links-themselves-grund-does-not-grow-a-link-command): record the clickable-citations experiment and decision for conversation text as an agent convention, not a per-citation tool. Local/TUI rendering follows a user preference installed into global agent instructions; repository web text follows one fixed, context-sensitive rule. Links keep the citation as visible text and plain is always the fallback. Markdown link-title hover is explicitly rejected: it repeats declaration headings in output for a limited desktop tooltip rather than a portable preview. `grund` grows no `link` command (a prototype was built and reverted on the PR branch); `grund fmt --cross-refs` ([§FS-fmt.6](functional-spec/FS-fmt.md#6-cross-reference-emission)) remains the only link emitter for repository Markdown. PR #45.
- [§FS-integrations](functional-spec/FS-integrations.md#fs-integrations-grund-prints-and-installs-its-rendering-layer-integrations) / [§DF-integrations-command](decisions/functional/DF-integrations-command.md#df-integrations-command-integrations-earns-a-cli-slot-as-one-time-setup-where-a-per-citation-link-command-did-not): add the `grund integrations [<client>]` command — the one-stop shop that makes the clickable-citation rendering layer installable from `cargo install grund`. It prints embedded artifacts on demand, detects the caller's terminal/editor, and installs on `--write` as an idempotent marked block. A write also records the user-local conversation preference and synchronizes global Codex, Claude, Gemini, GitHub Copilot, Zed, and Pi instructions; clientless `--write --conversation link` overrides the plain default without installing an arbitrary client or changing repository configuration. `--format json` emits a machine detection plan. Every artifact is embedded in the binary; nothing is published to a marketplace ([§FS-lsp.2.3](functional-spec/FS-lsp.md#23-editor-configuration-one-time-per-editor)). Resolves issue #46. PR #45.
- [§FS-integrations.3.2](functional-spec/FS-integrations.md#32-editor-clients-vscode-codium): add `codium`. VSCodium is a separate application with a separate extensions root, so `grund integrations vscode --write` installed the extension into `~/.vscode/extensions` where VSCodium never looks — and the failure was silent, reporting success while no link ever appeared. `codium` installs the identical extension into `~/.vscode-oss/extensions`. Detection cannot tell the two apart by presence, since both export an identical `VSCODE_*` environment; what differs is where those values *point*, so `codium` is marked alongside `vscode` when one of them names VSCodium's application directory, and the catalog offers both installs rather than guessing. PR #45.
- [§FS-integrations.3.5](functional-spec/FS-integrations.md#35-clients-grund-cannot-support-and-why): record the terminals that cannot be supported and why, so the question is not re-litigated. Ghostty documents exactly the needed option — `link`, a regex bound to an arbitrary action — but its reference marks it `TODO: This can't currently be set!`; only built-in URL matching works, and with no `path:line` opener the `--conversation link` fallback does not help either. Apple Terminal.app and Windows Terminal have no regex-to-action hook at all. The shared requirement is stated once: a terminal must let configuration bind arbitrary matched text to an arbitrary command. PR #45.
- [§FS-integrations.3.4](functional-spec/FS-integrations.md#34-manual-client-iterm2): add `iterm2`, the most-used macOS terminal, as the first **manual** client. It keeps its rules in a binary property list, so the managed-block contract does not apply and grund will not rewrite a live profile blob for a convenience. `grund integrations iterm2` prints the Smart Selection rule to add — the shared citation regex at `Very High` precision so it does not lose to iTerm2's built-in path rule, with a `Run Command…` action of `grund-open \0` on cmd-click and `grund-open --peek \0` as a second action on the right-click menu. `--write` installs the resolver and the user preference, then prints what only a human can apply, reporting `manual` and exiting `0`. A manual client always reports `installed: false` because grund never reads that plist; the detection plan gains `"install_kind"` so a caller can tell *not installed* from *not knowable*. Noted where it matters: iTerm2's Semantic History already makes `path:line` cmd-clickable, so `--conversation link` alone gives Mac users clickable citations with no rule at all. PR #45.
- [§FS-integrations.3.3](functional-spec/FS-integrations.md#33-reading-a-declaration-without-leaving): read a declaration without leaving what you are doing. Opening a citation answers *where*; peek answers *what it says*. `grund-open --peek` renders the resolved `path:line` and the declaration lead through a pager, and each terminal client binds it to a disposable surface: a kitty overlay (`ctrl+shift+p`), a tmux popup (`prefix` + `G`, tmux 3.2+), a wezterm split pane (`ctrl+shift+`-click). It is the same resolver in a second mode, so a peek and a click cannot disagree about where a citation points. VS Code gets true hover instead — its terminal-link tooltip now carries the declaration's `--brief` slice and resolved location, cached per citation because the provider runs per rendered line. No terminal can hover: none exposes a hover event or link tooltip to configuration, and WezTerm's request for one has been open since 2018. PR #45.
- [`docs/clickable-citations.md`](clickable-citations.md), linked from the README: a user-facing setup guide for the terminal and editor integrations. Covers the three prerequisites that each fail silently (`grund` and `~/.local/bin` on `PATH`, an editor the resolver can find), the per-client install and the reload each one needs, a verification walkthrough whose line numbers are real IDs in this repository, the `plain` vs `link` conversation preference and how a repository opinion overrides it, and a troubleshooting path that separates a matcher problem from a resolver problem in one command. Documents that WezTerm requires wiring `grund_apply_hyperlink_rule(config)` by hand — the block installs but does nothing until it is called, which looks identical to a broken install. PR #45.

### Fixed

- [§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2): clicking a citation now opens the line it actually cites, from anywhere in the tree, under any configured marker. A product-management pass over the rendering layer found the shipped resolver truncated the citation at the first `.` — so every `§<ID>.<section>` click landed on the declaration heading rather than the section; handed the editor a config-root-relative path, which opens nothing when the shell sits in a subdirectory; and matched a hardcoded `§`, leaving repositories with a custom `[reference] marker` silently unclickable. `grund-open` and the VS Code extension now resolve through `grund <ID>[.<section>] --format json`, walk up to the config root and join against it, and strip whatever marker they are given; the click matchers accept any punctuation marker and the namespace-qualified `§<alias>/<ID>` form. Field extraction is anchored to the end of the JSON object so declaration prose containing `"path":` or `"line":` cannot shadow the real fields. PR #45.
- [§FS-integrations.4.1](functional-spec/FS-integrations.md#41-marked-blocks-in-dotfiles): `grund integrations wezterm --write` produced a `wezterm.lua` that does not parse. The managed-block markers were hardcoded to `#`, which comments `kitty.conf` and `.tmux.conf` but is the *length operator* in Lua — verified against the Lua 5.4 compiler as `unexpected symbol near '#'`, which costs the user their entire WezTerm configuration rather than just the grund block. Markers now use the host file's own comment token, and block lookup is scoped to that dialect so an existing block is never respliced with the wrong one. Separately, a from-scratch `wezterm.lua` defined `grund_apply_hyperlink_rule` but never called it and returned no config, so even a parsing file registered nothing; a fresh write now appends an unmanaged starter config that wires the helper up. Found by attempting the documented setup end to end. PR #45.
- [§FS-workspace.8.1](functional-spec/FS-workspace.md#81-grund-): `grund <alias>/<ID> --format json` reported a member-relative `path` while `grund list` reported a workspace-root-relative one, contradicting the [§FS-config.3.6](functional-spec/FS-config.md#36-output--report-format) promise that report paths are relative to the config root. Both now agree — including for `E2E` cases, whose pre-baked manifest JSON bypassed the fix — which is what lets the resolver join the reported path against the root it discovered. PR #45.
- [§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2): the click handlers now run the resolver in the clicked pane's working directory — tmux's `run-shell` starts in the tmux *server's* start directory and WezTerm's spawn in the GUI process's, so a click failed unless the terminal happened to be launched inside the repository. The click matchers accept digits inside the kind — the letters-only pattern could never match a `§E2E-<case>` citation — and the resolver accepts the [§FS-show.2.4](functional-spec/FS-show.md#24-e2e-cases) E2E manifest shape (no `"line"`; the case directory opens, with no `:line` suffix) instead of failing on every E2E click. A failed resolution continues the root climb upward instead of ending it, so a workspace-qualified `§<alias>/<ID>` clicked from inside a member resolves at the workspace root. PR #45.
- [§FS-integrations.3.2](functional-spec/FS-integrations.md#32-editor-clients-vscode-codium): the VS Code extension walked no further than the first workspace folder, so opening a subdirectory of the repository ran `grund` there and joined the config-root-relative path against the wrong base; it now walks up to `.agents/grund.toml` exactly as the shell resolver does. It also cached failed resolutions forever — a citation that resolved *after* its declaration was added stayed "unknown" until the extension host restarted; only successes are cached now. PR #45.
- [§FS-completions.1](functional-spec/FS-completions.md#1-user-facing-command): the generated bash, zsh, and fish completion scripts complete the `integrations` subcommand the spec already promised, and `grund help integrations` and the README name all six supported clients instead of four. PR #45.
