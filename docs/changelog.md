# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

- [§FS-init.1.2](functional-spec/FS-init.md#12-refused-targets) / [§FS-init.4](functional-spec/FS-init.md#4-exit-codes): **`grund init` now decides whether a target may be scaffolded at all before it writes anything.** The home directory is refused unconditionally, no flag lifting it; a target that no `.git`, `.hg`, `.jj`, or `.svn` marker covers, in it or any ancestor, is refused unless the new `--no-vcs` says otherwise. A refusal is total — nothing is created, appended, or updated, not even the files that would have been unobjectionable — the run exits `2`, and `--dry-run` reports the refusal rather than a preview, because a preview of a run that would be refused *is* that refusal. `--no-vcs` is deliberately not `--force`: `--force` decides whether files `init` owns get overwritten ([§FS-init.3](functional-spec/FS-init.md#3-non-intrusive-guarantees)), this one says *this really is where I want a project*, and a run may need either, both, or neither. The reported accident was a shell slip into `$HOME` followed by `grund init --claude`, which appended the 56-line managed block to a personal `~/.claude/CLAUDE.md` — the global instruction file every agent session in every project loads — turning a three-line file into a 59-line one, unprompted and recoverable only because the block is delimited and the user happened to look. **Nothing in the spec was violated when that happened**, which is the part worth recording: every guarantee in [§FS-init.3](functional-spec/FS-init.md#3-non-intrusive-guarantees) is scoped *inside* a file — user-authored content preserved, line endings preserved, the config never overwritten, re-running a true no-op — and the entire contract on `<path>` was that it exists and is a directory. The list answered *what will `init` not touch in a file it was pointed at* and never *should it have been pointed here*, so `$HOME` was a valid target by construction. Appending made it worse rather than better: appending to an existing entrypoint instead of inventing a competing `AGENTS.md` is the **conservative** branch in this spec's own value system, the first bullet of §3, so the one behavior that did the damage is the one every review read as the polite option. The collision underneath is that two commands know `~/.claude/CLAUDE.md` and did not know about each other. [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions) already models it correctly — a machine-global instruction file, gated on `~/.claude/` existing, receiving a deliberately small marked rendering block — while `init` modelled the same path as purely `<path>`-relative, so the *same signal*, `.claude/` exists, reads as "this machine runs Claude, sync the rendering block" to one command and "this project uses Claude, scaffold the project block" to the other. Both readings are right in their own scope; in `$HOME` they name one file, and nothing arbitrated. A second, independent rule therefore refuses any planned entrypoint that is one of that table's file-backed user-global targets, checked per path rather than per target — every path the run would write, **the canonical `AGENTS.md` included**. That rule is not the home rule restated, and the arithmetic that says it is is the same slip that produced the accident: it holds `<path>` at `$HOME` and asks which of the two tables' paths coincide there, but `<path>` is arbitrary, and `<path>/AGENTS.md` with `<path>` at `~/.codex`, `~/.config/zed`, or `~/.pi/agent` **is** the machine-global file, as is `<path>/GEMINI.md` under `~/.gemini`. The home rule says nothing about those targets — they are not the home directory — and on a machine whose dotfiles are a repository, which is the usual state of a machine that has those directories at all, neither does the version-control rule. Four of the five reachable rows are the canonical entrypoint, which is both the one `init` reaches for by default and the one file it *overwrites* rather than appends to under `--force` ([§FS-init.3](functional-spec/FS-init.md#3-non-intrusive-guarantees)) — the same accident with nothing left behind to hand-remove — and the plan carries it as a flag rather than as a path, so a check handed the entrypoint list could not see it. The division is the one [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions) already states — the user-global files carry machine-wide policy and are `grund integrations --write`'s to manage, the repository entrypoint carries this project's syntax and is `init`'s. The version-control rule is the only one with a legitimate other side (a directory scaffolded before `git init`, a project under no VCS at all), which is why it alone gets a flag; presence is tested rather than type, since a linked worktree and a submodule both write `.git` as a *file*, and nothing is parsed and no command is run, so [§FS-non-goals.6](functional-spec/FS-non-goals.md#6-decision-database-audit-log-history-tracking) is untouched — a marker's existence is a fact about the tree in the way a `grund.toml`'s is. These are refusals, not prompts: `init` still never asks a question ([§FS-non-goals.10](functional-spec/FS-non-goals.md#10-interactive-mode)), it declines and names the flag that would have let the run through, which is the only shape a guard can take in a non-interactive command and is why the unconditional rules carry no flag at all. **No existing test could have caught this**, and that is the last part of the record: `workdir()` in the CLI init suite builds a bare directory under `target/init-tests/` and `test_root()` in the core suite builds one under the system temp root — no marker, no manifest, nothing — which is precisely the "shows no sign of being a project" state, and it was the assumed-good state of every init fixture in the repository. The condition the guard exists to refuse was the condition the whole suite ran in. The five core fixtures that scaffold into a bare temp root now say `no_vcs: true` rather than growing a fake `.git`, because faking the marker is what made the hole invisible in the first place, and the new cases build their targets outside this repository's own git tree — the one place the rule can actually fire. `<path>` interpretation moved with the rules into `crates/grund-core/src/init_target.rs`: what the target is, and whether it may be scaffolded, decided in one place. `InitOpts` gains a public `no_vcs` field: a documented, additive break in the library surface ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)) for downstream code that constructs it with an exhaustive struct literal rather than from `Default`. Resolves issue #88. PR #91

- [§FS-check.3.16](functional-spec/FS-check.md#316-duplicate-section-path) / [§FS-show.2.2.2](functional-spec/FS-show.md#222-ambiguous-section) / [§AR-scanner.2.2](architecture/AR-scanner.md#22-section-detection) / [§DF-duplicate-section-path](decisions/functional/DF-duplicate-section-path.md#df-duplicate-section-path-a-section-coordinate-names-one-heading-or-the-run-says-so): **two headings claiming one dotted section path are no longer accepted in silence** (PR #108, [issue #97](https://github.com/vjovanov/grund/issues/97)). A section path is a citation target, so `## 1. Inputs` and `## 1. Outputs` under one declaration gave `§<ID>.1` two destinations with nothing reported — the case [§REQ-no-wrong-citation.1](requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution) names in as many words, and the twin one level down of the duplicate-declaration error [§FS-check.3.3](functional-spec/FS-check.md#33-duplicate-declaration) has always raised. **The two readers of the section map disagreed, and the one a user sees did worse than pick.** The scanner recorded the path last-wins, so the map held the second heading; `show` never read that line — it re-scanned the file and matched the path itself, with no guard against matching twice, so `grund <ID>.1` returned **both** headings and **both** bodies as one slice, a body no heading in the file spans. The section map now records a path **once, by the first heading** — the one a reader scrolling to section `1` meets and the one the finding anchors at — with later claimants kept in a parallel list that is inert to every lookup. The verdict change is owned rather than excused: [§REQ-backwards-compatibility.4](requirements/REQ-backwards-compatibility.md#4-what-was-never-a-promise) does *not* cover it — that clause wants a construct which produced **no output**, and this one printed a body — so the case rests on [§REQ-backwards-compatibility.3](requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations) instead, where a verdict may flip in the release that introduces it: the finding names every colliding line, renumbering one heading clears it, and this entry is the release saying so. What a tree loses is a green run over output that was wrong. No `grund_config_version` bump and no `AGENTS.md` block bump.

- [§FS-config.3.5](functional-spec/FS-config.md#35-scan--what-gets-walked) / [§AR-scanner.1](architecture/AR-scanner.md#1-tree-walk) / [§DF-symlink-scan](decisions/functional/DF-symlink-scan.md#df-symlink-scan-a-symlink-in-the-scanned-tree-is-followed-and-the-report-names-the-link): **a symlinked file inside the scanned tree is no longer dropped from the walk in silence.** The walker was built without `follow_links`, so a symlink entry was neither a file nor a directory to it and fell through with nothing reported. One skip produced two wrong answers at once: the citations in the linked file were never read, so a dangling one passed, and every declaration that file cited was reported `declared but never cited` because the edge that would have retired the warning went with it. Replacing the link with a copy of the same bytes changed the verdict from clean to two findings — a false negative that also lies about the tree it read, breaking [§REQ-no-missed-citation.1](requirements/REQ-no-missed-citation.md#1-no-silent-skips) and [§REQ-no-wrong-citation.2](requirements/REQ-no-wrong-citation.md#2-no-false-alarms) in the same run. **The spec had discussed symlinks only as `[scan] include` roots**, so a symlinked *descendant* was not the bounded, declared blind spot [§REQ-no-missed-citation.2](requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded) permits — it was one nobody had written down, and therefore one no reader could plan around. Links are now **followed, files and directories alike**, including a target that resolves outside the config root: the file is in the tree by the path the repository wrote, and refusing it by where its target lands would leave the false-alarm half of the bug standing for the case a user is most likely to have written deliberately. Everything is reported at the **in-tree link path**, never the target's — a target path may be absolute and may sit outside the root, so a finding wearing it is one nobody can jump to and one `relative_paths` cannot render, and naming the link is also what keeps `--full` purely additive ([§FS-check.1.3](functional-spec/FS-check.md#13-the-full-tree-scope---full)), whose promise is that the in-scope lines are the plain run's *spelling included*. The directory rules keep applying to a followed directory under its link name, so `docs/node_modules -> ../../node_modules` is excluded exactly as a real directory of that name would be. Following links means a **descendant** can alias and not just a root, so the identity pass `--full` already ran for an aliased root now also runs when the walk met a symlink — and only then: a `realpath` per file on every run of every repository is not a price the ordinary walk should pay ([§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)). That made *which* of two spellings survives a question the filesystem used to answer, so each root's own file list is sorted before it joins the others and the rule is written down: the earlier root wins, and within one root the lexicographically first path ([§FS-errors.4](functional-spec/FS-errors.md#4-determinism)). **`follow_links` also turns a link the walker cannot resolve into an error entry in place of the file**, and the old `entry?` would have made one broken link abort the whole scan — the opposite of what [§FS-check.2](functional-spec/FS-check.md#2-outputs) promises about a file the walk cannot read. Those are collected as per-file scan failures instead: reported `error: <path>: <reason>` at the link's own path, the walk continuing, the run exiting `2`. The report is owed only where the walk would otherwise have read *through* the link, which is two different tests because a loop and a broken link carry different evidence: a loop is a directory the walker was descending into, so it always earns one — with the hidden-name and `[scan] exclude` tests re-applied by hand, since the walker's own directory filter never sees an error entry — while a broken link is judged by the same `[scan] extensions` and ignore-file rules as any other file, so a dangling `docs/logo.png -> nowhere`, or one `.gitignore` covers, stays silent, having never been going to be read. The ignore half needs its own answer, because the walker applies those files to the entries it *yields* and a link it cannot resolve arrives as an error instead: the link's own directory is re-walked one level deep, without following links, where the link is an ordinary entry and the rules do reach it. Without that gate a repository full of links to build outputs turns red for reasons that have nothing to do with citations, and a mode that cries wolf about links is one whose scan errors get ignored. **The two boundaries the walk must not cross are asked by identity, not by name.** A workspace member root ([§AR-workspace.6](architecture/AR-workspace.md#6-the-workspace-boundary)) is pruned by comparing an entry's path *relative to the scan root* against precomputed member suffixes, and a member reached under a **link** name matches none of them — so `docs/link -> ../sub`, or `docs/link -> ../packages` with the member one level below it, walked the root scan straight into the member namespace, absorbed its declarations, and reported them as duplicates of themselves. The E2E case directory test had the same shape one compare down: it asks whether a directory's parent *is* the cases root, so a link onto that root scanned every fixture repo the manifest pass owns. A boundary is a property of the directory, not of the name it is reached under, so a directory the walk reached **through** a link is resolved with `canonicalize` and asked again — under both names, which is what keeps a case directory that is *itself* a link pruned. Only link-reached directories pay the syscall: the walk records each directory link it meets and a prefix test answers for the whole subtree. **The identity pass is armed by a list, not a flag.** The first cut raised a flag on the first symlink it saw, and the pass canonicalizes every file in the list — so one link anywhere bought a `realpath` per file, measured at ~2.7x on a 20 000-file tree with a single link in it, against a doc comment in the same file saying that was not a price the ordinary walk should pay. What the walk records instead is *which* files can wear a second name — a link, anything below a directory link, every file of an aliased root — and only those are resolved; the paths they resolve to are the only ones another file can turn out to be, so everything else is answered by a lookup and never resolved at all (measured against `main` on a 20 000-file source tree, and on two machines, which is why these are ranges rather than decimals: with **no** symlink in it 1.02–1.08x plain and 1.08–1.10x `--full`, which is what `follow_links` costs; with a **single** symlink 1.17–1.32x plain and 1.13–1.38x `--full`, the identity pass costing a hash lookup per file once anything in the tree can wear a second name; a tree of 2 000 symlinks pays 2 000 `realpath` calls and lands at 1.66–1.69x plain and 1.48–1.74x `--full`, which is the cost of the links and not of the repository). **Two verdict moves are worth naming**, both correct and both new ([§REQ-backwards-compatibility.1](requirements/REQ-backwards-compatibility.md#1-what-is-covered)): the identity pass is no longer conditioned on `--full`, so `include = ["docs", "docslink"]` with `docslink -> docs` stops reporting `duplicate declaration` and exits `0` instead of `1` — the duplicate was always false, and `--full` was merely where two roots were known to overlap; and where one file has two in-tree names, findings are reported at whichever spelling the rule selects — the earlier root, the lexicographically first path within it — which can be the link rather than the real file the plain run used to name. **`grund fmt` was the one command that walked this tree and said nothing about what it could not read.** It took a non-reporting wrapper justified by having "nowhere to put a scan error", while [§FS-fmt.3](functional-spec/FS-fmt.md#3-outputs) has defined exit `2` as the I/O failure all along: on a tree where `check`, `refs` and `list` each printed two `error:` lines and exited `2`, `fmt --check` printed the rewrite it would make and exited `1`. It now names every unreadable path in the [§FS-errors.2.2](functional-spec/FS-errors.md#22-cli-level-message) shape after its report and exits `2`, with `FmtOutput` carrying the same list so an embedder sees the same incompleteness — an additive field on that struct ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)). A run that needs the whole declaration set before it rewrites anything — `--cross-refs`, or a shorthand to expand — keeps its earlier refusal, now written down: an unreadable path is fatal up front there, because wrapping or expanding against a partial set can name the wrong declaration. **`fmt --write` no longer writes through a link that leaves the config root** ([§FS-fmt.2.3.2](functional-spec/FS-fmt.md#232-a-link-that-leaves-the-config-root-is-not-written-through), [§DF-symlink-scan.2.5](decisions/functional/DF-symlink-scan.md#25-fmt---write-refuses-a-link-that-leaves-the-config-root-and-nothing-else)): it read one and rewrote it on disk at the target, outside the root, with a relative cross-reference broken where the file actually lives. Reading a foreign file and editing it are different acts ([§REQ-no-data-loss.2](requirements/REQ-no-data-loss.md#2-writers-touch-only-what-they-own)), so the write, and only the write, stops at the boundary — the file is still read and still checked, `--write` names it once on stderr, the exit code is untouched, and the dry run still lists what it would have done. A link whose target is *inside* the root is written through, with one residue recorded rather than fixed: the file is read once under one of its two spellings, so `--cross-refs` anchors its relative links to that spelling and they are wrong at the other name — no single relative path is right from two directories. **The gate that decides which unresolvable links are owed a report is now the same for both kinds.** A loop was tested against the hidden-name and `[scan] exclude` rules only, so a looping directory link that `.gitignore` covered still turned a green tree red — the exact failure the decision's own rationale argued against, in the paragraph that declared a loop "always owed one". The ignore files now gate both, and `[scan] extensions` gates a broken link as well, which names a file where a loop names a directory. Two reporting bugs go with it: **a scan error was emitted once per walk root** — the file list was deduplicated after the sort and the error list only sorted, so under `--full`, where every `include` root is walked beside the config root that contains it, every `error:` line printed twice; and **a loop that escapes the walk root was reported at a doubled path**, `error: docs/up/docs/up` for `docs/up -> ..`, because the target is not an ancestor when the walker meets it and it descends a second copy of the tree first. The report is now the shortest path below the walk root naming the same *link*, tested by identity — the canonical directory holding it plus its name — rather than by "the first prefix that is a symlink", since a link two spellings deep is a different link and `docs/shared -> ../shared-docs` must not be blamed for a `self -> .` inside it. Two blind spots are declared rather than closed, both bounded ([§REQ-no-missed-citation.2](requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)): a broken link with **no extension** is not reported, because a target that does not exist cannot say whether it was a directory worth descending into and reporting every extensionless dangling link is the noise the gate exists to prevent; and the "reported at the in-tree link path" rule is scoped to a link met inside a *walked tree*, since an explicit path argument is resolved before any walk begins and `grund check docs/beta.md` on a symlink therefore reports at the target — pre-existing, and the resolution that makes `grund check <path>` work at all. The tree walk moved to `crates/grund-core/src/scanner_walk.rs` along the seam [§AR-scanner](architecture/AR-scanner.md#ar-scanner-how-grund-discovers-declarations-and-citations) already draws — §1 is a directory traversal, §2 is a line-by-line pass over a file's text, and they meet only at the file list one hands the other. **A second review round found the boundary rule stated in only one direction.** The member list a project carries says what lies *below* it, so a leaf member has none at all, and a symlink inside one member walked into a sibling's tree — or back up into the root project's — and filed that project's declarations under this one's namespace as duplicates of themselves. That is the same harm [§AR-workspace.6](architecture/AR-workspace.md#6-the-workspace-boundary) names for the root scan and it is mutual, so every project a run loads now carries the canonical root of every other one: a directory reached through a link is asked which project owns it, the innermost project root that contains it, and one owned by anybody else is not descended into — in either direction, and whether the link lands on a directory or on a single file ([§FS-workspace.6](functional-spec/FS-workspace.md#6-nested-project-boundary)). A directory **no** project owns is still followed, because content outside every project is content the repository linked in deliberately. A member checked on its own loads no workspace ([§FS-workspace.5](functional-spec/FS-workspace.md#5-command-scope)) and therefore cannot be told where the other projects are; that bound is written down rather than closed. **The report-at-the-link rule failed for the walk root itself.** An explicit scope is resolved before the walk so a run can recognize that it *is* the config root, and the resolved path was then used as the root to walk — so a repository reached through a symlinked path (a linked `~/work`, macOS resolving `/var` to `/private/var`) had every finding spelled physically: absolute, outside the root, and unrenderable by `relative_paths`. The resolution now answers only the question it was asked and the walk keeps the name it was given ([§FS-config.3.5.2](functional-spec/FS-config.md#352-a-finding-names-the-in-tree-link-path)). **`fmt --check` could never go green** on a tree holding a link that leaves the config root: the dry run listed the rewrite it would make in the file `--write` refuses, so it named a pending edit no author could clear and any CI gate or pre-commit hook built on it was red forever. The dry run now reports the **refusal** instead, in the same `warning:` shape, and `--check` predicts `--write` again ([§FS-fmt.2.3.2](functional-spec/FS-fmt.md#232-a-link-that-leaves-the-config-root-is-not-written-through)). **A loop was reported and then walked into.** `docs/up -> ..` is inside none of the directories the walker is descending when it meets it, so the walker descended a complete second copy of the tree, printed findings out of a tree the same run had just called unreadable, read past `[scan] include`, and under `--full` printed the error twice — once with an empty directory name where the ancestor was the config root. A link whose target is at or above the walk root is now pruned where it is met and the report raised without the descent, behind the same hidden-name, `[scan] exclude` and ignore-file gates ([§FS-config.3.5.5](functional-spec/FS-config.md#355-a-link-the-walk-cannot-resolve-is-reported-and-not-walked-into)). A two-hop loop — `docs/a/link -> ../b` with `docs/b/link -> ../a` — is reported at `docs/a/link` and `docs/b/link`, the two names a user can go and fix, rather than at the doubled `docs/a/link/link` the descent produced: the link's identity is re-expressed under the walk root, which finds a *sibling* spelling where a search over the reported path's prefixes could not. **`fmt` rendered its own paths against each project rather than against the run**, so in a workspace a member's unreadable path came out as `docs/FS-003-gone.md` where `check` says `packages/sub/docs/FS-003-gone.md` — a different real file in the same run's output — and the refusal line had the same defect; both now render where every other path `fmt` prints does ([§FS-fmt.3](functional-spec/FS-fmt.md#3-outputs)). `--write` turns `--cross-refs` on by itself wherever the scope holds Markdown ([§FS-fmt.6.6](functional-spec/FS-fmt.md#66-why-generated-configs-enable-cross-references)), so the abort-before-anything-is-written case is its **ordinary** path rather than the exception [§FS-fmt.3](functional-spec/FS-fmt.md#3-outputs) described it as, and that abort now names itself — `error: nothing was rewritten: <path>: <reason>` against the partial run's bare `error: <path>: <reason>` — because two exit `2`s that mean opposite things must not be spelled the same. The refused paths are returned on `FmtOutput.refused_writes` and printed by the command surface, as `scan_errors` beside them already were: an additive field ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)). **Three more verdict moves, all correct and all new** ([§REQ-backwards-compatibility.1](requirements/REQ-backwards-compatibility.md#1-what-is-covered)): a workspace whose members link into each other stops reporting `duplicate declaration` and exits `0`; `fmt --check` on a tree with an escaping link exits `0` where it exited `1`; and a tree with a loop above its walk root stops reporting the findings it read out of the second copy. - [§FS-fmt.2.4.1](functional-spec/FS-fmt.md#241-a-shorthand-in-a-numeric-run-is-not-rewritten) / [§FS-check.3.15](functional-spec/FS-check.md#315-shorthand-citation-in-a-numeric-run) / [§FS-fmt.3](functional-spec/FS-fmt.md#3-outputs) / [§DF-shorthand-numeric-run](decisions/functional/DF-shorthand-numeric-run.md#df-shorthand-numeric-run-a-marked-shorthand-glued-to-another-number-is-a-numeral-not-a-citation): **`grund fmt --write` no longer expands a number-only shorthand that is glued to a second number**, and says so instead of rewriting it. A changelog recording an ID remapping writes the old numbers as runs — `<§>SPEC-001→SPEC-003`, `<§>SPEC-001/003`, `<§>COMP-047/046/049`. Every character after the first number is one that cannot continue an ID, so the trailing-boundary rule of [§DF-number-only-citation-shorthand.2.6](decisions/functional/DF-number-only-citation-shorthand.md#26-the-full-id-always-wins-and-only-a-whole-token-is-a-shorthand) passed and today's slug was attached to a number that named something else, turning a renumbering table into a set of pointers at live, unrelated declarations. **The rewrite was silent and nothing downstream could see it**: the output is a well-formed citation of a real declaration, so `grund check` passed and the run reported success. That is the worst-shaped instance of the class [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) forbids — not a citation that resolves to nothing, but one that resolves to the *wrong thing* while reporting green — and it is only findable by a human reading the prose, which is how it was found, in a 5,750-line diff re-read after the fact. The rule the boundary test was missing is that a whole token is not always a citation: `§2.4` asked *does this token end here?*, which is a lexical question, and never asked *is this token being used as a citation?* The marker settles the first and cannot settle the second — a `§` in front of `SPEC-001→SPEC-003` says the sentence is about IDs, not which token in it is the reference — so the shorthand, which is precisely the ambiguous shape [§DF-number-only-citation-shorthand.2.4](decisions/functional/DF-number-only-citation-shorthand.md#24-the-marker-is-required-a-bare-shorthand-is-text) required the marker for, needs one more piece of evidence. **The evidence is the second number, not the punctuation.** A site is a numeric run when the characters after the token form a non-empty delimiter sequence carrying no whitespace, no marker, and no bracket or quote, followed by another `[id] number_pattern` match or another whole shorthand written **unqualified** — which derives `→`, `/`, `..`, `…`, `|`, `,` and everything else anyone writes between two numbers without enumerating a list that would be one defect short forever. The three exclusions are the safety margin: whitespace, because the gluing *is* the evidence and `<§>FS-042 (2024)` is an ordinary citation under the default `number_pattern = "\d+"`; the marker, because `<§>FS-042, <§>FS-043` is two citations the author marked one at a time; and brackets and quotes, because those bound a construct instead of gluing two numerals — a walk that crossed one would join the characters *closing* the construct the citation sits in to the ones *opening* the next and read the next construct’s number as the second one, making a run of the Markdown link `[<§>FS-042](FS-042-user-login.md)` that `fmt --cross-refs` itself writes and of the footnote reference `<§>FS-042[^1]`. Requiring the neighbour to be **unqualified** is the same guard from the other side: an `<alias>/` namespace precedes a citation and never follows one, so a path that happens to end in an ID-shaped segment — `docs/functional-spec/FS-042-user-login.md` — is not a second number. Both are shapes an ordinary citation wears, and refusing them would leave a `shorthand-numeric-run` error naming an edit `fmt` will never make. The rule reads forward only — a glued number-shaped token to the *left* is also what `2026-08-19/<§>FS-042` looks like, and refusing those would cost real citations for no evidence. The site is **reported, not skipped in silence**: a new `shorthand-numeric-run` error names both exits — the canonical form to paste if it was a citation, and the `<§>` escape if the numbers were a mapping — because only the author knows which. Nothing turns green-to-red: these sites are already errors today, and what changes is that the message stops advising the edit that corrupts the line. Recognition is untouched, so the site still resolves, still counts as an edge, still grounds its file, and its declaration is still not reported unused — dropping the edge would tidy the model and reintroduce the exact false negative the shorthand rule was added to end. Only the message that names the *rewrite* changes: a shorthand in a run matching zero or several declarations keeps its [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) message, because that is a resolution failure and a run is no reason to say less about it. The editor's live transform ([§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform)) applies the same rule, with one residue it cannot avoid: an author typing a fresh run has not written the second number yet when the keystroke that ends the token fires, so that expansion happens — visibly, one undo away, which is the loud failure and not the silent one. Independent of the rule, and the part that outlives it: **`grund fmt` now prints the text every expansion writes** — `docs/notes.md:1: shorthand → canonical: <§>FS-042 → <§>FS-042-user-login` — so a `--check` run is a review *before* `--write` puts it on disk. The other three rewrites leave the ID token byte-identical and only move markup around it, so a wrong one dangles or fails to resolve and `check` names it; expanding a shorthand is the one pass that writes characters *into* the ID, information the source never carried, and naming only the line and the rewrite class was enough to review the former and not the latter. `FmtChange.label` is therefore a `String` rather than one of four fixed labels — a documented, additive break in the library surface ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)). No `grund_config_version` bump, no `[id]` key, and no `AGENTS.md` block bump: the rule is derived from `[id] format` like the shorthand itself, and a knob would let two installs disagree about what a citation *is* ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). The numeric-run test lives with the `[id] format` template in `id_format.rs` rather than in `shorthand.rs` ([§AR-scanner.2.6](architecture/AR-scanner.md#26-number-only-shorthand-citations)) — where a token of the grammar ends is a question about the shape, and the test reads the shorthand patterns directly — and its cases are one module across all three stages, because the defect being guarded against is a rewrite and a report agreeing with each other and both being wrong. Resolves issue #81. PR #90

It is that the convention became repository prose: the generated entrypoint taught the budget and then left the agent to *infer* the arrangement from the surrounding files ([§FS-init.2.3](functional-spec/FS-init.md#23-generated-agent-entrypoints)) — the guessing [§GOAL-friendliness-first](goals.md#goal-friendliness-first-as-user--and-agent-friendly-as-possible) exists to remove. And one arrangement in particular is worth being able to demand: under `[reference] strict = false` a bare `// FS-x: note` line *is* an inline declaration heading, so writing the marker and the colon is what makes "cites `FS-x`" and "declares `FS-x`" two visibly different lines instead of one shape read two ways. `inline_note_layout = "citation-first-colon"` requires a run of citations joined by exactly `, `, then a colon, then a space and the note — or a colon that ends the line — read on the content left after the comment prefix and any block closer are stripped, exactly as the note-presence rule already reads it. A leading Markdown list marker is skipped with that indentation, so the enumerated block of grounded points every doc-comment convention renders as a list — `/// - §<ID>: note` — opens with its run like any other line; the marker stays note text where §2.3 decides whether the site carries a note at all, so no bulleted pointer is silently reclassified. The rule is judged **per line, not per site**: a line carrying no citation is unconstrained, so the summary-then-citation doc-comment that Rustdoc, Javadoc, and JSDoc all encourage stays legal, and the finding lands on the line an author has to edit rather than on the block's opener — the one member of the `inline-citation-style` rule that does not anchor at `first_line`. Per line is not *every* line: the site's first citation-bearing line opens the note and is always judged, a later one is judged when it opens with a citation of its own, and a citation-bearing line that opens with prose is the continuation of a note that already opened correctly. So a note may wrap and still name a second point on the way, which is exactly the freedom the line budget and the same-line rule already granted and which judging every such line quietly took back. A site with **no note at all** is exempt, because a layout is a relation between a citation and a note and `// §A  §B` is a pure pointer; the deliberate consequence is that a `// §A` line followed by a prose line *in the same block* is one site with a note, so the citation line is judged and fails. The form is **exact** — a space where the comma belongs, a comma with no space, a space before the colon, a dash for the colon — because a tolerant matcher would leave the project with the variation the key exists to remove while still leaving an agent to guess which tolerated spelling the humans write. Citations *later* on the line are free, so `// §A: note (see also §B)` conforms; only the opening run is constrained. Two keys rather than one, because a project answers "which style?" and "gate on it yet?" at different times: adopt the style so the entrypoint starts teaching it, migrate the tree with `warn` as the worklist, then move to `error`. That is a per-rule *channel* choice with existing precedent — `warn_on_suggested` does it for the soft cap, `[citations]` `must`/`should` does it per obligation — and not configurable severity: what an error and a warning *mean*, and how the exit code follows, stay fixed by [§FS-non-goals.9](functional-spec/FS-non-goals.md#9-severity-exit-code-or-report-ordering-customization), and both installs read the level from the same committed `grund.toml` ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). Both keys default to the inert value, so **nothing turns red on upgrade** ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)): no `grund_config_version` bump, and no `AGENTS.md` block bump either — under `any` the rendered block is byte-for-byte what the previous release produced, so no repository's managed block goes stale for a rule that changes nothing about what it should write. Under `citation-first-colon` the block gains one sentence naming the form with the project's own marker — deliberately wider than the gate, since a doc-comment that declares an ID is not a citation site and its body is therefore taught the form and never measured against it ([§FS-inline-citation-style.3.3](functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit), rule 6) — and the *enforcement level* deliberately does not change it: the house style is what an agent is asked to write, and an agent told the form and then told it is only advisory has been handed a reason to ignore it. The half of the report that is **declined** is `grund fmt` normalization, in `--check` and in `--write` alike ([§DF-inline-note-layout.2.5](decisions/functional/DF-inline-note-layout.md#25-check-only-grund-fmt-is-not-involved)). Turning `// note (§A).` into `// §A: note.` is a prose edit wearing a token edit's clothes — it needs to decide where the sentence ends, whether the trailing parenthetical was the citation, and what punctuation the remainder now needs, which is the judgment [§FS-non-goals.3](functional-spec/FS-non-goals.md#3-code-ast-parsing) refuses to acquire; a formatter that is right most of the time fails here as a silently mangled comment in a commit nobody read line by line. What the report actually needs is served without it: the fix is one token in the loop of whoever is already editing the line, and migrating an existing tree is what `warn` is for. `grund config show` prints both keys at every value, inert or not, and `templates/grund.toml` carries both with their accepted-value comments so the generated config still teaches the whole schema ([§FS-config.3.1](functional-spec/FS-config.md#31-reference--citation-form), [§FS-check.3.10](functional-spec/FS-check.md#310-inline-citation-style-violation), [§FS-check.4.4](functional-spec/FS-check.md#44-inline-note-layout-deviation-opt-in)). The enum is closed and ships one member on purpose: `citation-first-dash`, a bare `citation-first`, a bracketed form, `note-first-parenthesized`, and citations on a line of their own were all considered and all left out until something asks for them, since each costs its own spec examples, its own rendered sentence, and its own coverage, while adding one later is additive; a free-form `"{cites}: {note}"` template is rejected outright for now, because a template is a small language — parser, inverse matcher, escaping, validation — and there is no way to render one canonical sentence into an entrypoint from a form the tool was handed rather than one it knows. Implementation-wise the rule is one file, `crates/grund-core/src/inline_note_layout.rs`, over a second holding what is not the rule — `comment_line.rs`, where reducing one line to its content and its citation tokens now lives for the scanner walk and both note verdicts alike ([§AR-scanner.3](architecture/AR-scanner.md#3-output), [§AR-checker.2.14](../crates/grund-core/src/checker.rs)): the scanner records, per inline citation site, the ascending list of its lines that deviate, and the checker reads that list instead of re-opening the file, so the rule stays a pure pass over `Findings`. Under `any`, and under a layout whose check is `off`, no line is classified at all, which is why neither the default path nor a documented-only style tokenizes or classifies a line on the key's account ([§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)); the memo that lets the two verdicts share one tokenization is built only where a second reader exists, so the default path allocates none of it and pays one comparison per site. It comes out ahead on the way: the comment-prefix list every note walk reads is now built once per comment block rather than once per line, which it was before this key existed. Gathering the classifier, the note-presence helpers it shares, and the checker rule in that one file — the arrangement `shorthand.rs` already uses, for the same reason: four halves of one invariant in four files with nothing naming the invariant is how the halves drift — took `scanner.rs` from 1523 to 1383 lines — the citation tokenizer left with the helpers that are now its only callers, which is most of that file's standing `until` clause — and `checker.rs` from 1083 to 1013, and every file-size ceiling drops to what the files now measure; sharing them is literal and lazy, since a line of a site is tokenized once, when the first pass that needs it asks, and the note-presence verdict and the layout verdicts read that one answer — so a block the note walk leaves early, and every block under a configuration that classifies nothing, is read no further than its answer needs. One reading changes for every project, not only for one that sets the key: what separates two citation tokens of a chain — whitespace, or a single comma with optional whitespace — is no longer note text ([§FS-inline-citation-style.1](functional-spec/FS-inline-citation-style.md#1-scope)), so `// <§>FS-a, <§>FS-b` is a pure citation comment. It has to be: that is the spelling the layout mandates in front of a colon, and it was previously read as prose — rejected outright under `inline_style = "citation-only"`, and reported as a layout deviation under the new key for lacking the note it does not have. Resolves issue #52. PR #65
