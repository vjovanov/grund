# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

## Unreleased

### Added

- [§FS-init.1.2](functional-spec/FS-init.md#12-refused-targets) / [§FS-init.4](functional-spec/FS-init.md#4-exit-codes): **`grund init` now decides whether a target may be scaffolded at all before it writes anything.** The home directory is refused unconditionally, no flag lifting it; a target that no `.git`, `.hg`, `.jj`, or `.svn` marker covers, in it or any ancestor, is refused unless the new `--no-vcs` says otherwise. A refusal is total — nothing is created, appended, or updated, not even the files that would have been unobjectionable — the run exits `2`, and `--dry-run` reports the refusal rather than a preview, because a preview of a run that would be refused *is* that refusal. `--no-vcs` is deliberately not `--force`: `--force` decides whether files `init` owns get overwritten ([§FS-init.3](functional-spec/FS-init.md#3-non-intrusive-guarantees)), this one says *this really is where I want a project*, and a run may need either, both, or neither. The reported accident was a shell slip into `$HOME` followed by `grund init --claude`, which appended the 56-line managed block to a personal `~/.claude/CLAUDE.md` — the global instruction file every agent session in every project loads — turning a three-line file into a 59-line one, unprompted and recoverable only because the block is delimited and the user happened to look. **Nothing in the spec was violated when that happened**, which is the part worth recording: every guarantee in [§FS-init.3](functional-spec/FS-init.md#3-non-intrusive-guarantees) is scoped *inside* a file — user-authored content preserved, line endings preserved, the config never overwritten, re-running a true no-op — and the entire contract on `<path>` was that it exists and is a directory. The list answered *what will `init` not touch in a file it was pointed at* and never *should it have been pointed here*, so `$HOME` was a valid target by construction. Appending made it worse rather than better: appending to an existing entrypoint instead of inventing a competing `AGENTS.md` is the **conservative** branch in this spec's own value system, the first bullet of §3, so the one behavior that did the damage is the one every review read as the polite option. The collision underneath is that two commands know `~/.claude/CLAUDE.md` and did not know about each other. [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions) already models it correctly — a machine-global instruction file, gated on `~/.claude/` existing, receiving a deliberately small marked rendering block — while `init` modelled the same path as purely `<path>`-relative, so the *same signal*, `.claude/` exists, reads as "this machine runs Claude, sync the rendering block" to one command and "this project uses Claude, scaffold the project block" to the other. Both readings are right in their own scope; in `$HOME` they name one file, and nothing arbitrated. A second, independent rule therefore refuses any planned entrypoint that is one of that table's file-backed user-global targets, checked per path rather than per target — every path the run would write, **the canonical `AGENTS.md` included**. That rule is not the home rule restated, and the arithmetic that says it is is the same slip that produced the accident: it holds `<path>` at `$HOME` and asks which of the two tables' paths coincide there, but `<path>` is arbitrary, and `<path>/AGENTS.md` with `<path>` at `~/.codex`, `~/.config/zed`, or `~/.pi/agent` **is** the machine-global file, as is `<path>/GEMINI.md` under `~/.gemini`. The home rule says nothing about those targets — they are not the home directory — and on a machine whose dotfiles are a repository, which is the usual state of a machine that has those directories at all, neither does the version-control rule. Four of the five reachable rows are the canonical entrypoint, which is both the one `init` reaches for by default and the one file it *overwrites* rather than appends to under `--force` ([§FS-init.3](functional-spec/FS-init.md#3-non-intrusive-guarantees)) — the same accident with nothing left behind to hand-remove — and the plan carries it as a flag rather than as a path, so a check handed the entrypoint list could not see it. The division is the one [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions) already states — the user-global files carry machine-wide policy and are `grund integrations --write`'s to manage, the repository entrypoint carries this project's syntax and is `init`'s. The version-control rule is the only one with a legitimate other side (a directory scaffolded before `git init`, a project under no VCS at all), which is why it alone gets a flag; presence is tested rather than type, since a linked worktree and a submodule both write `.git` as a *file*, and nothing is parsed and no command is run, so [§FS-non-goals.6](functional-spec/FS-non-goals.md#6-decision-database-audit-log-history-tracking) is untouched — a marker's existence is a fact about the tree in the way a `grund.toml`'s is. These are refusals, not prompts: `init` still never asks a question ([§FS-non-goals.10](functional-spec/FS-non-goals.md#10-interactive-mode)), it declines and names the flag that would have let the run through, which is the only shape a guard can take in a non-interactive command and is why the unconditional rules carry no flag at all. **No existing test could have caught this**, and that is the last part of the record: `workdir()` in the CLI init suite builds a bare directory under `target/init-tests/` and `test_root()` in the core suite builds one under the system temp root — no marker, no manifest, nothing — which is precisely the "shows no sign of being a project" state, and it was the assumed-good state of every init fixture in the repository. The condition the guard exists to refuse was the condition the whole suite ran in. The five core fixtures that scaffold into a bare temp root now say `no_vcs: true` rather than growing a fake `.git`, because faking the marker is what made the hole invisible in the first place, and the new cases build their targets outside this repository's own git tree — the one place the rule can actually fire. `<path>` interpretation moved with the rules into `crates/grund-core/src/init_target.rs`: what the target is, and whether it may be scaffolded, decided in one place. `InitOpts` gains a public `no_vcs` field: a documented, additive break in the library surface ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)) for downstream code that constructs it with an exhaustive struct literal rather than from `Default`. Resolves issue #88. PR #91

### Fixed

- [§FS-init.2.1.1](functional-spec/FS-init.md#211-one-entrypoint-per-agent) / [§FS-init.2.2](functional-spec/FS-init.md#22-stdout--stderr): **`grund init` no longer writes a second entrypoint for an agent that already has one.** `--claude` wrote `CLAUDE.md` and `.claude/CLAUDE.md` unconditionally, so a repository with the first and no `.claude/` directory got the second created — and Claude Code reads both, which put the whole managed block in the model's context twice, for no benefit. Across a five-project workspace that meant deleting a freshly written `.claude/CLAUDE.md` after every `init`, five times, and remembering to do it again on the next upgrade. The block is the file [§GOAL-token-economy](goals.md#goal-token-economy-give-an-agent-the-right-amount-of-spec-not-the-whole-file) is about — it is read at session start, in full, before any work — so paying for it twice is the one cost that goal exists to refuse. **The table `init` selects from already knew the agent behind each path and never used it for this**: `agent` answered *does this flag select this row* and was asked nothing else, so a row was a path and two rows were two files, which is exactly right for choosing what to *update* and wrong for choosing what to *create*. `init` now creates **at most one entrypoint per agent, and only for an agent that has none**; every entrypoint the repository already has is still appended to or updated in place, however many there are, because an existing file is the user's and `init` does not decide which of their files to stop maintaining. The one it creates is the first of that agent's paths that is free: for Claude, `CLAUDE.md` — the root-visible form, chosen for the reason `init` also generates the bare `grund.toml` ([§DF-config-file-location.2.3](decisions/functional/DF-config-file-location.md#23-grund-init-writes-the-bare-grundtoml)), that it is the form the rest of the ecosystem uses and it adds no hidden directory to a repository that has none. The directory form stays one command away and needs no flag to reach: create `<path>/.claude/CLAUDE.md` empty and re-run, since `init` fills in every entrypoint that exists. The same reasoning fixes automatic mode, where `.claude/` used to create both aliases — the directory proves Claude is in use, which is one fact, not two files. **The rule is per agent, not per Claude**: Cursor reads `.cursor/rules/grund.mdc` and the legacy `.cursorrules`, and `--cursor` against a repository whose rules live in the legacy file added the modern one beside it — the same defect one row down, now the same fix, with migration off the legacy form being *delete it, then re-run* rather than *end up with both*. A companion that is a **symlink** to `AGENTS.md` counts as the agent having one, and the first draft of this fix had that backwards. Reading the symlink as "not the agent's own file, so write it a real one" is defensible — it is the canonical file under another name — but it reproduces the reported bug exactly: with the default config the two files carry byte-identical blocks, so `--claude` against a repository with `CLAUDE.md -> AGENTS.md` wrote `.claude/CLAUDE.md` and Claude read the same 55 lines twice, silently, on that run and every re-run. Automatic mode did it too, through the workspace alias, with nothing asked for at all. The reason that carve-out exists is narrower than the carve-out was: the two files differ only when the repository commits `[reference] conversation = "link"`, which gates the Claude entrypoints to a form the canonical file is not allowed to carry ([§FS-init.2.3.4.17](functional-spec/FS-init.md#23417-clickable-citations)). So it is gated on exactly that — with the key, `--claude` still writes the Claude-specific file the symlink left free, which is the escape hatch that section depends on; without it, the symlink is simply the agent's copy and nothing is written beside it. That section's `note:` follows the same reasoning one step further: it now names the fix that is still open — write the entrypoint where there is none, delete the symlink where this run just wrote one — because advising the command that has just run is a note that never retires. Where a repository already carries two of one agent's entrypoints, both are maintained and the run says so in one `note:` line naming the files and the agent that reads them — the run that just wrote to each of them is the only place that duplication is visible, and silence there is what let it accumulate. The `--dry-run` half of the report needed no new wording: the run that would have printed `exists CLAUDE.md` beside `would-write .claude/CLAUDE.md`, leaving the reader to work out that this means two copies of one block, now has no second line to explain. The fixtures had the defect written down: `e2e/cases/init-conversation-link-claude/expected.repo` carried `CLAUDE.md` and `.claude/CLAUDE.md` as two byte-identical golden files, asserted as correct output. Landing it moved three boundaries that were already named as missing ([§AR-core-module-layout.1](architecture/AR-core-module-layout.md#1-module-categories)): entrypoint *selection* — which files a repository has and which a run touches — left `init_templates.rs` for `init_entrypoints.rs`, the managed-block machinery left `init.rs` for `init_block.rs` (the extraction half of that file's recorded debt, whose remaining half is the second implementation of the same protocol in `integrations.rs`), the `note:` builders left for `init_notes.rs`, and the entrypoint-selection test cases left `tests/init.rs` for `tests/init_agent_entrypoints.rs` over a shared fixture — which is the whole of *that* file's recorded debt, so its hard-severity exception is retired. `grund check`'s companion scan is now derived from `init`'s existing-entrypoint set rather than restating the same walk, so the two cannot disagree about what an entrypoint is. Resolves issue #87. PR #92

- [§FS-fmt.2.4.1](functional-spec/FS-fmt.md#241-a-shorthand-in-a-numeric-run-is-not-rewritten) / [§FS-check.3.15](functional-spec/FS-check.md#315-shorthand-citation-in-a-numeric-run) / [§FS-fmt.3](functional-spec/FS-fmt.md#3-outputs) / [§DF-shorthand-numeric-run](decisions/functional/DF-shorthand-numeric-run.md#df-shorthand-numeric-run-a-marked-shorthand-glued-to-another-number-is-a-numeral-not-a-citation): **`grund fmt --write` no longer expands a number-only shorthand that is glued to a second number**, and says so instead of rewriting it. A changelog recording an ID remapping writes the old numbers as runs — `<§>SPEC-001→SPEC-003`, `<§>SPEC-001/003`, `<§>COMP-047/046/049`. Every character after the first number is one that cannot continue an ID, so the trailing-boundary rule of [§DF-number-only-citation-shorthand.2.6](decisions/functional/DF-number-only-citation-shorthand.md#26-the-full-id-always-wins-and-only-a-whole-token-is-a-shorthand) passed and today's slug was attached to a number that named something else, turning a renumbering table into a set of pointers at live, unrelated declarations. **The rewrite was silent and nothing downstream could see it**: the output is a well-formed citation of a real declaration, so `grund check` passed and the run reported success. That is the worst-shaped instance of the class [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) forbids — not a citation that resolves to nothing, but one that resolves to the *wrong thing* while reporting green — and it is only findable by a human reading the prose, which is how it was found, in a 5,750-line diff re-read after the fact. The rule the boundary test was missing is that a whole token is not always a citation: `§2.4` asked *does this token end here?*, which is a lexical question, and never asked *is this token being used as a citation?* The marker settles the first and cannot settle the second — a `§` in front of `SPEC-001→SPEC-003` says the sentence is about IDs, not which token in it is the reference — so the shorthand, which is precisely the ambiguous shape [§DF-number-only-citation-shorthand.2.4](decisions/functional/DF-number-only-citation-shorthand.md#24-the-marker-is-required-a-bare-shorthand-is-text) required the marker for, needs one more piece of evidence. **The evidence is the second number, not the punctuation.** A site is a numeric run when the characters after the token form a non-empty delimiter sequence carrying no whitespace, no marker, and no bracket or quote, followed by another `[id] number_pattern` match or another whole shorthand written **unqualified** — which derives `→`, `/`, `..`, `…`, `|`, `,` and everything else anyone writes between two numbers without enumerating a list that would be one defect short forever. The three exclusions are the safety margin: whitespace, because the gluing *is* the evidence and `<§>FS-042 (2024)` is an ordinary citation under the default `number_pattern = "\d+"`; the marker, because `<§>FS-042, <§>FS-043` is two citations the author marked one at a time; and brackets and quotes, because those bound a construct instead of gluing two numerals — a walk that crossed one would join the characters *closing* the construct the citation sits in to the ones *opening* the next and read the next construct’s number as the second one, making a run of the Markdown link `[<§>FS-042](FS-042-user-login.md)` that `fmt --cross-refs` itself writes and of the footnote reference `<§>FS-042[^1]`. Requiring the neighbour to be **unqualified** is the same guard from the other side: an `<alias>/` namespace precedes a citation and never follows one, so a path that happens to end in an ID-shaped segment — `docs/functional-spec/FS-042-user-login.md` — is not a second number. Both are shapes an ordinary citation wears, and refusing them would leave a `shorthand-numeric-run` error naming an edit `fmt` will never make. The rule reads forward only — a glued number-shaped token to the *left* is also what `2026-08-19/<§>FS-042` looks like, and refusing those would cost real citations for no evidence. The site is **reported, not skipped in silence**: a new `shorthand-numeric-run` error names both exits — the canonical form to paste if it was a citation, and the `<§>` escape if the numbers were a mapping — because only the author knows which. Nothing turns green-to-red: these sites are already errors today, and what changes is that the message stops advising the edit that corrupts the line. Recognition is untouched, so the site still resolves, still counts as an edge, still grounds its file, and its declaration is still not reported unused — dropping the edge would tidy the model and reintroduce the exact false negative the shorthand rule was added to end. Only the message that names the *rewrite* changes: a shorthand in a run matching zero or several declarations keeps its [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) message, because that is a resolution failure and a run is no reason to say less about it. The editor's live transform ([§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform)) applies the same rule, with one residue it cannot avoid: an author typing a fresh run has not written the second number yet when the keystroke that ends the token fires, so that expansion happens — visibly, one undo away, which is the loud failure and not the silent one. Independent of the rule, and the part that outlives it: **`grund fmt` now prints the text every expansion writes** — `docs/notes.md:1: shorthand → canonical: <§>FS-042 → <§>FS-042-user-login` — so a `--check` run is a review *before* `--write` puts it on disk. The other three rewrites leave the ID token byte-identical and only move markup around it, so a wrong one dangles or fails to resolve and `check` names it; expanding a shorthand is the one pass that writes characters *into* the ID, information the source never carried, and naming only the line and the rewrite class was enough to review the former and not the latter. `FmtChange.label` is therefore a `String` rather than one of four fixed labels — a documented, additive break in the library surface ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)). No `grund_config_version` bump, no `[id]` key, and no `AGENTS.md` block bump: the rule is derived from `[id] format` like the shorthand itself, and a knob would let two installs disagree about what a citation *is* ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). The numeric-run test lives with the `[id] format` template in `id_format.rs` rather than in `shorthand.rs` ([§AR-scanner.2.6](architecture/AR-scanner.md#26-number-only-shorthand-citations)) — where a token of the grammar ends is a question about the shape, and the test reads the shorthand patterns directly — and its cases are one module across all three stages, because the defect being guarded against is a rewrite and a report agreeing with each other and both being wrong. Resolves issue #81. PR #90

- [§FS-distribution.4](functional-spec/FS-distribution.md#4-release-process): **archiving a release no longer breaks the links it carries above `docs/`.** `scripts/prepare_changelog_release.py` moves the outgoing release body from `docs/changelog.md` into `docs/changelog/<version>.md`, one directory deeper, and rewrote each relative destination to match — except one already beginning `../`, which it skipped. Those are exactly the destinations that need a second `../`: a link to a repository-root path is written `../crates/…` against `docs/`, and from `docs/changelog/` it has to climb twice. v0.10.0 archived v0.9.1 and its two `§AR-checker` links to an inline source declaration became `docs/crates/…`, which turned the tree's own `lychee` gate — and so CI on `main` — red. The rule is now the file's depth rather than the link's shape, an anchor, an absolute path and a URL still mean the same thing at any depth, and the archived v0.9.1 links are corrected. PR #80

## 2. [0.10.0] — 2026-08-18

### Added

- [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces) / [§FS-workspace.1](functional-spec/FS-workspace.md#1-citation-syntax) / [§DF-nested-workspaces](decisions/functional/DF-nested-workspaces.md#df-nested-workspaces-a-nested-project-is-named-by-its-whole-alias-path): **a workspace member may declare its own `[workspace]`**, to any depth, and a project is named by its whole alias path — `<§>hardware/sprayer/FS-nozzle`, one segment per level, read from the outermost workspace down. Before this, a member carrying `[workspace]` was a load-time error, so a repository that groups sub-projects under a directory had to enumerate every leaf at the root and the grouping directory could not own its own member list; the hierarchy survived only in prose. The grammar is now `<§>[alias/…/alias/]<ID>[.section]` and the namespace is still one string, so nesting adds recursion at the expansion step and no second shape anywhere below it — an ID never contains `/`, so the last separator is the path/ID boundary for the scanner, the CLI argument, and `[citations]` rule entries alike. Paths, not globally unique names, are what let two `pod` projects under different parents coexist: alias uniqueness is now per sibling set, not per tree. An intermediate node is a project of its own unless its block sets `include_root = false` — otherwise its files would be scanned by nobody, since the outer scan stops at the member boundary — and opting out still leaves its segment in the paths below it. Alias paths do not change with scope for every scope *in* the *claimed chain* — each level's `[workspace]` block listing the directory below it — so a run narrowed to one of those blocks resolves a *subset* of the same paths, and a citation cannot pass such a check and fail the run CI does. The guarantee is quantified over the scope a command starts at, not over the project it names: the projects under a block the chain never lists can themselves be reached by the chain, since a multi-segment entry (`grp/inner`) hops the block, and a run started **at** that block re-spells them — the recorded limitation below, not a property of a chained scope. Every block in that chain has to answer, so one that claims a directory and cannot expand its members or name the project below it fails the run with its own error instead of dropping its segment and letting the subtree invent a namespace; a `[workspace]` block that no enclosing block lists is outside that chain, absorbed into the enclosing namespace at the outer scope and a root of its own from the inside, and reporting it is a recorded limitation rather than a check. A member that resolves to a project root *another* block already holds is a config error at the `members` line that introduced it — a backstop, since what bounds expansion is containment: a member root lands strictly inside the block that lists it and no member of one block contains another, so every step goes strictly downward into a finite tree and no two roots in it can be equal. Two entries in one `members` list naming the same root stay deduped, so a glob may overlap an explicit entry. A malformed namespace qualifier in a `[citations]` rule entry is now reported the way a malformed `<alias>/<ID>` command argument is — naming the segment that failed rather than quoting the whole path ([§FS-config.3.9.3](functional-spec/FS-config.md#393-namespace-matching)). `grund init`'s Workspace members section ([§FS-init.2.3.4.15](functional-spec/FS-init.md#23415-workspace-members)) follows the same claimed chain, so it lists the tree a command run at that directory resolves — a repository that merely sits *under* an unrelated `[workspace]` still teaches its own aliases. Single-level workspaces are unaffected — one level is one segment, which is what they already write. Resolves issue #47. PR #66
- [§FS-check.3.8](functional-spec/FS-check.md#38-cross-project-citation-failure): **an unknown project alias now names the projects it could have meant.** Whole alias paths make one mistake likely — writing a project's short leaf name where its path is required — so `check` matches the unresolved path against the projects in scope in one tier only, best first: a path that *ends with* what was written (a dropped prefix), else one whose last segment matches (a wrong prefix), else one a typo away under the near-match rule §3.1 already uses. Up to three are listed, and a path with no candidate reports exactly as it did. `unknown project alias sprayer` becomes `unknown project alias sprayer; did you mean hardware/sprayer?`, which is what makes migrating a flat leaf list to a nested tree mechanical instead of a search. This reaches **single-level** workspaces too, with no config change: a typo'd alias that reported bare now carries the suffix (`unknown project alias ap; did you mean api?`) from the typo tier. Message text is part of the user-visible contract ([§FS-errors.3](functional-spec/FS-errors.md#3-message-text), [§GOAL-no-silent-breakage.1](goals.md#1-what-counts-as-user-visible)), so it is named here as intended: everything up to the `;` is byte-identical, so a consumer matching the phrase or its prefix still matches. A run **narrowed** to a subtree offers no candidate at all and says which subtree it covers instead: it cannot tell a dropped prefix from a path that correctly names a project outside its scope — a *shorter* written path is a complete alias path whenever a top-level project carries that name — so any hint it could give risks rewriting a citation the workspace-root run accepts into a different project's, green before and green after. The tiers run at the outermost root, which is the scope CI runs and the only one that can see every project a path could name. PR #66
- [§FS-inline-citation-style.3.3](functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit) / [§FS-inline-citation-style.4.4](functional-spec/FS-inline-citation-style.md#44-warnings-and-errors--opt-in-layout-deviations) / [§DF-inline-note-layout](decisions/functional/DF-inline-note-layout.md#df-inline-note-layout-inline-note-layout-is-a-configured-house-style-checked-per-line-and-never-normalized): add **`[reference] inline_note_layout`**, the third axis of an inline citation's shape — *where* the `§<ID>` tokens sit inside the note — and **`inline_note_layout_check`**, which says whether `grund check` reports a deviation and through which channel. `inline_style = "citation-with-note"` already said whether prose is allowed and how much of it; it said nothing about arrangement, so `// <§>FS-x: note`, `// note. <§>FS-x`, and `// <§>FS-x note` all passed and a project that wanted exactly one of them had nowhere to say so. The cost is not tidiness. It is that the convention became repository prose: the generated entrypoint taught the budget and then left the agent to *infer* the arrangement from the surrounding files ([§FS-init.2.3](functional-spec/FS-init.md#23-generated-agent-entrypoints)) — the guessing [§GOAL-friendliness-first](goals.md#goal-friendliness-first-as-user--and-agent-friendly-as-possible) exists to remove. And one arrangement in particular is worth being able to demand: under `[reference] strict = false` a bare `// FS-x: note` line *is* an inline declaration heading, so writing the marker and the colon is what makes "cites `FS-x`" and "declares `FS-x`" two visibly different lines instead of one shape read two ways. `inline_note_layout = "citation-first-colon"` requires a run of citations joined by exactly `, `, then a colon, then a space and the note — or a colon that ends the line — read on the content left after the comment prefix and any block closer are stripped, exactly as the note-presence rule already reads it. A leading Markdown list marker is skipped with that indentation, so the enumerated block of grounded points every doc-comment convention renders as a list — `/// - §<ID>: note` — opens with its run like any other line; the marker stays note text where §2.3 decides whether the site carries a note at all, so no bulleted pointer is silently reclassified. The rule is judged **per line, not per site**: a line carrying no citation is unconstrained, so the summary-then-citation doc-comment that Rustdoc, Javadoc, and JSDoc all encourage stays legal, and the finding lands on the line an author has to edit rather than on the block's opener — the one member of the `inline-citation-style` rule that does not anchor at `first_line`. Per line is not *every* line: the site's first citation-bearing line opens the note and is always judged, a later one is judged when it opens with a citation of its own, and a citation-bearing line that opens with prose is the continuation of a note that already opened correctly. So a note may wrap and still name a second point on the way, which is exactly the freedom the line budget and the same-line rule already granted and which judging every such line quietly took back. A site with **no note at all** is exempt, because a layout is a relation between a citation and a note and `// §A  §B` is a pure pointer; the deliberate consequence is that a `// §A` line followed by a prose line *in the same block* is one site with a note, so the citation line is judged and fails. The form is **exact** — a space where the comma belongs, a comma with no space, a space before the colon, a dash for the colon — because a tolerant matcher would leave the project with the variation the key exists to remove while still leaving an agent to guess which tolerated spelling the humans write. Citations *later* on the line are free, so `// §A: note (see also §B)` conforms; only the opening run is constrained. Two keys rather than one, because a project answers "which style?" and "gate on it yet?" at different times: adopt the style so the entrypoint starts teaching it, migrate the tree with `warn` as the worklist, then move to `error`. That is a per-rule *channel* choice with existing precedent — `warn_on_suggested` does it for the soft cap, `[citations]` `must`/`should` does it per obligation — and not configurable severity: what an error and a warning *mean*, and how the exit code follows, stay fixed by [§FS-non-goals.9](functional-spec/FS-non-goals.md#9-severity-exit-code-or-report-ordering-customization), and both installs read the level from the same committed `grund.toml` ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). Both keys default to the inert value, so **nothing turns red on upgrade** ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)): no `grund_config_version` bump, and no `AGENTS.md` block bump either — under `any` the rendered block is byte-for-byte what the previous release produced, so no repository's managed block goes stale for a rule that changes nothing about what it should write. Under `citation-first-colon` the block gains one sentence naming the form with the project's own marker — deliberately wider than the gate, since a doc-comment that declares an ID is not a citation site and its body is therefore taught the form and never measured against it ([§FS-inline-citation-style.3.3](functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit), rule 6) — and the *enforcement level* deliberately does not change it: the house style is what an agent is asked to write, and an agent told the form and then told it is only advisory has been handed a reason to ignore it. The half of the report that is **declined** is `grund fmt` normalization, in `--check` and in `--write` alike ([§DF-inline-note-layout.2.5](decisions/functional/DF-inline-note-layout.md#25-check-only-grund-fmt-is-not-involved)). Turning `// note (§A).` into `// §A: note.` is a prose edit wearing a token edit's clothes — it needs to decide where the sentence ends, whether the trailing parenthetical was the citation, and what punctuation the remainder now needs, which is the judgment [§FS-non-goals.3](functional-spec/FS-non-goals.md#3-code-ast-parsing) refuses to acquire; a formatter that is right most of the time fails here as a silently mangled comment in a commit nobody read line by line. What the report actually needs is served without it: the fix is one token in the loop of whoever is already editing the line, and migrating an existing tree is what `warn` is for. `grund config show` prints both keys at every value, inert or not, and `templates/grund.toml` carries both with their accepted-value comments so the generated config still teaches the whole schema ([§FS-config.3.1](functional-spec/FS-config.md#31-reference--citation-form), [§FS-check.3.10](functional-spec/FS-check.md#310-inline-citation-style-violation), [§FS-check.4.4](functional-spec/FS-check.md#44-inline-note-layout-deviation-opt-in)). The enum is closed and ships one member on purpose: `citation-first-dash`, a bare `citation-first`, a bracketed form, `note-first-parenthesized`, and citations on a line of their own were all considered and all left out until something asks for them, since each costs its own spec examples, its own rendered sentence, and its own coverage, while adding one later is additive; a free-form `"{cites}: {note}"` template is rejected outright for now, because a template is a small language — parser, inverse matcher, escaping, validation — and there is no way to render one canonical sentence into an entrypoint from a form the tool was handed rather than one it knows. Implementation-wise the rule is one file, `crates/grund-core/src/inline_note_layout.rs`, over a second holding what is not the rule — `comment_line.rs`, where reducing one line to its content and its citation tokens now lives for the scanner walk and both note verdicts alike ([§AR-scanner.3](architecture/AR-scanner.md#3-output), [§AR-checker.2.14](../crates/grund-core/src/checker.rs)): the scanner records, per inline citation site, the ascending list of its lines that deviate, and the checker reads that list instead of re-opening the file, so the rule stays a pure pass over `Findings`. Under `any`, and under a layout whose check is `off`, no line is classified at all, which is why neither the default path nor a documented-only style tokenizes or classifies a line on the key's account ([§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)); the memo that lets the two verdicts share one tokenization is built only where a second reader exists, so the default path allocates none of it and pays one comparison per site. It comes out ahead on the way: the comment-prefix list every note walk reads is now built once per comment block rather than once per line, which it was before this key existed. Gathering the classifier, the note-presence helpers it shares, and the checker rule in that one file — the arrangement `shorthand.rs` already uses, for the same reason: four halves of one invariant in four files with nothing naming the invariant is how the halves drift — took `scanner.rs` from 1523 to 1383 lines — the citation tokenizer left with the helpers that are now its only callers, which is most of that file's standing `until` clause — and `checker.rs` from 1083 to 1013, and every file-size ceiling drops to what the files now measure; sharing them is literal and lazy, since a line of a site is tokenized once, when the first pass that needs it asks, and the note-presence verdict and the layout verdicts read that one answer — so a block the note walk leaves early, and every block under a configuration that classifies nothing, is read no further than its answer needs. One reading changes for every project, not only for one that sets the key: what separates two citation tokens of a chain — whitespace, or a single comma with optional whitespace — is no longer note text ([§FS-inline-citation-style.1](functional-spec/FS-inline-citation-style.md#1-scope)), so `// <§>FS-a, <§>FS-b` is a pure citation comment. It has to be: that is the spelling the layout mandates in front of a colon, and it was previously read as prose — rejected outright under `inline_style = "citation-only"`, and reported as a layout deviation under the new key for lacking the note it does not have. Resolves issue #52. PR #65
