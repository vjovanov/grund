# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

## Unreleased

### Added

- [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces) / [§FS-workspace.1](functional-spec/FS-workspace.md#1-citation-syntax) / [§DF-nested-workspaces](decisions/functional/DF-nested-workspaces.md#df-nested-workspaces-a-nested-project-is-named-by-its-whole-alias-path): **a workspace member may declare its own `[workspace]`**, to any depth, and a project is named by its whole alias path — `<§>hardware/sprayer/FS-nozzle`, one segment per level, read from the outermost workspace down. Before this, a member carrying `[workspace]` was a load-time error, so a repository that groups sub-projects under a directory had to enumerate every leaf at the root and the grouping directory could not own its own member list; the hierarchy survived only in prose. The grammar is now `<§>[alias/…/alias/]<ID>[.section]` and the namespace is still one string, so nesting adds recursion at the expansion step and no second shape anywhere below it — an ID never contains `/`, so the last separator is the path/ID boundary for the scanner, the CLI argument, and `[citations]` rule entries alike. Paths, not globally unique names, are what let two `pod` projects under different parents coexist: alias uniqueness is now per sibling set, not per tree. An intermediate node is a project of its own unless its block sets `include_root = false` — otherwise its files would be scanned by nobody, since the outer scan stops at the member boundary — and opting out still leaves its segment in the paths below it. Alias paths do not change with scope for every scope *in* the *claimed chain* — each level's `[workspace]` block listing the directory below it — so a run narrowed to one of those blocks resolves a *subset* of the same paths, and a citation cannot pass such a check and fail the run CI does. The guarantee is quantified over the scope a command starts at, not over the project it names: the projects under a block the chain never lists can themselves be reached by the chain, since a multi-segment entry (`grp/inner`) hops the block, and a run started **at** that block re-spells them — the recorded limitation below, not a property of a chained scope. Every block in that chain has to answer, so one that claims a directory and cannot expand its members or name the project below it fails the run with its own error instead of dropping its segment and letting the subtree invent a namespace; a `[workspace]` block that no enclosing block lists is outside that chain, absorbed into the enclosing namespace at the outer scope and a root of its own from the inside, and reporting it is a recorded limitation rather than a check. A member that resolves to a project root *another* block already holds is a config error at the `members` line that introduced it, which is also what bounds expansion; two entries in one `members` list naming the same root stay deduped, so a glob may overlap an explicit entry. `grund init`'s Workspace members section ([§FS-init.2.3.4.15](functional-spec/FS-init.md#23415-workspace-members)) follows the same claimed chain, so it lists the tree a command run at that directory resolves — a repository that merely sits *under* an unrelated `[workspace]` still teaches its own aliases. Single-level workspaces are unaffected — one level is one segment, which is what they already write. Resolves issue #47. PR #66
- [§FS-check.3.8](functional-spec/FS-check.md#38-cross-project-citation-failure): **an unknown project alias now names the projects it could have meant.** Whole alias paths make one mistake likely — writing a project's short leaf name where its path is required — so `check` matches the unresolved path against the projects in scope in one tier only, best first: a path that *ends with* what was written (a dropped prefix), else one whose last segment matches (a wrong prefix), else one a typo away under the near-match rule §3.1 already uses. Up to three are listed, and a path with no candidate reports exactly as it did. `unknown project alias sprayer` becomes `unknown project alias sprayer; did you mean hardware/sprayer?`, which is what makes migrating a flat leaf list to a nested tree mechanical instead of a search. A run **narrowed** to a subtree offers no candidate at all and says which subtree it covers instead: it cannot tell a dropped prefix from a path that correctly names a project outside its scope — a *shorter* written path is a complete alias path whenever a top-level project carries that name — so any hint it could give risks rewriting a citation the workspace-root run accepts into a different project's, green before and green after. The tiers run at the outermost root, which is the scope CI runs and the only one that can see every project a path could name. PR #66
- [§FS-inline-citation-style.3.3](functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit) / [§FS-inline-citation-style.4.4](functional-spec/FS-inline-citation-style.md#44-warnings-and-errors--opt-in-layout-deviations) / [§DF-inline-note-layout](decisions/functional/DF-inline-note-layout.md#df-inline-note-layout-inline-note-layout-is-a-configured-house-style-checked-per-line-and-never-normalized): add **`[reference] inline_note_layout`**, the third axis of an inline citation's shape — *where* the `§<ID>` tokens sit inside the note — and **`inline_note_layout_check`**, which says whether `grund check` reports a deviation and through which channel. `inline_style = "citation-with-note"` already said whether prose is allowed and how much of it; it said nothing about arrangement, so `// <§>FS-x: note`, `// note. <§>FS-x`, and `// <§>FS-x note` all passed and a project that wanted exactly one of them had nowhere to say so. The cost is not tidiness. It is that the convention became repository prose: the generated entrypoint taught the budget and then left the agent to *infer* the arrangement from the surrounding files ([§FS-init.2.3](functional-spec/FS-init.md#23-generated-agent-entrypoints)) — the guessing [§GOAL-friendliness-first](goals.md#goal-friendliness-first-as-user--and-agent-friendly-as-possible) exists to remove. And one arrangement in particular is worth being able to demand: under `[reference] strict = false` a bare `// FS-x: note` line *is* an inline declaration heading, so writing the marker and the colon is what makes "cites `FS-x`" and "declares `FS-x`" two visibly different lines instead of one shape read two ways. `inline_note_layout = "citation-first-colon"` requires a run of citations joined by exactly `, `, then a colon, then a space and the note — or a colon that ends the line — read on the content left after the comment prefix and any block closer are stripped, exactly as the note-presence rule already reads it. A leading Markdown list marker is skipped with that indentation, so the enumerated block of grounded points every doc-comment convention renders as a list — `/// - §<ID>: note` — opens with its run like any other line; the marker stays note text where §2.3 decides whether the site carries a note at all, so no bulleted pointer is silently reclassified. The rule is judged **per line, not per site**: a line carrying no citation is unconstrained, so the summary-then-citation doc-comment that Rustdoc, Javadoc, and JSDoc all encourage stays legal, and the finding lands on the line an author has to edit rather than on the block's opener — the one member of the `inline-citation-style` rule that does not anchor at `first_line`. Per line is not *every* line: the site's first citation-bearing line opens the note and is always judged, a later one is judged when it opens with a citation of its own, and a citation-bearing line that opens with prose is the continuation of a note that already opened correctly. So a note may wrap and still name a second point on the way, which is exactly the freedom the line budget and the same-line rule already granted and which judging every such line quietly took back. A site with **no note at all** is exempt, because a layout is a relation between a citation and a note and `// §A  §B` is a pure pointer; the deliberate consequence is that a `// §A` line followed by a prose line *in the same block* is one site with a note, so the citation line is judged and fails. The form is **exact** — a space where the comma belongs, a comma with no space, a space before the colon, a dash for the colon — because a tolerant matcher would leave the project with the variation the key exists to remove while still leaving an agent to guess which tolerated spelling the humans write. Citations *later* on the line are free, so `// §A: note (see also §B)` conforms; only the opening run is constrained. Two keys rather than one, because a project answers "which style?" and "gate on it yet?" at different times: adopt the style so the entrypoint starts teaching it, migrate the tree with `warn` as the worklist, then move to `error`. That is a per-rule *channel* choice with existing precedent — `warn_on_suggested` does it for the soft cap, `[citations]` `must`/`should` does it per obligation — and not configurable severity: what an error and a warning *mean*, and how the exit code follows, stay fixed by [§FS-non-goals.9](functional-spec/FS-non-goals.md#9-severity-exit-code-or-report-ordering-customization), and both installs read the level from the same committed `grund.toml` ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). Both keys default to the inert value, so **nothing turns red on upgrade** ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)): no `grund_config_version` bump, and no `AGENTS.md` block bump either — under `any` the rendered block is byte-for-byte what the previous release produced, so no repository's managed block goes stale for a rule that changes nothing about what it should write. Under `citation-first-colon` the block gains one sentence naming the form with the project's own marker — deliberately wider than the gate, since a doc-comment that declares an ID is not a citation site and its body is therefore taught the form and never measured against it ([§FS-inline-citation-style.3.3](functional-spec/FS-inline-citation-style.md#33-inline_note_layout--where-the-citations-sit), rule 6) — and the *enforcement level* deliberately does not change it: the house style is what an agent is asked to write, and an agent told the form and then told it is only advisory has been handed a reason to ignore it. The half of the report that is **declined** is `grund fmt` normalization, in `--check` and in `--write` alike ([§DF-inline-note-layout.2.5](decisions/functional/DF-inline-note-layout.md#25-check-only-grund-fmt-is-not-involved)). Turning `// note (§A).` into `// §A: note.` is a prose edit wearing a token edit's clothes — it needs to decide where the sentence ends, whether the trailing parenthetical was the citation, and what punctuation the remainder now needs, which is the judgment [§FS-non-goals.3](functional-spec/FS-non-goals.md#3-code-ast-parsing) refuses to acquire; a formatter that is right most of the time fails here as a silently mangled comment in a commit nobody read line by line. What the report actually needs is served without it: the fix is one token in the loop of whoever is already editing the line, and migrating an existing tree is what `warn` is for. `grund config show` prints both keys at every value, inert or not, and `templates/grund.toml` carries both with their accepted-value comments so the generated config still teaches the whole schema ([§FS-config.3.1](functional-spec/FS-config.md#31-reference--citation-form), [§FS-check.3.10](functional-spec/FS-check.md#310-inline-citation-style-violation), [§FS-check.4.4](functional-spec/FS-check.md#44-inline-note-layout-deviation-opt-in)). The enum is closed and ships one member on purpose: `citation-first-dash`, a bare `citation-first`, a bracketed form, `note-first-parenthesized`, and citations on a line of their own were all considered and all left out until something asks for them, since each costs its own spec examples, its own rendered sentence, and its own coverage, while adding one later is additive; a free-form `"{cites}: {note}"` template is rejected outright for now, because a template is a small language — parser, inverse matcher, escaping, validation — and there is no way to render one canonical sentence into an entrypoint from a form the tool was handed rather than one it knows. Implementation-wise the rule is one file, `crates/grund-core/src/inline_note_layout.rs`, over a second holding what is not the rule — `comment_line.rs`, where reducing one line to its content and its citation tokens now lives for the scanner walk and both note verdicts alike ([§AR-scanner.3](architecture/AR-scanner.md#3-output), [§AR-checker.2.14](../crates/grund-core/src/checker.rs)): the scanner records, per inline citation site, the ascending list of its lines that deviate, and the checker reads that list instead of re-opening the file, so the rule stays a pure pass over `Findings`. Under `any`, and under a layout whose check is `off`, no line is classified at all, which is why neither the default path nor a documented-only style tokenizes or classifies a line on the key's account ([§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)); the memo that lets the two verdicts share one tokenization is built only where a second reader exists, so the default path allocates none of it and pays one comparison per site. It comes out ahead on the way: the comment-prefix list every note walk reads is now built once per comment block rather than once per line, which it was before this key existed. Gathering the classifier, the note-presence helpers it shares, and the checker rule in that one file — the arrangement `shorthand.rs` already uses, for the same reason: four halves of one invariant in four files with nothing naming the invariant is how the halves drift — took `scanner.rs` from 1523 to 1383 lines — the citation tokenizer left with the helpers that are now its only callers, which is most of that file's standing `until` clause — and `checker.rs` from 1083 to 1013, and every file-size ceiling drops to what the files now measure; sharing them is literal and lazy, since a line of a site is tokenized once, when the first pass that needs it asks, and the note-presence verdict and the layout verdicts read that one answer — so a block the note walk leaves early, and every block under a configuration that classifies nothing, is read no further than its answer needs. One reading changes for every project, not only for one that sets the key: what separates two citation tokens of a chain — whitespace, or a single comma with optional whitespace — is no longer note text ([§FS-inline-citation-style.1](functional-spec/FS-inline-citation-style.md#1-scope)), so `// <§>FS-a, <§>FS-b` is a pure citation comment. It has to be: that is the spelling the layout mandates in front of a colon, and it was previously read as prose — rejected outright under `inline_style = "citation-only"`, and reported as a layout deviation under the new key for lacking the note it does not have. Resolves issue #52. PR #65

### Changed

- [§FS-workspace.2](functional-spec/FS-workspace.md#2-workspace-configuration) / [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces): **a `[workspace]` member must resolve to a directory strictly inside the config root that lists it** — not that root, not an ancestor of it, not another tree — and one that does not is now a config error at that block's `members` line, naming the entry as written. Member entries already reject `..`, so escaping takes a symlink, and `canonicalize` used to accept wherever it pointed. Two failures made that unfixable from anywhere else: a member root with no lexical ancestor listing it is named from a different chain at each scope, so `grund check` at the root demanded `real/leaf` where a run at the member demanded `leaf` and no citation text passed both; and a member root that is an *ancestor* of its own block scans nothing at all, because every scan root then lies under that project's own member boundary — its declarations vanish from `grund list` and its dangling citations pass, a [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) hole opened by a symlink. **Migration:** a workspace that joined an external directory by symlink (`members = ["link"]` with `link -> ../other-repo`) stops loading — move or nest the project, or check it as its own repository, since external-repository aliases are out of contract until a cache layer exists ([§DF-subproject-namespaces](decisions/functional/DF-subproject-namespaces.md#df-subproject-namespaces-alias-namespace-model-for-sub-projects-and-external-repos) §3.4). PR #66
- [§FS-config.3.2](functional-spec/FS-config.md#32-id--id-grammar) / [§FS-workspace.1](functional-spec/FS-workspace.md#1-citation-syntax): **no ID the grammar can build may contain a `/`** — a literal `/` in `[id] format` or in a `[[kinds]]` prefix, or an `[id] number_pattern` / `[id] slug_pattern` that can *match* one, is now a config error at that key's line. For the two patterns the question is what they match, not what they spell: `slug_pattern = "[^.[:space:]]+"` carries no `/` and produces one freely, so it is rejected, while `"[^/.]+"` names the character in order to exclude it and loads. `slug_pattern = "[a-z][a-z0-9/-]*"` used to load, declare `FS-a/b`, and check clean, while `grund m/FS-a/b` split the token on its last `/` and read `m/FS-a` as the alias path — grund emitted an ID it then refused as a query, and the alias boundary landed inside it. The nested-workspace naming rules rest on "an ID never contains `/`" and nothing enforced it. A repository that really did spell IDs with a `/` must rename them before it can load. PR #66
- [§AR-ci.9](architecture/AR-ci.md#9-file-size-budget-gate): **markdown now carries two file-size budgets instead of one.** The citable tree under `docs/` goes to soft 750 / hard 1500, because `grund` decides who pays for a document's length: a spec is reached by citation and read as a lead, a section, or a table of contents ([§FS-show](functional-spec/FS-show.md#fs-show-grund-reads-a-single-declaration-body-by-id)), so [§GOAL-token-economy](goals.md#goal-token-economy-give-an-agent-the-right-amount-of-spec-not-the-whole-file) is answered at the read rather than at the file and a ceiling in the hundreds of lines bought a reader nothing. It did have a price — a document whose numbered sections are live citation targets cannot be split without relocating those IDs and sweeping every citing site in the same change, so the budget kept collecting deferred exceptions instead of splits, and three of them retire here (the soft entries for `FS-workspace.md` and `AR-workspace.md`, and both halves of the `clickable-citations.md` pair). The always-read-whole entrypoints — `README.md`, `CLAUDE.md`, `AGENTS.md`, `skills/**/*.md` — move to a rule of their own at the previous numbers, because nothing addresses them by citation: an agent entrypoint is loaded into every session's context, so there every line *is* charged to every read. `skills/grund-init/SKILL.md` keeps its structural entry, repointed at the rule that now measures it. ## 2. [0.9.1] — 2026-08-17

### Added

- [§FS-lsp.1.2](functional-spec/FS-lsp.md#12-hover-preview): the **declaration-side title hover now answers "who leans on this?"** — hovering a Markdown declaration heading, the same declaration written inline in a doc-comment, a numbered section heading, or an inline-spec stub title returns `` `FS-check: …` — cited at 12 sites across 5 files `` where it used to return the bare title token. That hover existed as an editor affordance and little else: a title hover has to return *something* for Codium and its relatives to give the whole title a hover range, and what it returned was the text the cursor was already resting on — a popup whose entire content was legible behind it. The fact that is genuinely missing from that screen is the usage, and reading it meant leaving the editor for `grund refs <ID>` ([§FS-refs](functional-spec/FS-refs.md#fs-refs-grund-lists-every-citation-of-an-id)), which is the lookup an agent or a contributor runs before changing or deleting a declaration — precisely when the editor is open on the declaration. The numbers are that query's, not a second tally kept beside it: on a whole-ID title the counted set is by definition the set `grund refs` reports from the root the server was started at, citations inside scanned source comments included and `[reference] strict` honoured — in a workspace that is `grund refs <alias>/<ID>` run from the workspace root, counting a member's own `§<ID>` and a sibling's `§<alias>/<ID>` alike ([§FS-workspace.8.2](functional-spec/FS-workspace.md#82-grund-refs)) — held by a test that runs the query over the same tree and compares, rather than by the claim. They are counted off the session snapshot the server already maintains, never a fresh query: `refs` loads its own workspace context, so calling it per hover would re-walk the tree on a request the editor fires as the cursor moves ([§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible), [§AR-lsp.5](architecture/AR-lsp.md#5-determinism-and-parity-tests)). On a numbered section heading the count is the section subtree — `§<ID>.<section>` and deeper — which is the set that heading's own references and definition already return ([§FS-lsp.1.3.1](functional-spec/FS-lsp.md#131-references-from-declarations)), and deliberately wider than `grund refs <ID> --section <s>`, whose filter keeps only citations whose coordinate is *exactly* `<s>` ([§FS-refs.1](functional-spec/FS-refs.md#1-inputs)). Where the two readings conflict, the one that keeps a title's hover and its reference list in agreement wins: those are one gesture apart in the same editor, while the terminal comparison is one a reader has to go looking for. The wording is fixed rather than clever — only the two nouns inflect, `across` is the preposition at every count, and zero reads `not cited` instead of `cited at 0 sites across 0 files`, a sentence pretending to be a count. The token inside the code span is the title as the document writes it, section headings included (`1. Detail`, not a composed `FS-….1: Detail`), and a title that carries backticks of its own — plenty of headings name a flag — is fenced with a run one longer than the longest run inside it rather than backslash-escaped, which does nothing inside a code span. Zero is not suppressed in favour of the unused-declaration warning ([§FS-check.4.1](functional-spec/FS-check.md#41-unused-declaration)) either: that warning never fires on `E2E` declarations or on section headings, so a hover that fell silent at zero would go quiet exactly where nothing else speaks — and `not cited` stays a count in the hover's own words, so an editor that renders diagnostics inside the hover popup still shows the warning once and only once ([§FS-lsp.1.1](functional-spec/FS-lsp.md#11-diagnostics)). One matcher in `grund-core` now decides which citations belong to a declaration-side title, so the hover count, `textDocument/references`, definition-as-usages, and occurrence highlight cannot drift apart, and the body bytes are formed in the engine rather than in the transport, so a second frontend cannot re-word them ([§FS-lsp.4](functional-spec/FS-lsp.md#4-determinism-and-parity-with-the-cli)). The LSP suite's stdio harness moved to shared test support on the way, which is what let the hover cases land as a suite named for the request they drive. Resolves issue #51. PR #63

- [§FS-check.1.3](functional-spec/FS-check.md#13-the-full-tree-scope---full) / [§FS-check.3.14](functional-spec/FS-check.md#314-out-of-scope-unresolvable-citation---full-only) / [§DF-check-full-scope](decisions/functional/DF-check-full-scope.md#df-check-full-scope-check---full-walks-past-scan-include-and-reports-only-unresolvable-references-out-there): add **`grund check --full`**, which walks the whole config root past `[scan] include` and reports the references that resolve to nothing out there. `include` names the roots the walk starts from, so a citation outside it was not merely unchecked — it was *invisible*: it did not resolve, it did not dangle, it appeared in no report, and the declaration it pointed at was reported `declared but never cited` as if nothing referred to it. `check` printed `success`, which means "clean *within* `include`" and reads as "clean". That is the false negative [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) calls a bug, and the worst-shaped one available: `include` is written once, early; code then moves into `sim/`, `render/`, `lib/`, and nothing ever says that half the repository's citations stopped being read — the citations that most need checking are exactly the ones somebody forgot to bring into scope. Widening `include` is the durable fix, but nobody widens a config toward a problem they cannot see, and pointing `check` at each candidate directory by hand is a search, not a check. The reported case found three genuine defects behind that gap: a citation a formatter had wrapped across a line break, a cited section that did not exist, and a citation missing its workspace namespace, so it resolved against the wrong project. The flag **cancels `include` and nothing else**. `[scan] exclude`, `.gitignore` and every other ignore file, hidden directories, workspace member boundaries, and `[scan] extensions` apply to the wider walk unchanged; an explicit `PATH` argument still narrows, because `--full` cancels a config key, never a scope the caller typed — a path that *resolves to the config root* (`grund check .`, `grund check ./`, `grund check <abs-root>`) is the root scope and does widen, while any other path leaves the flag nothing to cancel and earns one CLI-level `warning:` on stderr saying so, rather than being accepted in silence. Which file *types* carry citations is a project fact that belongs in the config; which *directories* were forgotten is the accident this flag exists to expose, and one flag that widened both would leave "what did this run read?" underivable from the config. Out there, **only reference resolution is judged**: unknown ID, missing section, unknown namespace alias, and a shorthand matching zero or several declarations — never style, grounding, placement, direction, duplicate, or unused. That line is not cheap-versus-expensive, it is *what the repository agreed to*: "this citation points at nothing" is true of any tree under any convention, while "this inline note is over budget" is true only of a tree that adopted that convention, and `[scan] include` is where a project says which files it adopted it for. The reported case is the argument in numbers — scanning one unconfigured directory produced 160 findings, of which 3 were real, the other 157 being inline-note budget violations on module docstrings that had never been written to that convention. A mode that fails CI on conventions a directory never adopted is a mode nobody runs twice. The one finding withheld on its own terms is the mechanical shorthand rewrite ([§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation)): its named fix is `grund fmt --write`, and `fmt` scopes by `include` too, so out there it would name a fix the formatter declines to apply. Out-of-scope findings are **errors** and move the exit code to `1`. A warning would leave the mode exit-code-neutral, and a finding no CI run can fail on is one a repository accumulates behind forever — the argument [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) already makes. Nothing turns red without being asked: the flag is opt-in and no existing invocation changes behaviour ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)). It is also **purely additive** — the findings inside the configured scope are exactly the ones `grund check` reports on the same tree, so `--full` can only turn a green run red, never the reverse, and a team can add it beside the ordinary check without re-auditing the verdict they already trusted. That is why the wider walk does *not* feed the in-scope rules: an inline declaration living outside `include` would otherwise make an in-scope citation resolve under `--full` and dangle without it, reported green by the mode meant to find *more*. The additive property has a mechanical precondition that is easy to get wrong: `.gitignore`, `[scan] exclude`, and the hidden-directory rule prune *descendants* and never the directory a walk starts at, so the wider walk starts at the config root **and** at every `include` root and reads each file once — starting at the root alone would lose a gitignored, excluded, or hidden `include` root that the ordinary run reads as a root of its own, and `--full` would read *fewer* files than `grund check`. One thing the flag deliberately does **not** change: an in-scope declaration cited only from outside `include` keeps its `declared but never cited` warning ([§FS-check.4.1](functional-spec/FS-check.md#41-unused-declaration)), because counting the wider walk's citations toward it would *retire* an in-scope finding — the one direction additivity forbids — and the remedy the tier already names is to widen `include`. The wider walk can also fail wider: a file it reaches that cannot be read or decoded is the ordinary scan failure, so a tree whose plain `check` exits `0` can exit `2` under `--full`. In a workspace the flag applies per project — root and every member widens past its own `include`, because `include` is a per-project statement; with `[workspace] include_root = false` there is no root project to widen, so files at the workspace root outside every member stay unread either way. It is a flag and **never a `grund.toml` key** ([§FS-config.3.5](functional-spec/FS-config.md#35-scan--what-gets-walked)): a project that wants its whole tree governed widens `include` and gets the whole rule set, and a key that made `--full` the default would be a second, weaker `include` — two knobs describing one scope, which is how two correctly-configured installs come to disagree ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). No `grund_config_version` bump and no `AGENTS.md` block bump. Four new diagnostic codes carry the tier — `out-of-scope-dangling`, `out-of-scope-missing-section`, `out-of-scope-unknown-project`, `out-of-scope-shorthand-citation`, each the in-scope rule's code under an `out-of-scope-` prefix — so `--format=json` filters the tier by prefix and the rule by exact match on the `code` field the shape already has, and no consumer learns a new field ([§FS-errors.5](functional-spec/FS-errors.md#5-json-format)). In text the tier leads the message (`sim/world.py:1: outside [scan] include: unknown reference FS-999-missing`) rather than trailing it, because out there the fix is usually to widen the key and a rule's own `did you mean …?` hint is the part most likely to be wrong. `CheckOpts` gains `full: bool`, and the `Config` the crate hands an embedder gains `scan_full: bool` (the same flag, after the CLI has resolved it, so a caller building a `Config` directly can widen the walk too) — two documented, additive breaks in the library surface, like `include_suggestions` before it ([§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate)). The second half of the report — grepping ID-shaped tokens out of string literals and unscanned file types as an advisory tier — is **declined**, with the reasons recorded in [§DF-check-full-scope.2.6](decisions/functional/DF-check-full-scope.md#26-id-shaped-tokens-used-as-data-are-not-reported). Both real cases already have a deterministic answer: a marker-prefixed citation is recognized *everywhere*, string literal or not, so writing the marker on the token in the data table makes it checked today; and a file type is scanned by adding its extension to `[scan] extensions`. Reporting *unmarked* tokens instead would re-admit the false-positive class `strict = true` exists to end, contradict a rule the specs state outright — a bare ID-shaped token inside a string literal is not a citation — and need exactly the "is this a data table or a coincidence?" judgment [§FS-non-goals.3](functional-spec/FS-non-goals.md#3-code-ast-parsing) refuses to make. The implementation lives in `crates/grund-core/src/checker_references.rs` ([§AR-checker.2.13](../crates/grund-core/src/checker.rs)) — the reference-resolution family and the scope layer in one file, because `--full` is precisely that family run a second time over a wider tree. This repository now runs the flag on itself: the CI self-check step and the `grund check` pre-commit hook are both `check --full` ([§AR-ci.1](architecture/AR-ci.md#1-pre-commit-is-the-source-of-truth)), which found ten unresolvable illustrative citations in `README.md` and `examples/workspace/README.md` — two files `[scan] include` has never covered — now written with the `<§>` escape. Resolves issue #55. PR #64

- [§FS-check.1.2](functional-spec/FS-check.md#12-the-number-only-shorthand) / [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) / [§DF-number-only-citation-shorthand](decisions/functional/DF-number-only-citation-shorthand.md#df-number-only-citation-shorthand-the-number-only-shorthand-is-authoring-sugar-and-a-persisted-one-is-a-check-error): the **number-only citation shorthand** — `§FS-042` for `§FS-042-user-login` — is recognized, and a persisted one is now an error naming the canonical form to write. Under the `{kind}-{number}-{slug}` format `grund init` generates, the number alone already identifies a declaration within its kind, so people write the short form; `grund` had no position on it at all and the failure mode was silent. A `§`-marked token that every reader takes for a live citation was dropped on the floor — not resolved, not flagged, absent from `refs` and `cover` — while the declaration it cited was *simultaneously* reported `declared but never cited`, which is the opposite of the truth and invites deleting a live declaration. A dangling *full* ID errored correctly; only this shape vanished. [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) names that class in one line — *false negatives are bugs* — and the fix is one rule applied identically on every surface, because a shorthand that resolves in the editor and not in CI is worse than one that resolves nowhere. The shorthand is **authoring sugar, not a second stored grammar** ([§DISC-declaration-local-shorthand](discussions/proposals/2026-05-24-declaration-local-shorthand.md#disc-declaration-local-shorthand-declaration-local-shorthand-for-citing-sections-of-the-same-declaration) reached the same verdict in advance): it expands where you type it, resolves where you pass it, and is corrected where it is stored — so one greppable string per edge survives, and a citation still tells a reader what it points at without a lookup. Typing `$$FS-042` lands `§FS-042-user-login` in one step, in the editor ([§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform)) and under `grund fmt --write` ([§FS-fmt.2.4](functional-spec/FS-fmt.md#24-shorthand-to-canonical), a new `shorthand → canonical` rewrite that is also the bulk fix-it for the error). `grund FS-042` and `grund refs FS-042` resolve, which is what makes a clicked `§FS-042` open in a terminal or editor — the shared client matcher already claimed that shape, so before this the clients linked it and the resolver then reported the ID unknown ([§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2)); putting the rule in the engine rather than in six hand-written regexes is what keeps them from drifting from it. Three properties bound the recognition. The **marker is required** even under `strict = false`, where a bare *full* ID does count: `KIND-NNN` carries no slug to make an accidental match unlikely and occurs constantly as issue keys, part numbers, and standards references, so the marker is what supplies the intent ([§DF-reference-marker.2.1](decisions/functional/DF-reference-marker.md#21-marker)). The **full ID always wins**, and **only a whole token is a shorthand** — the full pattern claims its tokens first, and the shorthand pass then requires that nothing which could continue an ID follows its match. Both halves are load-bearing: the shorthand is a prefix of every longer ID-shaped token, so without the trailing boundary a typo'd `<§>FS-042-User-Login` would be reported as `<§>FS-042` and rewritten with `-User-Login` left glued to the canonical slug. And a **resolved shorthand is a real edge**: `refs` lists it, `cover` groups it, it grounds its file under `require_grounding`, it counts for citation directions, and the declaration stops being reported unused — the half that is easy to skip and expensive to omit, since the original report's most damaging symptom was not the missing error but the lie about an uncited declaration. Ambiguity is named, never guessed: a shorthand matching several declarations lists every candidate and resolves nothing, and one matching none says so — three message shapes, at most one *shorthand* finding per site, with §3.1 suppressed there so `unknown reference FS-042` never names a token that is not a full ID (a bad section or a forbidden direction at the same site is a different fact and still reported). It is an error rather than a warning because a warning leaves the exit code alone, so a repository could accumulate shorthand citations forever while CI stayed green, which is the state this ends. That does mean a repository already holding shorthand citations gains errors on upgrade, and it needs no deprecation window ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)): the shorthand was never a working feature to deprecate — it resolved nowhere and appeared in no report — so nothing that used to pass and mean something now means something else; a token that meant *nothing* now means *fix me*, and says so with the exact replacement text and a `grund fmt --write` that applies it. The shape is derived from `[id] format` by dropping `{slug}` and one adjacent separator, so it exists **only where the format carries both `{number}` and `{slug}`** ([§FS-id.4.1](functional-spec/FS-id.md#41-number-less-id-formats)): a `{kind}-{slug}` repository like `grund` itself compiles no extra pattern and pays nothing, which is why this tree gains no findings. Cross-namespace `<§>api/FS-042` resolves too (escaped here — this repository has no `api` member), against the aliased project's declarations, and `grund fmt --write` rewrites it there as well, under that project's `[id] format`. Where [§FS-fmt.2.3](functional-spec/FS-fmt.md#23-what-is-never-rewritten) forbids the rewrite — inline code, a link destination, a runtime string — the error does not fire either, so everything `check` reports is something `fmt` can clear. No `grund_config_version` bump and no `[id]` key — a second knob would let two installs disagree about what a citation *is* ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)) — and no `AGENTS.md` block bump: the block tells an agent to write canonical citations, which is still exactly right, and bumping it would hand every repository on v7 an `agents-init` error for a rule that changes nothing about what they should write. The rule itself lives in one `crates/grund-core/src/shorthand.rs` ([§AR-scanner.2.6](architecture/AR-scanner.md#26-number-only-shorthand-citations), [§AR-checker.2.12](../crates/grund-core/src/checker.rs)) rather than split across the four stages it plugs into, because the four halves of one invariant in four files with nothing naming the invariant is the drift this rule exists to prevent. What is *not* the rule sits beside it: the `[id] format` template parser and the ID renderer are grammar rather than shorthand (`id_format.rs`), and the keystroke-time transform is the LSP's (`on_type.rs`). Three shapes of the pass were rejected on the instruction-count meter before this one ([§AR-benchmarks](architecture/AR-benchmarks.md#ar-benchmarks-instruction-counting-benchmarks-for-the-hot-cli-commands), [§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)), and each failure is worth recording because the obvious implementation of every one of them is the slow one. Sweeping the line with an unanchored shorthand pattern cost **+46%** on the 10k-file fixture, because `FS-042` is a prefix of *every* `FS-042-user-login`, so the sweep yields one candidate per citation and each needs a second search to reject — the pass is therefore driven from marker positions and skips the markers the full-ID pass already claimed. Scanning the tree in `grund fmt` whenever the repo *could* have a shorthand cost **+89%** on `fmt --check`, which otherwise never scans at all — so `fmt` now starts with no declarations and scans on the first candidate it actually meets, redoing that one file, which means a repo that never writes a shorthand pays nothing. And compiling the two shorthand patterns at config load cost **+3–5% on every read command**, because on a small tree regex construction is a visible share of the whole run — they are built on first use instead. What remains is between **0.6% and 3.8%** across the suite, all of it under the 5% regression gate ([§AR-ci.5](architecture/AR-ci.md#5-benchmark-job)). Resolves issue #50. PR #62

### Changed

- [§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform) / [§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate): the `grund-core` on-type helper is now `on_type_line_edits(path, text, line_index, cursor, declarations) -> Vec<LineEdit>`, replacing `on_type_trigger_replacement`'s `Option<TriggerReplacement>`. An embedder applies the returned edits in order instead of reading a trigger span plus an optional expansion; `TriggerReplacement` and `TokenExpansion` are gone and `LineEdit` and `DeclaredId` take their place. Three things forced the shape. The two rewrites fire on *different* keystrokes rather than together, so a struct with one mandatory trigger field could not say "this keystroke only expanded a shorthand". The expansion can rewrite a citation the author did not just type, so it has to honour the whole-line skips `grund fmt` applies — a fenced block, a declaration heading — which a single line cannot reveal: hence the document plus a line index rather than one line. And `declarations` carries each declaration's path so the expansion is scoped to the edited file's own project. Passing an empty slice still gives trigger conversion alone. PR #62
- [§FS-fmt.2.1](functional-spec/FS-fmt.md#21-trigger-to-marker): `grund fmt` now consumes a trigger followed by the number-only shorthand, so `$$FS-042` becomes a citation where it used to stay literal text. A repository on a numbered format that contains a *typo'd* trigger — `$$FS-999` naming nothing — therefore gains a [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) error after `grund fmt --write` where the tree was previously green and silent. That is the intended direction: the author typed a citation trigger, so a token that resolves nowhere is a dangling reference and [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) wants it named rather than dropped. PR #62
- [§FS-config.3.2](functional-spec/FS-config.md#32-id--id-grammar): `[id] number_pattern` and `[id] slug_pattern` must each be a valid regex on their own. Two that balanced only against each other — `number_pattern = "("` with `slug_pattern = "a)"` — used to load successfully; they are now rejected on load with the underlying regex error. PR #62

### Fixed

- [§FS-config.3.5](functional-spec/FS-config.md#35-scan--what-gets-walked) / [§AR-scanner.1](architecture/AR-scanner.md#1-tree-walk): two `[scan] include` entries that name **one** subtree no longer report every declaration under it as a duplicate of itself. `include = ["docs", "docs/functional-spec"]` — or one directory written twice as `docs` and `./docs/` — started the walk twice inside the overlap, so `grund check` read each file there twice and every declaration came back as `duplicate declaration of <ID> (also declared at <the same path>:<the same line>)`, exiting `1` with nothing the author could act on: the two sites the message named were one site, and the only fix was to guess that the *config* was the problem. A redundant `include` list should be a no-op, not an error accusing a file of duplicating itself. Each root is now folded through its path components, so `docs`, `./docs`, and `docs/` are one root, and the sorted file list is collapsed before scanning. Under [§FS-check.1.3](functional-spec/FS-check.md#13-the-full-tree-scope---full) the same collapse carries the wider walk, where the config root is walked beside every `include` root by construction; there it is keyed on file *identity* rather than on the path, because an `include` root may be a symlink to a directory inside the config root and the two walks would otherwise reach one file under two names. The `include` roots are walked first so the surviving spelling is the one the plain run prints, which is what makes the in-scope half of a `--full` report byte-identical to `grund check` on the same tree.
