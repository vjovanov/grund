# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

## Unreleased

### Added

- [§FS-workspace.2.2](functional-spec/FS-workspace.md#22-a-member-that-may-be-legitimately-absent), [§FS-check.4.9](functional-spec/FS-check.md#49-a-workspace-member-declared-optional-is-absent): **a workspace member can be declared absent, and the run says which namespace it did not check.** A checkout where one member is legitimately missing — a private submodule CI never fetches, a sparse checkout, a sibling repository vendored in only for release builds — had no `grund check` run at all. Leaving the entry in `[workspace] members` is a fatal config error, and taking it out unregisters the alias, so every citation into that namespace becomes an unknown-alias error at its own site ([§FS-check.3.8](functional-spec/FS-check.md#38-cross-project-citation-failure)) — thousands of lines in a tree that cites the namespace widely. One path refuses to start and the other calls the whole tree broken, and neither is a run. `[workspace] optional_members` is the third path: a sibling of `members` with the same grammar, whose entries are the members this repository has declared **may** be absent. Present, an entry there is an ordinary member and is checked to the letter. Absent, the block loads without it, the run continues, and the namespace it would have contributed is *unverified* — a third state beside resolved and unknown ([§FS-workspace.4](functional-spec/FS-workspace.md#4-resolution)), reported once per namespace at the `optional_members` line rather than once per citation site. This is an opt-out, not a softer default: a member listed in `members` and missing still fails at the same line with the same verdict, and the message now names the key that would have made the absence legal. Absent means the path is not a directory and nothing more, so the empty directory git leaves for an uninitialized submodule is *present* — widening the test would put a typo'd directory on the unverified path and move the blind spot's edge somewhere no line of the repository records ([§FS-workspace.2.2.1](functional-spec/FS-workspace.md#221-what-absent-means)). The alias of an optional member is the entry's last path segment in both checkouts, and a present member whose `project_name` disagrees with it is a config error naming both names ([§FS-workspace.2.2.2](functional-spec/FS-workspace.md#222-the-alias-of-an-optional-member)): otherwise one citation text would resolve in the tree that has the member and quietly name nothing in the tree that does not, which is a trap only the checkout least equipped to notice can spring. A trailing `/*` glob may not be optional, because an absent parent names no namespaces — the refusal says to list one concrete entry per namespace instead. An absent entry's alias is unique among its siblings like every other alias ([§FS-workspace.3](functional-spec/FS-workspace.md#3-aliases)): an entry that collides with a present member, with the root project, or with another optional entry is a launch-time error, because a run that announced a namespace as unchecked while checking a different project under that same name would contradict itself in two adjacent lines. An entry that appears in both `members` and `optional_members` is refused from the config text rather than from the checkout, so the same pair of lists is refused in the tree that has the directory and the tree that does not. One entry written twice is one member in both checkouts as well, folded the way a repeat in `members` is folded rather than refused ([§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces)): a repeat names one directory and one namespace, so there is nothing to discard by folding it, and refusing it only where the directory is missing would be the checkout-dependent verdict the key exists to remove. A block whose every member is an absent optional one puts no project in scope, which is not an error either — the run announces each absent member and earns the empty-scan caution beside them, in the wording that is true of it: nothing was looked for under `[scan] include`, so the caution says what happened rather than offering a `grund init` scaffold for a tree that is already there ([§FS-check.2.2](functional-spec/FS-check.md#22-empty-scan)). What the run pays is a blind spot, and it is a **declared** one: [§REQ-no-missed-citation.2](requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded) enrols it as the fourth, chosen by the repository one written entry at a time and announced by every run that takes it. The announcement is a located warning on **stdout**, unlike its two neighbours ([§FS-check.4.7](functional-spec/FS-check.md#47-a-workspace-member-swallows-the-blocks-own-scan), [§FS-check.4.8](functional-spec/FS-check.md#48-unlisted-workspace-block)), which are CLI-level lines on stderr: nothing here is misconfigured and no other command's output is wrong, and this is the one run that is deliberately incomplete and still exits `0` — so the exit code carries nothing about coverage and the report has to. It withholds the `success` marker like any other warning ([§FS-check.2.1](functional-spec/FS-check.md#21-report-format)), names no remedy, and names no release, because the skip is the standing price of the opt-out rather than a state to migrate off. The key works in a nested `[workspace]` block exactly as it does at the outermost root, and `grund config show` prints it between `members` and `include_root` ([§FS-config.3.8](functional-spec/FS-config.md#38-workspace--sub-project-namespaces)). It is additive with an empty default, so `grund_config_version` stays at 1 and no configuration has to be edited. Decided in [§DF-optional-workspace-members](decisions/functional/DF-optional-workspace-members.md#df-optional-workspace-members-an-absent-member-is-declared-in-a-sibling-list-and-the-run-announces-the-namespace-it-did-not-check). Closes [issue #85](https://github.com/vjovanov/grund/issues/85). (PR #195)
- [§FS-check.4.10](functional-spec/FS-check.md#410-include_root--false-leaves-the-blocks-own-files-unread), [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces): **a `[workspace]` block that opted out of being a project no longer takes its own files out of every scan in silence.** `include_root = false` says the block's root is not a project, and the enclosing scan stops at the member boundary ([§FS-workspace.6](functional-spec/FS-workspace.md#6-nested-project-boundary)), so that directory's own files are read by nobody — a declaration there reaches no catalog, a citation there is never checked, and `--full` widens a project's scope and has no project here to widen. [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces) has said exactly that in prose since the key existed; no run said it, and over a grouping directory holding two dangling citations `check`, `check --full` and `list` were all silent and all exited `0`. Every command that resolves a block's member boundary — `check`, `list`, `refs`, `cover`, `fmt` and the rest — now prints one CLI-level `warning:` on stderr naming the block's own `include_root` line, the tree no project scans, what that costs, and the two remedies: set `include_root = true`, or point another project's `[scan] include` at the directory. It fires **only where the block's own tree actually holds a file a scan would have read** — the block's default scope, less the roots that are not on disk, the roots its own members already cover, and the roots another project of the run owns, then probed with the scanner's own walk and stopped at the first hit — so a grouping directory that only groups, a tree of unscanned file types, an excluded, gitignored or hidden tree, and a scope root that is a symlink into a sibling project all stay silent, and the walk is paid only by a block that opted out. That last one is [§FS-workspace.6](functional-spec/FS-workspace.md#6-nested-project-boundary)'s boundary in the one direction a member list cannot see, and it is asked of the root itself as well as of the descent, because a walk root is never pruned. A block with no member in scope is not this finding either: that is already a config error at its own line, and a run whose workspace expansion fails carries no such line for the blocks below its root, because the answer depends on where that run's other projects are and a failed expansion never produced that list — a declared, bounded blind spot that clears on the next run. It is once per block per run, keeps its text under `--format json` with no diagnostic `code`, and never moves the exit code — but like every warning it stands in place of the `success` marker ([§FS-check.2.1](functional-spec/FS-check.md#21-report-format)), which this finding is the first `[workspace]` caution to have to say out loud, because it is the first that can fire on an otherwise clean run. Unlike its two siblings [§FS-check.4.7](functional-spec/FS-check.md#47-a-workspace-member-swallows-the-blocks-own-scan) and [§FS-check.4.8](functional-spec/FS-check.md#48-unlisted-workspace-block) it names no release it becomes an error in, and never will: [§DF-unread-opted-out-block.2.3](decisions/functional/DF-unread-opted-out-block.md#23-what-makes-a-workspace-finding-ramp-and-what-makes-one-permanent) states the rule for all three — a finding is eligible to become an error only when every repository in that state is wrong *and* the configuration has a way to say "I meant it" — and a grouping directory holding a README nobody needs checked fails both, which leaves [§REQ-backwards-compatibility.2](requirements/REQ-backwards-compatibility.md#2-the-deprecation-path)'s deprecation path with nothing to schedule. This is the last of the two silent-scope holes [§DF-absorbed-scan-warning.4](decisions/functional/DF-absorbed-scan-warning.md#4-consequences) left open. Library callers: `CheckOutput` gains a public `unread_opted_out_blocks: usize` field carrying how many such lines the run printed before the report existed, an additive break for exhaustive struct literals and exhaustive destructuring; the struct has no `Default`, so unlike the `InitOpts` entry below there is no `..Default::default()` spelling that absorbs it. Decided in [§DF-unread-opted-out-block](decisions/functional/DF-unread-opted-out-block.md#df-unread-opted-out-block-the-unread-files-of-an-opted-out-block-are-a-conditional-warning-that-never-ramps). Closes [issue #71](https://github.com/vjovanov/grund/issues/71). (PR #196)

- [§FS-fmt.7](functional-spec/FS-fmt.md#7-one-model-and-a-write-step), [§REQ-no-wrong-citation.3](requirements/REQ-no-wrong-citation.md#3-no-wrong-write): **what `grund fmt` is is written down once, and every clause of it now has a check.** Twelve `fmt` defects were each fixed as its own bug, and the fix commits kept independently rediscovering fragments of one sentence: `fmt` is the model `grund check` verifies plus a write step, never a second implementation of it. [§FS-fmt.7](functional-spec/FS-fmt.md#7-one-model-and-a-write-step) states that as four rules, each citable and each with an artifact that fails when it breaks — scope-equivalence ([§FS-fmt.7.1](functional-spec/FS-fmt.md#71-scope-equivalence)), reader-equivalence ([§FS-fmt.7.2](functional-spec/FS-fmt.md#72-reader-equivalence)), preview-equivalence ([§FS-fmt.7.3](functional-spec/FS-fmt.md#73-preview-equivalence)), and no write without a complete model ([§FS-fmt.7.4](functional-spec/FS-fmt.md#74-no-write-without-a-complete-model)). Reader-equivalence is equality of the **(path, reason)** pairs rather than of the bytes of the line, with `nothing was rewritten: ` named as the one licensed difference: [§FS-fmt.3](functional-spec/FS-fmt.md#3-outputs) spells a strict abort's line differently on purpose, because the two exit `2`s mean opposite things, so byte equality would have put §7 in contradiction with §3 on the day it landed. The first three rules are behavioral and are pinned as cross-run properties over a corpus of six tree shapes — clean, strict-abort, partial source-only, two-scope, workspace, and workspace-member-abort — rather than over the one shape whose defect prompted each; the new `fmt-partial-scan-error-still-reports` e2e case pins the partial form of [§FS-fmt.7.2](functional-spec/FS-fmt.md#72-reader-equivalence) that no golden covered. The fourth is structural, because its prose form had already failed twice: completeness of the declaration set is now a precondition of the consumer instead of a habit of each producer, so the whole-project findings a `fmt` walk resolves shorthands and cross-references against are accepted only as a `CompleteFindings` proof, obtainable from a scan that met no error or from a reuse that checks the same field a fresh scan would have refused on. Handing that consumer a bare findings collection — the mistake [issue #105](https://github.com/vjovanov/grund/issues/105) actually was — is now a program that does not build, and `scripts/check_fmt_complete_findings.sh` is the check that it stays one. The rule has a direction, and §7 says so: equivalence binds `fmt` to `check`'s **model**, and never `check`'s findings to what `fmt` is able to rewrite — the second coupling is what [§FS-fmt.2.4](functional-spec/FS-fmt.md#24-shorthand-to-canonical) has and what makes a citation inside a string literal unflaggable by any command ([issue #83](https://github.com/vjovanov/grund/issues/83)). No behavior changes anywhere: no output, exit code, or diagnostic text moves, and every existing golden passes unmodified. Decided in [§DF-fmt-one-model](decisions/functional/DF-fmt-one-model.md#df-fmt-one-model-fmt-is-the-shared-verified-model-plus-a-write-step-and-completeness-is-a-precondition-rather-than-a-convention). Closes [issue #106](https://github.com/vjovanov/grund/issues/106). (PR #192)

- [§FS-check.4.8](functional-spec/FS-check.md#48-unlisted-workspace-block), [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces): **a `[workspace]` block no enclosing block lists is no longer silently ignored.** Such a block is claimed by nobody: at the outer scope it is ignored and its whole subtree is absorbed into the enclosing project's namespace, while a run started *at* it names every project from itself — so the two scopes spell the same projects differently and a citation passes the inner check and fails the run CI does. Every command whose run walks the tree — `check`, `list`, `refs`, `cover`, `fmt`, and the ID read — now emits one CLI-level `warning:` on stderr naming the block's `[workspace]` line, saying its projects are absorbed rather than named under their own alias path, and giving the two config edits that clear it: list the directory in the enclosing `[workspace] members`, or keep it out of that project's `[scan]`. Only the outermost unlisted block of a chain is reported, because one edit fixes the chain; `include_root = false` on the block changes nothing, because it still contributes a segment to every alias path below it. The scope is the walk the run already makes, at one config probe per walked directory — which is what finds the `.agents/grund.toml` form the walk never descends into — so a block behind `[scan] exclude`, an ignore file, a member boundary, or a narrowed scope stays unreported, and both [§FS-workspace.6.1](functional-spec/FS-workspace.md#61-nested-workspaces) and [§DF-nested-workspaces.3.4](decisions/functional/DF-nested-workspaces.md#34-a-path-means-the-same-thing-at-every-scope) still record that residue. It is a warning, so the exit code is unchanged — but like every warning it stands in place of the `success` marker, and the message names the release it becomes an error in ([§RM-unlisted-workspace-error](roadmap.md#rm-unlisted-workspace-error-flip-the-unlisted-workspace-warning-to-an-error)), the deprecation path [§REQ-backwards-compatibility.2](requirements/REQ-backwards-compatibility.md#2-the-deprecation-path) asks of a finding no `grund` command can write the fix for. Decided in [§DF-unlisted-workspace-block](decisions/functional/DF-unlisted-workspace-block.md#df-unlisted-workspace-block-an-unlisted-workspace-block-is-reported-by-the-walk-that-meets-it). Closes [issue #72](https://github.com/vjovanov/grund/issues/72). (PR #191)

- [§FS-init.1](functional-spec/FS-init.md#1-inputs), [§FS-init.4](functional-spec/FS-init.md#4-exit-codes), [§AR-ci.3](architecture/AR-ci.md#3-current-hooks): **`grund init --check` turns the `--dry-run` preview into a gate.** A managed agent-entrypoint block can go stale in its rendered *text* while its `(vN)` heading is still current, and until now nothing in the toolchain could fail a build over it: `grund check` verifies the block's version rather than its bytes ([§FS-check.3.5](functional-spec/FS-check.md#35-invalid-agent-entrypoint-init-block)), and `grund init --dry-run` saw the drift, printed `would-update AGENTS.md`, and exited `0`. `--check` runs that same preview, prints that same report byte for byte, writes nothing under any flag combination including `--force`, and exits `1` when any reported path is a `would-write `, `would-append `, or `would-update `; a `note:` and the `next:` block never earn it, and a refused target still exits `2`. `--dry-run` itself deliberately keeps its `0`: `1` is the findings slot [§FS-cli.5](functional-spec/FS-cli.md#5-exit-code-mapping-is-fixed) freezes and `init` had never used, so `--check` fills a hole in the mapping, whereas moving `--dry-run` would change the verdict an existing green CI step gets on upgrade — the one thing [§REQ-backwards-compatibility.1](requirements/REQ-backwards-compatibility.md#1-what-is-covered) puts the exit-code mapping out of reach of. This repository now runs the gate on itself, as a `grund-init-check` pre-commit hook placed after `grund fmt --write` so the block is measured once `fmt` has had its say. Library callers: `InitOpts` gains a public `check: bool` field, an additive break for exhaustive struct literals in the same way `--no-vcs` was in `0.10.1`; `..InitOpts::default()` is unaffected. Closes [issue #172](https://github.com/vjovanov/grund/issues/172). (PR #185)

- [§FS-fmt.2.5](functional-spec/FS-fmt.md#25-suppressed-scopes), [§FS-config.3.10](functional-spec/FS-config.md#310-fmt--suppressing-the-rewrite): **`grund fmt` can be suppressed per file and per region, without taking the citations out of `check`.** A new `[fmt] exclude` list names files the command performs no rewrite in, as gitignore-style globs against the config root; a `grund:fmt off` comment line — `<!-- grund:fmt off -->` in Markdown, a `[scan] comment_prefixes` comment in a source file — suppresses the rewrite from the next line until the matching `on` or the end of the file. Both cover all four rewrite classes ([§FS-fmt.2.5.1](functional-spec/FS-fmt.md#251-fmt-exclude--a-file-at-a-time), [§FS-fmt.2.5.2](functional-spec/FS-fmt.md#252-grundfmt-off--grundfmt-on--a-region-at-a-time)), not just cross-reference wrapping, because every one of them disturbs the thing the scopes exist to protect: a hand-aligned diagram in an HTML `<pre>` block or an indented block, whose edge labels are citations that must stay live for `grund refs` and the LSP. Nothing else changes — a suppressed file is still walked and still checked, so `grund check` reports exactly what it reported before, and the dry run and `--write` agree about the scope by saying nothing about it. The LSP's live on-type expansion honours both scopes as well ([§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform)), so an editor cannot canonicalize a shorthand on a line `grund fmt --write` refuses to touch. A kind's index entries outrank both scopes and are still linkified ([§FS-fmt.2.5.3](functional-spec/FS-fmt.md#253-a-kinds-index-is-still-linkified)), the same precedence [§DF-index-always-linkified](decisions/functional/DF-index-always-linkified.md#df-index-always-linkified-the-cross-reference-pass-always-runs-on-a-kinds-index-file) already has over `[fmt.cross_refs] enabled = false`, so no suppression can leave an index in a state [§FS-check.3.17](functional-spec/FS-check.md#317-index-entry-is-not-a-link) reports and `fmt` refuses to repair. The key is additive with an empty default, so `grund_config_version` stays at 1 and no configuration has to be edited. Decided in [§DF-fmt-suppression](decisions/functional/DF-fmt-suppression.md#df-fmt-suppression-fmt-suppression-is-per-file-and-per-region-and-the-index-carve-out-outranks-both). - [§FS-config.3.4.8](functional-spec/FS-config.md#348-require_grounding-and-grounding_level--grounding-per-place-and-per-level), [§FS-check.3.6](functional-spec/FS-check.md#36-ungrounded-source-file-opt-in): **grounding is now asked per place and per level.** `require_grounding` and a new `grounding_level` are `[[kinds]]` row keys, each with its `[reference]` twin as the default for rows that do not say — the shape `index` already has ([§FS-config.3.4.2](functional-spec/FS-config.md#342-index--the-kinds-index-file)), a global default with the row winning. So "every file under `skills/` must cite a declared ID" is finally sayable without also demanding it of every workflow and build script in the scan, which is why that hole stayed open and [§FS-check.2.2.1](functional-spec/FS-check.md#221-citation-direction-obligation-applies-to-nothing) could only warn about it — and that warning now names the row's key rather than the global one. `grounding_level` is an integer in Markdown heading levels: `1` is the file, which is the unit every configuration had before the key existed, `2` adds every `##` subtree, `6` every heading; a leaf cites directly, a parent is satisfied by any descendant, and a file with no heading at the level is one unit, so nothing passes vacuously. A source file has no headings, so it gets the two ranks grund can see without parsing code ([§FS-non-goals.3](functional-spec/FS-non-goals.md#3-code-ast-parsing)) — unindented doc-comment blocks at level 2, all of them above it — read by indentation, not by syntax. `[citations]` obligations follow the same unit ([§FS-check.3.11](functional-spec/FS-check.md#311-missing-required-citation)), so *whether* a place's files must cite and *what* they must cite are asked of one thing. `grund check --require-grounding` and the global key stay one knob: the flag sets the same default, and an explicit `false` on a row still wins ([§FS-check.1](functional-spec/FS-check.md#1-inputs)). Both keys are additive, so `grund_config_version` stays at 1 and no configuration has to be edited to keep the meaning it had. One finding is added to trees that changed nothing: an inline declaration in a **non-citable** home no longer grounds the file it sits in ([§FS-check.3.6.2](functional-spec/FS-check.md#362-the-unit)), because a declaration there is misplaced to begin with ([§FS-check.3.7](functional-spec/FS-check.md#37-misplaced-declaration-configured-kind-home)). Every file it reaches already carries a `must not be declared in <home>` error at the same line, so no passing tree starts failing and no verdict moves ([§REQ-backwards-compatibility.1](requirements/REQ-backwards-compatibility.md#1-what-is-covered)) — but a run's bytes do, which is why it is written here. Decided in [§DF-require-grounding.4](decisions/functional/DF-require-grounding.md#4-grounding-per-place-and-per-level). Closes [issue #150](https://github.com/vjovanov/grund/issues/150). (PR #182)

### Changed

- [§FS-config.3.4.6](functional-spec/FS-config.md#346-prefix-the-former-spelling-of-kind-removed-in-0130), [§FS-distribution.4.2](functional-spec/FS-distribution.md#42-a-release-may-not-contradict-the-releases-the-trees-own-messages-name): **the `[[kinds]] prefix` key stops loading, at the release its warning named.** `prefix` was this key's name until `citable = false` made it wrong for half the table; 0.12.0 renamed it to `kind`, kept the old spelling loading, and warned every config that still used it, naming **0.13.0** as the release it would stop working in — the deprecation path [§REQ-backwards-compatibility.2](requirements/REQ-backwards-compatibility.md#2-the-deprecation-path) asks of a renamed config key. This is that release, so this is a **breaking change** for any configuration still on the old spelling, which is what the window was for. A `[[kinds]]` entry that spells `prefix` is now **refused** rather than read with the key ignored — an ignored name would leave the row with no kind and change what the configuration means without saying so — so every walking command exits `2` on it with an ordinary config error ([§FS-config.4.3](functional-spec/FS-config.md#43-invalid-config-behavior)) anchored at the line `prefix` is written on: ``error: grund.toml:4: [[kinds]] `prefix` was removed in grund 0.13.0 — rename it to `kind` ``. An entry that sets both `kind` and `prefix` earns that same error at that same line, and the old "sets both" error is gone with the key: with one of the two names removed there is nothing left to disambiguate. **The migration is the rename, by hand**, and that is why the error names the line to make it on — a grund before 0.13.0 did it in one `grund config show > grund.toml`, but from 0.13.0 the config does not load, so nothing that has to read it can help. `grund_config_version` stays at 1: every affected config is already version 1 or carries no version key, so no version gate could catch one and only this rejection can. The deprecation warning, its `deprecated-config-key` diagnostic and the release constant behind it are deleted, and the roadmap milestone that scheduled the removal is retired into [§FS-config.3.4.6](functional-spec/FS-config.md#346-prefix-the-former-spelling-of-kind-removed-in-0130). Retiring that milestone took away the last thing tying the `0.13.0` in the error to the version actually published, and the direction it left open is the dangerous one: a bump that reaches a *deadline* reddens a ramp test, while a bump that stays *below* a release a landed change already names reddens nothing, so a scheduled patch release would have published this breaking change as `0.12.4` under an error saying `0.13.0`. - [§AR-workspace.9.1](architecture/AR-workspace.md#91-a-golden-has-one-on-disk-spelling): **refreshing the e2e goldens over an unchanged tree now rewrites nothing.** `UPDATE_EXPECTED=1` used to rewrite 21 tracked goldens whatever case the change was about, so a golden update arrived with churn that had to be reverted by hand or was committed by accident.
