# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

### Added

- §DF-conversation-link-target: the local-conversation `link` form is now a **Markdown link whose label is the bare citation and whose target is an absolute URI**, and the addressing scheme is a per-machine choice — the new user-configuration key `[reference] conversation_target` and its flag `grund integrations --write --conversation-target <target>`, accepting `file` (default), `path`, `web`, `vscode`, `vscodium`, and `cursor` (§FS-config.3.1, §FS-integrations.4.3). This reverses the plain-`path:line` form recorded days earlier: that form rested on the one row of the §DF-neural-link-generation matrix carrying no observation of its own — Claude Code linkifying `file_path:line_number` — which failed its first click-test on 2026-08-11, while an absolute-URI Markdown link worked on the first try under `file:`, `vscodium:`, and `https:` (matrix rows 12–14; row 1's recorded failure was a *relative* target all along). The form is **gated per agent**: Claude receives every target, Codex receives `web` only — its renderer shows a local destination in place of the label, erasing the citation — and every unverified agent keeps `path`, the form it already had, so the gate can never make a surface worse. `path` remains available as the explicit opt-out. **Schema:** the `AGENTS.md` init block bumps to **v6** and the `grund integrations` agent-guidance block to **v3**; run `grund init` and `grund integrations --write` to refresh. Note that a `CLAUDE.md` that is a symlink to `AGENTS.md` resolves to the canonical entrypoint and therefore keeps the plain form (§FS-init.2.3.4.17). PR #45.

- [§DF-repo-conversation-opinion](decisions/functional/DF-repo-conversation-opinion.md#df-repo-conversation-opinion-repositories-may-commit-a-link-only-conversation-rendering-opinion) / [§DISC-conversation-rendering-layers](discussions/proposals/2026-07-21-conversation-rendering-layers.md#disc-conversation-rendering-layers-layered-ownership-of-local-conversation-citation-rendering): repositories may commit a `link`-only conversation-rendering opinion via `[reference] conversation` ([§FS-config.3.1](functional-spec/FS-config.md#31-reference--citation-form)). When set, the generated agent entrypoint teaches linked local-conversation citations — the declaration location beside the citation — at the time as plain `path:line` text, superseded within this same cycle by the absolute-URI link form of §DF-conversation-link-target (then recorded non-working in terminal TUIs by the [§DF-neural-link-generation](decisions/functional/DF-neural-link-generation.md#df-neural-link-generation-agents-compose-clickable-citation-links-themselves-grund-does-not-grow-a-link-command) matrix). The `grund integrations` global block texts become self-scoping (inert outside grund repositories) and carry the precedence rule: explicit machine preference > repository opinion > `plain` — the committed opinion is the no-knowledge fallback for readers whose machines grund never touched (fresh clones, cloud and CI sessions, Cursor and Windsurf, whose only channel is the committed entrypoint), while a recorded `plain` proves an installed rendering layer and wins, so an opinionated repository costs installed users nothing. A preference-only design (no repository key) was considered and rejected: it permanently orphans the entrypoint-only readers; the serving matrix in the DISC records who is reached by which layer, and the setup guide (`docs/clickable-citations.md` §6) walks users through each case. A repo-local uncommitted instruction file was researched across the supported-agent set and deferred (portable to Codex alone). PR #45.

Local/TUI rendering follows a user preference installed into global agent instructions; repository web text follows one fixed, context-sensitive rule. Links keep the citation as visible text and plain is always the fallback. (Later in this same cycle, click-testing reversed the Claude Code rows and the local-conversation form became an absolute-URI Markdown link — see the §DF-conversation-link-target entry above.) PR #45.
- [§FS-integrations](functional-spec/FS-integrations.md#fs-integrations-grund-prints-and-installs-its-rendering-layer-integrations) / [§DF-integrations-command](decisions/functional/DF-integrations-command.md#df-integrations-command-integrations-earns-a-cli-slot-as-one-time-setup-where-a-per-citation-link-command-did-not): add the `grund integrations [<client>]` command — the one-stop shop that makes the clickable-citation rendering layer installable from `cargo install grund`. A write also records the user-local conversation preference and synchronizes global Codex, Claude, Gemini, GitHub Copilot, Zed, and Pi instructions; clientless `--write --conversation link` overrides the plain default without installing an arbitrary client or changing repository configuration. `--format json` emits a machine detection plan. Detection cannot tell the two apart by presence, since both export an identical `VSCODE_*` environment; what differs is where those values *point*, so `codium` is marked alongside `vscode` when one of them names VSCodium's application directory, and the catalog offers both installs rather than guessing. Ghostty documents exactly the needed option — `link`, a regex bound to an arbitrary action — but its reference marks it `TODO: This can't currently be set!`; only built-in URL matching works, and with no `path:line` opener the `--conversation link` fallback does not help either. Apple Terminal.app and Windows Terminal have no regex-to-action hook at all. - [§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2): the location beside a citation is a link too. The `link` conversation form prints `§<ID> path:line`, and iTerm2 and the VS Code terminal open such locations natively — WezTerm and kitty matched URLs only, leaving the location half inert text. The terminal matchers gain a location shape (a dot-extension segment with a `:line[:col]` suffix); `grund-open` tells it from an ID mechanically — a section suffix is dotted, never coloned — climbs to the nearest ancestor holding the file, and opens the editor at that line, dropping any column. No `grund` and no config is consulted, so a location click works in any repository; peek pages the file from the cited line. Registered before the citation rule in WezTerm, the location matcher also converts the recorded path false positive into one correct link for `:line`-suffixed paths. PR #45.
- [§FS-integrations.3.4](functional-spec/FS-integrations.md#34-manual-client-iterm2): add `iterm2`, the most-used macOS terminal, as the first **manual** client. It keeps its rules in a binary property list, so the managed-block contract does not apply and grund will not rewrite a live profile blob for a convenience. `grund integrations iterm2` prints the Smart Selection rule to add — the shared citation regex at `Very High` precision so it does not lose to iTerm2's built-in path rule, with a `Run Command…` action of `grund-open \0` on cmd-click and `grund-open --peek \0` as a second action on the right-click menu. `--write` installs the resolver and the user preference, then prints what only a human can apply, reporting `manual` and exiting `0`. A manual client always reports `installed: false` because grund never reads that plist; the detection plan gains `"install_kind"` so a caller can tell *not installed* from *not knowable*. Noted where it matters: iTerm2's Semantic History already makes `path:line` cmd-clickable, so `--conversation link` alone gives Mac users clickable citations with no rule at all. PR #45.
- [§FS-integrations.3.3](functional-spec/FS-integrations.md#33-reading-a-declaration-without-leaving): reach a citation from the keyboard in WezTerm. `ctrl+shift+g` labels every citation on the screen and opens the one whose label you type, `ctrl+shift+i` peeks at it instead — kitty's hints model, built on WezTerm's quick-select. This is the more dependable of the two paths, not a convenience twin of the click: a full-screen program that has captured the mouse can swallow a click, and citations are read while typing. `p` would have mirrored kitty exactly, but WezTerm binds it to the command palette, so peek takes `i` for *inspect*. Every gesture — both clicks and both keys — now ends in one shared resolver call, so they cannot drift apart, and a custom picker action suppresses quick-select's copy so the clipboard is left alone. Asked and answered while investigating: true hover is not possible in any terminal, and for WezTerm the reason is now recorded rather than asserted — its mouse bindings trigger only on `Down`, `Up`, `Drag`, `WheelUp`, `WheelDown`, no callback learns the cursor's row and column, and [wezterm#4](https://github.com/wez/wezterm/issues/4) has requested a link tooltip since 2018 with no implementation. PR #45.
- [§FS-integrations.3.3](functional-spec/FS-integrations.md#33-reading-a-declaration-without-leaving): read a declaration without leaving what you are doing. Opening a citation answers *where*; peek answers *what it says*. `grund-open --peek` renders the resolved `path:line` and the declaration lead through a pager, and each terminal client binds it to a disposable surface: a kitty overlay (`ctrl+shift+p`), a tmux popup (`prefix` + `G`, tmux 3.2+), a wezterm split pane (`ctrl+shift+`-click). It is the same resolver in a second mode, so a peek and a click cannot disagree about where a citation points. VS Code gets true hover instead — its terminal-link tooltip now carries the declaration's `--brief` slice and resolved location, cached per citation because the provider runs per rendered line. No terminal can hover: none exposes a hover event or link tooltip to configuration, and WezTerm's request for one has been open since 2018. PR #45.
- [`docs/clickable-citations.md`](clickable-citations.md), linked from the README: a user-facing setup guide for the terminal and editor integrations. Covers the three prerequisites that each fail silently (`grund` and `~/.local/bin` on `PATH`, an editor the resolver can find), the per-client install and the reload each one needs, a verification walkthrough whose line numbers are real IDs in this repository, the `plain` vs `link` conversation preference and how a repository opinion overrides it, and a troubleshooting path that separates a matcher problem from a resolver problem in one command. Documents that WezTerm requires wiring `grund_apply_hyperlink_rule(config)` by hand — the block installs but does nothing until it is called, which looks identical to a broken install. PR #45.
- `scripts/try-integrations.sh`: a manual testbed for the [§FS-integrations](functional-spec/FS-integrations.md#fs-integrations-grund-prints-and-installs-its-rendering-layer-integrations) clients. It installs the integrations built from the working tree into a throwaway `HOME` — so the client dotfiles, the resolver, the user preference, and six global agent instruction files all land in a sandbox rather than on the developer's machine — then launches the client in a repository full of real citations with every open logged. `show` skips all of that and prints one citation of every shape into the terminal you are already in — with `--tui`, under mouse capture, the state an agent TUI leaves the terminal in. `doctor` reports what is testable on this machine, including a `wezterm` on `PATH` that is really a Flatpak wrapper (there the sandbox environment never crosses the sandbox boundary, so the launch would silently test the real configuration); `resolve` runs the click path headlessly (marker stripping, section suffix, swept-in punctuation, the root climb from a subdirectory and past a workspace member, E2E directory targets, unknown ids, `--peek`), so the part that can be automated does not need a human clicking. PR #45.

### Fixed

- [§FS-config.3.1](functional-spec/FS-config.md#31-reference--citation-form) / [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions): the user-level preference is spelled `[reference] conversation`, the same key a repository commits — it was `[render.links] conversation`, a second name for one setting that appeared in no documentation at all. The file is hand-editable, so the repository spelling is the one a user reaches for, and the scan matched a single literal: `[reference] conversation = "link"` there was silently ignored, recorded as its opposite (`plain`), and written back *beside* what the user wrote, leaving a duplicate table no TOML parser will load. So were `[ reference ]` with spaces and the dotted `reference.conversation`, both plain TOML; `conversation = 'link'` was rejected outright as "not quoted". The key is now read the way TOML defines it — header whitespace, dotted paths, either quote style. Both scopes are documented, with which value to choose and why `plain` stays machine-only ([`docs/clickable-citations.md`](clickable-citations.md) §6.1). PR #45.
- [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions): **nothing in the user configuration is an error any more** — every line grund does not act on is one `warning:` at its line, then ignored. That covers a key grund does not read (naming `reference.conversation` as the only one it consumes there — so a typo like `converstaion`, a spelling from an older grund, and a repository-only key such as `marker` set there in the belief that it applies to every project are all reported instead of reading as configured and doing nothing), a value it cannot interpret (which leaves it with no preference from this file, the same state as a machine that never wrote one), and a repeated key (the first wins, which is the occurrence a write rewrites, so a read and a write cannot disagree). This is the one place the two configuration files deliberately differ, and the difference is what each decides: the repository config is a closed allow-list that refuses an unknown key or a bad value outright ([§FS-config.4.3](functional-spec/FS-config.md#43-invalid-config-behavior)) because it governs whether a tree checks clean, while this file is machine-local, read by one command, and only picks between two renderings of the same true citation — a stale line in a personal config is not a reason to refuse to install a terminal integration. `--conversation` given on the command line is still validated as an argument. Exit code is unchanged at `0`. PR #45.
- [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions): installing a *terminal* integration no longer provisions the configuration trees of five agents the machine does not have. `grund integrations kitty --write` created `~/.gemini/GEMINI.md`, `~/.copilot/copilot-instructions.md`, `~/.config/zed/AGENTS.md`, and `~/.pi/agent/AGENTS.md` from nothing — files the user did not ask for and would not think to remove. A target is written when the agent's own directory or its instruction file already exists, and reported `skipped <path> (no <dir>)` otherwise, the same discovery rule the repository entrypoints follow ([§FS-init.2.3](functional-spec/FS-init.md#23-generated-agent-entrypoints)); re-running after installing an agent picks it up. PR #45.

Printed target hints stay `~`-rooted and byte-stable; only resolution changed. PR #45.

- [§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2): the kitty integration took two of kitty's own keymaps away and then could not run the resolver. `ctrl+shift+g` is kitty's `show_last_command_output`, and `ctrl+shift+p` is the prefix its nine hint kittens already live under (`p` `f` a path, `p` `y` a hyperlink, `p` `c` choose-files) — where a plain binding is not a collision but a deletion, because kitty resolves a trigger by discarding every sequence mapped before the last non-sequence definition, which was ours. The two gestures now join that family instead of replacing it: `ctrl+shift+p` `g` opens a citation, `ctrl+shift+p` `i` peeks — the same *go* and *inspect* letters WezTerm takes plainly, verified against kitty's own `get_shortcut` to leave all nine defaults reachable. Both gestures now spawn through `sh` with `~/.local/bin` and `~/.cargo/bin` prepended, as WezTerm already did — tested end to end against a kitty started with a desktop-session `PATH`. No `cd` joins them: kitty hands the picked window's directory to whatever it spawns, which is the one piece of this that was already right. The guide gains the matching prerequisite it was missing — `GRUND_OPEN_CMD`/`EDITOR` must be set where the terminal process sees them, since a GUI terminal never ran your `.zshrc`. PR #45.

Every lookup is now guarded and tried in turn, with `get_foreground_process_info().cwd` behind them — except under Flatpak, where WezTerm spawns the pane's program on the host through `flatpak-spawn` and can only see the sandbox-side helper, whose directory is a real one that is not the shell's. - [§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2): clicking a citation now opens the line it actually cites, from anywhere in the tree, under any configured marker. A product-management pass over the rendering layer found the shipped resolver truncated the citation at the first `.` — so every `§<ID>.<section>` click landed on the declaration heading rather than the section; handed the editor a config-root-relative path, which opens nothing when the shell sits in a subdirectory; and matched a hardcoded `§`, leaving repositories with a custom `[reference] marker` silently unclickable. `grund-open` and the VS Code extension now resolve through `grund <ID>[.<section>] --format json`, walk up to the config root and join against it, and strip whatever marker they are given; the click matchers accept any punctuation marker and the namespace-qualified `§<alias>/<ID>` form. - [§FS-integrations.4.1](functional-spec/FS-integrations.md#41-marked-blocks-in-dotfiles): `grund integrations wezterm --write` produced a `wezterm.lua` that does not parse. The managed-block markers were hardcoded to `#`, which comments `kitty.conf` and `.tmux.conf` but is the *length operator* in Lua — verified against the Lua 5.4 compiler as `unexpected symbol near '#'`, which costs the user their entire WezTerm configuration rather than just the grund block. Separately, a from-scratch `wezterm.lua` defined `grund_apply_hyperlink_rule` but never called it and returned no config, so even a parsing file registered nothing; a fresh write now appends an unmanaged starter config that wires the helper up. - [§FS-workspace.8.1](functional-spec/FS-workspace.md#81-grund-aliasid): `grund <alias>/<ID> --format json` reported a member-relative `path` while `grund list` reported a workspace-root-relative one, contradicting the [§FS-config.3.6](functional-spec/FS-config.md#36-output--report-format) promise that report paths are relative to the config root. - [§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2): the click handlers now run the resolver in the clicked pane's working directory — tmux's `run-shell` starts in the tmux *server's* start directory and WezTerm's spawn in the GUI process's, so a click failed unless the terminal happened to be launched inside the repository. - [§FS-integrations.3.2](functional-spec/FS-integrations.md#32-editor-clients-vscode-codium): the VS Code extension walked no further than the first workspace folder, so opening a subdirectory of the repository ran `grund` there and joined the config-root-relative path against the wrong base; it now walks up to `.agents/grund.toml` exactly as the shell resolver does. And a click on a `§E2E-<case>` citation failed with an editor error: a directory-backed E2E declaration answers with the manifest shape — no `"line"`, and a `path` naming the case *directory* ([§FS-show.2.4](functional-spec/FS-show.md#24-e2e-cases)) — which `showTextDocument` rejects; the case directory is now revealed in the Explorer, the editor's form of the bare directory open the terminal resolver already performed — falling back to the OS file manager when the opened folder is a subdirectory of the repository and the Explorer cannot show the case. Hover and click now share one `--brief` resolution, since the brief report already carries the `path` and `line` a click needs; a click on a hovered citation spawns nothing. PR #45.
- [§FS-init.2.3.6](functional-spec/FS-init.md#236-clickable-citations): the generated `### Clickable citations` section hardcoded `§` while every other part of the managed block renders the repository's configured `[reference] marker`. In a repo using another marker the block therefore instructed agents to write a token that repo does not treat as a citation at all — `grund check` ignores it under `strict`, so the claim it grounded was silently never verified. Both sentences now carry the real marker; with the default `§` the output is byte-identical, so no existing block changes. Found by generating a `marker = "@"` repo and reading what agents then wrote into it. PR #45.
- [§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions): the global agent-guidance blocks name no marker. They are user-global and written once, before grund knows which repositories will be opened, while `[reference] marker` is per-repo — the same constraint that already forbids the click matchers and the resolver from hardcoding `§` ([§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2)), which these texts alone were violating. Unlike the repository entrypoint there is nothing to interpolate at install time, so the user layer now carries the *policy* (`write citations bare` / `follow each citation with its declaration location`) and the repository layer carries the *syntax*. Verified in a `marker = "@"` repository: agents wrote bare `@`-marked citations and suppressed the repository's `link` opinion, so dropping the marker cost no actionability. PR #45.
- [§FS-completions.1](functional-spec/FS-completions.md#1-user-facing-command): the generated bash, zsh, and fish completion scripts complete the `integrations` subcommand the spec already promised, and `grund help integrations` and the README name all six supported clients instead of four. PR #45.

### Changed

- **Schema:** the `AGENTS.md` init block version bumps v4 → v5 ([§FS-init.2.3.6](functional-spec/FS-init.md#236-clickable-citations)): the `### Clickable citations` section gains the config-derived local-conversation sentence and joins the [§FS-check.3.5](functional-spec/FS-check.md#35-invalid-agent-entrypoint-init-block) drift check. Migration: re-run `grund init`. The `grund integrations` user-instruction block bumps v1 → v2 ([§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions)); re-run `grund integrations --write --conversation <value>` to refresh global agent instructions. PR #45.
