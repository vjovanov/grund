# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file, and **older releases live one-per-file under `docs/changelog/`** so a reader (human or agent) only loads the history they ask for. Each entry cites the FS/AR/G/DF IDs it touches, so the changelog is itself part of the conformant tree (`grund .` validates the citations).

Schema-version bumps are called out explicitly: `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) and the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)). A bump to either is a breaking change for the consumer and must appear under **Changed** with a migration note.

## 1. Conventions

### 1.1 Sections per release

`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` — the Keep-a-Changelog set; omit any with no entries. A large entry (the first release, folding in pre-history, is the case in point) may add narrative subsection headings — e.g. `Baseline`, `Renamed`, `Implemented`, `Distribution and bindings` — for readability when the standard six would bury the structure; the semver-relevant changes still live under the standard names.

### 1.2 Schema version callouts

Any change to `grund_config_version` or the `AGENTS.md` block version goes under **Changed** with the prefix `**Schema:**` and a one-line migration pointer.

### 1.3 Entry style

One bullet per change, present tense, leading with the affected ID. Example: `§FS-show: add --head mode for truncated output`.

### 1.4 Progressive discovery

Only **Unreleased** and the **most recent release** are inline. When a new release ships, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md` and a one-line link is added under [§3 Older releases](#3-older-releases). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

## Unreleased

### Added

- [§FS-lsp.1.2](functional-spec/FS-lsp.md#12-hover-preview): the **declaration-side title hover now answers "who leans on this?"** — hovering a Markdown declaration heading, the same declaration written inline in a doc-comment, a numbered section heading, or an inline-spec stub title returns ``​`FS-check: …` — cited at 12 sites across 5 files`` where it used to return the bare title token. That hover existed as an editor affordance and little else: a title hover has to return *something* for Codium and its relatives to give the whole title a hover range, and what it returned was the text the cursor was already resting on — a popup whose entire content was legible behind it. The fact that is genuinely missing from that screen is the usage, and reading it meant leaving the editor for `grund refs <ID>` ([§FS-refs](functional-spec/FS-refs.md#fs-refs-grund-lists-every-citation-of-an-id)), which is the lookup an agent or a contributor runs before changing or deleting a declaration — precisely when the editor is open on the declaration. The numbers are that query's, not a second tally kept beside it: on a whole-ID title the counted set is by definition the set `grund refs <ID>` reports, citations inside scanned source comments included, `[reference] strict` honoured, and in a workspace a member's own `§<ID>` and a sibling's `§<alias>/<ID>` both counted ([§FS-workspace.8.2](functional-spec/FS-workspace.md#82-grund-refs)) — held by a test that runs the query over the same tree and compares, rather than by the claim. They are counted off the session snapshot the server already maintains, never a fresh query: `refs` loads its own workspace context, so calling it per hover would re-walk the tree on a request the editor fires as the cursor moves ([§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible), [§AR-lsp.5](architecture/AR-lsp.md#5-determinism-and-parity-tests)). On a numbered section heading the count is the section subtree — `§<ID>.<section>` and deeper — which is the set that heading's own references and definition already return ([§FS-lsp.1.3.1](functional-spec/FS-lsp.md#131-references-from-declarations)), and deliberately wider than `grund refs <ID> --section <s>`, whose filter keeps only citations whose coordinate is *exactly* `<s>` ([§FS-refs.1](functional-spec/FS-refs.md#1-inputs)). Where the two readings conflict, the one that keeps a title's hover and its reference list in agreement wins: those are one gesture apart in the same editor, while the terminal comparison is one a reader has to go looking for. The wording is fixed rather than clever — only the two nouns inflect, `across` is the preposition at every count, and zero reads `not cited` instead of `cited at 0 sites across 0 files`, a sentence pretending to be a count. Zero is not suppressed in favour of the unused-declaration warning ([§FS-check.4.1](functional-spec/FS-check.md#41-unused-declaration)) either: that warning never fires on `E2E` declarations or on section headings, so a hover that fell silent at zero would go quiet exactly where nothing else speaks — and `not cited` stays a count in the hover's own words, so an editor that renders diagnostics inside the hover popup still shows the warning once and only once ([§FS-lsp.1.1](functional-spec/FS-lsp.md#11-diagnostics)). One matcher in `grund-core` now decides which citations belong to a declaration-side title, so the hover count, `textDocument/references`, definition-as-usages, and occurrence highlight cannot drift apart, and the body bytes are formed in the engine rather than in the transport, so a second frontend cannot re-word them ([§FS-lsp.4](functional-spec/FS-lsp.md#4-determinism-and-parity-with-the-cli)). The LSP suite's stdio harness moved to shared test support on the way, which is what let the hover cases land as a suite named for the request they drive. Resolves issue #51.

- [§FS-check.1.2](functional-spec/FS-check.md#12-the-number-only-shorthand) / [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) / [§DF-number-only-citation-shorthand](decisions/functional/DF-number-only-citation-shorthand.md#df-number-only-citation-shorthand-the-number-only-shorthand-is-authoring-sugar-and-a-persisted-one-is-a-check-error): the **number-only citation shorthand** — `§FS-042` for `§FS-042-user-login` — is recognized, and a persisted one is now an error naming the canonical form to write. Under the `{kind}-{number}-{slug}` format `grund init` generates, the number alone already identifies a declaration within its kind, so people write the short form; `grund` had no position on it at all and the failure mode was silent. A `§`-marked token that every reader takes for a live citation was dropped on the floor — not resolved, not flagged, absent from `refs` and `cover` — while the declaration it cited was *simultaneously* reported `declared but never cited`, which is the opposite of the truth and invites deleting a live declaration. A dangling *full* ID errored correctly; only this shape vanished. [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) names that class in one line — *false negatives are bugs* — and the fix is one rule applied identically on every surface, because a shorthand that resolves in the editor and not in CI is worse than one that resolves nowhere. The shorthand is **authoring sugar, not a second stored grammar** ([§DISC-declaration-local-shorthand](discussions/proposals/2026-05-24-declaration-local-shorthand.md#disc-declaration-local-shorthand-declaration-local-shorthand-for-citing-sections-of-the-same-declaration) reached the same verdict in advance): it expands where you type it, resolves where you pass it, and is corrected where it is stored — so one greppable string per edge survives, and a citation still tells a reader what it points at without a lookup. Typing `$$FS-042` lands `§FS-042-user-login` in one step, in the editor ([§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform)) and under `grund fmt --write` ([§FS-fmt.2.4](functional-spec/FS-fmt.md#24-shorthand-to-canonical), a new `shorthand → canonical` rewrite that is also the bulk fix-it for the error). `grund FS-042` and `grund refs FS-042` resolve, which is what makes a clicked `§FS-042` open in a terminal or editor — the shared client matcher already claimed that shape, so before this the clients linked it and the resolver then reported the ID unknown ([§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2)); putting the rule in the engine rather than in six hand-written regexes is what keeps them from drifting from it. Three properties bound the recognition. The **marker is required** even under `strict = false`, where a bare *full* ID does count: `KIND-NNN` carries no slug to make an accidental match unlikely and occurs constantly as issue keys, part numbers, and standards references, so the marker is what supplies the intent ([§DF-reference-marker.2.1](decisions/functional/DF-reference-marker.md#21-marker)). The **full ID always wins**, and **only a whole token is a shorthand** — the full pattern claims its tokens first, and the shorthand pass then requires that nothing which could continue an ID follows its match. Both halves are load-bearing: the shorthand is a prefix of every longer ID-shaped token, so without the trailing boundary a typo'd `<§>FS-042-User-Login` would be reported as `<§>FS-042` and rewritten with `-User-Login` left glued to the canonical slug. And a **resolved shorthand is a real edge**: `refs` lists it, `cover` groups it, it grounds its file under `require_grounding`, it counts for citation directions, and the declaration stops being reported unused — the half that is easy to skip and expensive to omit, since the original report's most damaging symptom was not the missing error but the lie about an uncited declaration. Ambiguity is named, never guessed: a shorthand matching several declarations lists every candidate and resolves nothing, and one matching none says so — three message shapes, at most one *shorthand* finding per site, with §3.1 suppressed there so `unknown reference FS-042` never names a token that is not a full ID (a bad section or a forbidden direction at the same site is a different fact and still reported). It is an error rather than a warning because a warning leaves the exit code alone, so a repository could accumulate shorthand citations forever while CI stayed green, which is the state this ends. That does mean a repository already holding shorthand citations gains errors on upgrade, and it needs no deprecation window ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)): the shorthand was never a working feature to deprecate — it resolved nowhere and appeared in no report — so nothing that used to pass and mean something now means something else; a token that meant *nothing* now means *fix me*, and says so with the exact replacement text and a `grund fmt --write` that applies it. The shape is derived from `[id] format` by dropping `{slug}` and one adjacent separator, so it exists **only where the format carries both `{number}` and `{slug}`** ([§FS-id.4.1](functional-spec/FS-id.md#41-number-less-id-formats)): a `{kind}-{slug}` repository like `grund` itself compiles no extra pattern and pays nothing, which is why this tree gains no findings. Cross-namespace `<§>api/FS-042` resolves too (escaped here — this repository has no `api` member), against the aliased project's declarations, and `grund fmt --write` rewrites it there as well, under that project's `[id] format`. Where [§FS-fmt.2.3](functional-spec/FS-fmt.md#23-what-is-never-rewritten) forbids the rewrite — inline code, a link destination, a runtime string — the error does not fire either, so everything `check` reports is something `fmt` can clear. No `grund_config_version` bump and no `[id]` key — a second knob would let two installs disagree about what a citation *is* ([§FS-non-goals.13](functional-spec/FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)) — and no `AGENTS.md` block bump: the block tells an agent to write canonical citations, which is still exactly right, and bumping it would hand every repository on v7 an `agents-init` error for a rule that changes nothing about what they should write. The rule itself lives in one `crates/grund-core/src/shorthand.rs` ([§AR-scanner.2.6](architecture/AR-scanner.md#26-number-only-shorthand-citations), [§AR-checker.2.12](../crates/grund-core/src/checker.rs)) rather than split across the four stages it plugs into, because the four halves of one invariant in four files with nothing naming the invariant is the drift this rule exists to prevent. What is *not* the rule sits beside it: the `[id] format` template parser and the ID renderer are grammar rather than shorthand (`id_format.rs`), and the keystroke-time transform is the LSP's (`on_type.rs`). Three shapes of the pass were rejected on the instruction-count meter before this one ([§AR-benchmarks](architecture/AR-benchmarks.md#ar-benchmarks-instruction-counting-benchmarks-for-the-hot-cli-commands), [§GOAL-fast-feedback](goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)), and each failure is worth recording because the obvious implementation of every one of them is the slow one. Sweeping the line with an unanchored shorthand pattern cost **+46%** on the 10k-file fixture, because `FS-042` is a prefix of *every* `FS-042-user-login`, so the sweep yields one candidate per citation and each needs a second search to reject — the pass is therefore driven from marker positions and skips the markers the full-ID pass already claimed. Scanning the tree in `grund fmt` whenever the repo *could* have a shorthand cost **+89%** on `fmt --check`, which otherwise never scans at all — so `fmt` now starts with no declarations and scans on the first candidate it actually meets, redoing that one file, which means a repo that never writes a shorthand pays nothing. And compiling the two shorthand patterns at config load cost **+3–5% on every read command**, because on a small tree regex construction is a visible share of the whole run — they are built on first use instead. What remains is between **0.6% and 3.8%** across the suite, all of it under the 5% regression gate ([§AR-ci.5](architecture/AR-ci.md#5-benchmark-job)). Resolves issue #50. PR #62

### Changed

- [§FS-lsp.1.4](functional-spec/FS-lsp.md#14-live-trigger-transform) / [§FS-distribution.3.1](functional-spec/FS-distribution.md#31-rust-grund-core-crate): the `grund-core` on-type helper is now `on_type_line_edits(path, text, line_index, cursor, declarations) -> Vec<LineEdit>`, replacing `on_type_trigger_replacement`'s `Option<TriggerReplacement>`. An embedder applies the returned edits in order instead of reading a trigger span plus an optional expansion; `TriggerReplacement` and `TokenExpansion` are gone and `LineEdit` and `DeclaredId` take their place. Three things forced the shape. The two rewrites fire on *different* keystrokes rather than together, so a struct with one mandatory trigger field could not say "this keystroke only expanded a shorthand". The expansion can rewrite a citation the author did not just type, so it has to honour the whole-line skips `grund fmt` applies — a fenced block, a declaration heading — which a single line cannot reveal: hence the document plus a line index rather than one line. And `declarations` carries each declaration's path so the expansion is scoped to the edited file's own project. Passing an empty slice still gives trigger conversion alone. PR #62
- [§FS-fmt.2.1](functional-spec/FS-fmt.md#21-trigger-to-marker): `grund fmt` now consumes a trigger followed by the number-only shorthand, so `$$FS-042` becomes a citation where it used to stay literal text. A repository on a numbered format that contains a *typo'd* trigger — `$$FS-999` naming nothing — therefore gains a [§FS-check.3.13](functional-spec/FS-check.md#313-number-only-shorthand-citation) error after `grund fmt --write` where the tree was previously green and silent. That is the intended direction: the author typed a citation trigger, so a token that resolves nowhere is a dangling reference and [§GOAL-no-dangling-refs](goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration) wants it named rather than dropped. PR #62
- [§FS-config.3.2](functional-spec/FS-config.md#32-id--id-grammar): `[id] number_pattern` and `[id] slug_pattern` must each be a valid regex on their own. Two that balanced only against each other — `number_pattern = "("` with `slug_pattern = "a)"` — used to load successfully; they are now rejected on load with the underlying regex error. PR #62

## 2. [0.9.0] — 2026-08-13

### Added

- [§AR-ci.9](architecture/AR-ci.md#9-file-size-budget-gate): a `fissile` pre-commit hook gives [§AR-core-module-layout.3](architecture/AR-core-module-layout.md#3-file-size)'s "below 500 lines of code" its first enforcement. The rule has been stated since the core/CLI split but never checked, and files had reached eight times it — `crates/grund-core/src/tests.rs` was 4,111 code lines in a single `mod tests`. Budgets live in `.agents/fissile.toml`, per file type, counting code lines only so doc-comment citations are never taxed; soft overflows warn, hard overflows fail the commit. The `tests/` Python suite that gates this repository's own scripts is measured too, on the Rust test budget but with its own guidance, since advice to add an `include!()` line is meant for a crate. Adoption is a ratchet rather than a freeze: every file already over budget is pinned at today's size, with a reason and the trigger that retires it, in the registry matching its severity — `docs/file-size-agent-exceptions.toml` for soft, `docs/file-size-human-exceptions.toml` for hard. Each entry declares `kind`, which fixes what its reason must establish: `structural` states the architectural constraint that makes splitting the file illegal or harmful and never expires (`until = "indefinite"`, enforced), while `deferred` names the boundary that is missing and what must exist before the split can happen. Three files are structural — `skills/grund-init/SKILL.md`, `crates/grund-core/src/model.rs`, `crates/grund-cli/src/cli_help.rs` — and 20 carry debt across 32 registry entries, a distinction `fissile audit` now reports as two separate counts. Keeping them apart is the point — a file that is merely large should not be able to borrow the language of one that must stay whole. So the tree starts clean at both tiers, nothing is blocked now, and one line past a recorded ceiling brings the finding straight back. A file over the hard budget is over the soft one too, and a `deferred` hard entry leaves that soft finding standing on purpose, so such a file needs an entry in each registry; rather than copy the argument across, the human registry carries it and the soft twin records the same ceiling, points at the registry that reasons, and retires when it does — one file, one argument, with no stale half for a reader to trust. A `structural` hard entry needs no twin, since it silences both tiers itself. Entries carry no `EX-NNN` id: what identifies one is the registry it lives in and the path it accepts, the same pair `fissile` leads its diagnostics with, and a slug on top of that is a second name that can go stale. `fissile` validates the sizes but not what a reason may claim, so `tests/test_file_size_exceptions.py` enforces the rest: structural entries never expire, a `deferred` `until` must name a condition rather than a bigger number (`"revisit if it passes 500"` is rejected as a budget wearing the word "until"), twins agree with their originals and appear only where a deferred entry leaves a soft finding standing, the registry schema version is pinned so an unmigrated upgrade fails by name, and every recorded path still exists, so a rename cannot strand an entry pointing at nothing. Per [§AR-ci.1](architecture/AR-ci.md#1-pre-commit-is-the-source-of-truth) the hook is in `.pre-commit-config.yaml` and CI installs `fissile` 0.5.0 — whose registry schema is `fissile_exceptions_version = 2` — so `pre-commit run --all-files` enforces the same budgets remotely. PR #59, PR #60

- [§AR-ci.8](architecture/AR-ci.md#8-commit-message-attribution-gate): CI gains a `commit-messages` job that rejects AI-tool attribution boilerplate — an assistant co-author trailer, a "generated with" marker, a session-link trailer — in the commit messages a push or pull request contributes. The check already existed as a pre-commit hook bound to two stages, but [§AR-ci.1](architecture/AR-ci.md#1-pre-commit-is-the-source-of-truth)'s parity promise is delivered by `pre-commit run --all-files`, which reproduces only the stages whose input is a file list; the `commit-msg` stage takes a message file and was therefore absent from CI, leaving a trailer that touches no tracked file with no remote gate at all. Eleven such commits had reached `main`. The job scans `base..head` on a pull request and `before..sha` on a push, narrowing to the tip commit when the base is unresolvable after a force-push, and runs without a Rust toolchain so it reports in seconds. `scripts/check_no_claude_attribution.py` replaces the shell script and serves all three surfaces — staged files, one message file, a revision range — from a single pattern set, kept narrow so ordinary prose about Claude stays legal. [§AR-ci.1](architecture/AR-ci.md#1-pre-commit-is-the-source-of-truth) now records the `--all-files` limitation so the next stage-bound hook does not repeat the gap. PR #58

### Changed

- **Schema:** [§FS-config.1](functional-spec/FS-config.md#1-file-location-and-discovery) / [§DF-config-file-location](decisions/functional/DF-config-file-location.md#df-config-file-location-grundtoml-is-discovered-at-two-names-per-directory-and-init-writes-the-bare-one): config discovery now probes **two names at every level** of the upward walk — the bare root-visible `grund.toml` first, then `.agents/grund.toml` — and `grund init` generates the bare one ([§FS-init.2.4](functional-spec/FS-init.md#24-generated-grundtoml)). The `.agents/` wrapper earned its keep at a repository root, where it keeps agent tooling off a root already carrying `Cargo.toml` and `package.json`; it stopped earning it at workspace members, where it meant one `member/.agents/` directory per member holding exactly one file one level down, and where the layout was not merely conventional — a member root was partly *identified* by carrying `.agents/grund.toml`, so the nesting was load-bearing in the workspace-member rendering of [§FS-init.2.3.4.15](functional-spec/FS-init.md#23415-workspace-members) as well as in discovery. One uniform rule replaces the special-casing: root and members each pick the form that suits them, a workspace may mix the two, and a bare member config shadows an ancestor's `.agents/` one exactly as a nested `.agents/grund.toml` always did. Nothing existing breaks — no key changes meaning, no file becomes invalid, and there is no `grund_config_version` bump ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)); a config written for the old rule is read identically by the new one, and `init` never overwrites a config it finds under either name, so re-running it after this change cannot produce a redundant pair. What *does* change is the default a new project meets, and the reason is discoverability across *several* workspaces rather than tidiness within one ([§DF-config-file-location.2.4](decisions/functional/DF-config-file-location.md#24-a-projects-grounding-must-be-visible-from-its-root-listing)). `.agents/` is a dot-directory — hidden by `ls`, by editor file trees, by shell globs — so under that layout the question "is this a grund workspace?" had no answer a reader could see: you had to already know to look inside a hidden directory, or run a command per candidate. With one repository that cost is paid once and forgotten, which is why the original choice looked right; with a workspace root and its members, or a dozen sibling checkouts of which some are grounded and some are not, every one of them looks un-grounded and the property a reader most needs at a glance is the one the layout hides. A root `grund.toml` answers it from the listing, the way `Cargo.toml` answers "is this a Rust crate" — and a tool that supports both forms while generating the one that needs a directory created for it was recommending the other by omission. Everything that asked "does this directory have `.agents/grund.toml`" now asks whether it has *either* name, and where the answer feeds a diagnostic, the diagnostic names the file that was actually read. Moving an existing config to the root is a `git mv` with no other edit, and never required. This repository moved its own. **Schema:** two managed blocks bump, each for a taught-workflow change rather than wording. The `grund integrations` agent-guidance block goes to **v4** — its self-scoping texts gated on "repositories with a `.agents/grund.toml`", which a bare-config repository does not match on a literal reading ([§FS-integrations.4.3](functional-spec/FS-integrations.md#43-user-preference-and-global-agent-instructions)); run `grund integrations --write` to refresh. The `AGENTS.md` init block goes to **v6 → v7** — its namespace rule tells an agent to give a new subproject its own config, and that instruction now names the bare form `init` generates ([§FS-init.2.3](functional-spec/FS-init.md#23-generated-agent-entrypoints)); `grund check` reports a v6 block as outdated and `grund init` re-renders it. Without the bump an agent reading a stale block would keep creating configs in the form the tool no longer generates, with nothing saying so ([§GOAL-no-silent-breakage](goals.md#goal-no-silent-breakage-changes-ship-through-a-deprecation-path)). The clickable-citation integrations are part of the same sweep: the terminal resolver and the VS Code extension each found the config root by probing `.agents/grund.toml` alone, so every repository on the generated bare form had unclickable citations; both now climb on either name ([§FS-integrations.3.1](functional-spec/FS-integrations.md#31-terminal-clients-wezterm-kitty-tmux-iterm2), [§FS-integrations.3.2](functional-spec/FS-integrations.md#32-editor-clients-vscode-codium)), and `grund integrations --write` refreshes them by content comparison without a further block bump. Resolves issue #48. PR #61

- [§FS-check.4.3](functional-spec/FS-check.md#43-redundant-config-pair) / [§FS-config.1.1](functional-spec/FS-config.md#11-when-one-directory-carries-both): when one directory carries **both** names, the bare `grund.toml` wins and `grund check` warns about the `.agents/` file it ignored — `warning: .agents/grund.toml is ignored — grund.toml takes precedence; delete one`, a CLI-level line on stderr that leaves the exit code alone. The form the tool generates is the form that governs, so a project never has to hold one rule for the file grund writes and a contradicting one for the file grund reads; it is also what a user reaching for a root `grund.toml` means, since a repository acquires the pair only when someone deliberately puts one beside an existing `.agents/` config. The warning is what makes that order safe to state — the losing file is never silently ignored, so a config quietly replaced is reported at the first `check`. It is a warning and not an error because the pair is the ordinary transient state of a migration in either direction, and making the intermediate step of a supported move a hard failure is the opposite of what a migration aid should do. `grund config validate` and `grund config show` report it too ([§FS-config.4.1](functional-spec/FS-config.md#41-grund-config-validate-path), [§FS-config.4.2](functional-spec/FS-config.md#42-grund-config-show-path)) — those are the surfaces a user reaches when the answer to "why is my config not taking effect" is that grund is reading the other file. Six e2e fixtures turned out to be carrying exactly this pair — dead root copies left behind on 2026-05-11 when the fixtures' configs moved into `.agents/`, one of them stale enough to disagree with the file that was actually read. The new warning surfaced four of them on its first run (the other two are cases that exit before any warning is emitted) and all six are deleted here. They are also the strongest evidence *against* this tie-break, and the reason it is recorded rather than assumed ([§DF-config-file-location.4](decisions/functional/DF-config-file-location.md#4-alternatives-considered)): every one of them predates dual discovery, when a bare `grund.toml` was neither generated nor read, so they are artifacts of a form that was never live rather than files a user wrote on purpose. PR #61

- [§FS-config.4.1](functional-spec/FS-config.md#41-grund-config-validate-path): **`grund_core::validate_config` now returns `Result<Config>`** instead of `Result<()>`, so a caller can print the non-fatal findings the new `config_warnings` reports without loading the config twice. Embedders matching on `Ok(())` need `Ok(_)`. It is `effective_config` under the name of the question `grund config validate` asks and delegates to it rather than repeating the body. `print_config_warnings` is exported alongside, so the published CLI and the deprecated `grund_core` command adapter ([§AR-bindings.2](architecture/AR-bindings.md#2-grund-core-the-only-place-logic-lives)) cannot drift on the `warning: ` prefix or the stream it goes to. PR #61

- [§AR-core-module-layout.1](architecture/AR-core-module-layout.md#1-module-categories): split the three largest files into category siblings, a pure refactor with no change to CLI output, diagnostics, scan behavior, or template bytes ([§AR-core-module-layout.2](architecture/AR-core-module-layout.md#2-refactor-boundary)). `crates/grund-core/src/tests.rs` (4,111 lines, one `mod tests`) becomes thirteen `tests_*` modules plus a shared `tests_support`; `crates/grund-cli/src/cli.rs` (1,735 lines) becomes one file per command, each now carrying the `§FS-` citation for the command it implements; and the deprecated `config` command adapter moves out of `crates/grund-core/src/config.rs` into `config_cmd.rs`, taking that file from 936 to 732 lines. Because both crates are assembled by `include!`, the moves needed no module, visibility, or import changes. The 159 tests are unchanged and still pass. Two of the new modules import `tests_support` for cases that are all `#[cfg(unix)]` — the resolver is a POSIX shell script — so those imports are gated the same way; unguarded they are dead code on Windows, which `-D warnings` rejects.
