# FS-integrations: grund prints and installs its rendering-layer integrations

Locally, a plain `§<ID>` citation is meant to be clickable and hoverable — resolution belongs to the rendering layer ([§DF-neural-link-generation](../decisions/functional/DF-neural-link-generation.md#df-neural-link-generation-agents-compose-clickable-citation-links-themselves-grund-does-not-grow-a-link-command)). That layer is user-side, one-time configuration in the spirit of the editor LSP snippets ([§FS-lsp.2.3](FS-lsp.md#23-editor-configuration-one-time-per-editor)): grund ships no first-party marketplace plugin. `grund integrations` is the one-stop shop that makes those integrations installable by humans and agents alike — the binary carries every artifact and prints it on demand, in the same dry-run-first ethos as `grund completions` ([§FS-completions](FS-completions.md#fs-completions-grund-completes-declared-ids-in-shells)) and `grund init` ([§FS-init](FS-init.md#fs-init-grund-bootstraps-a-new-grund-conformant-repo)). It exists so that `cargo install grund` is enough to get clickable citations in a terminal or editor, serving [§GOAL-agent-grounding](../goals.md#goal-agent-grounding-agents-stay-cited-as-they-work) without asking the user to hand-assemble scripts. Why a one-time-setup command earns a slot on the frozen subcommand surface when a per-citation `link` command did not is recorded in [§DF-integrations-command](../decisions/functional/DF-integrations-command.md#df-integrations-command-integrations-earns-a-cli-slot-as-one-time-setup-where-a-per-citation-link-command-did-not).

## 1. User-facing command

```
grund integrations [<client>] [--write] [--conversation plain|link] [--conversation-target <target>] [--agent <name>] [--format text|json]
```

- With no `<client>` and no write flags, grund detects the caller's environment (§2) and prints the integrations that apply, each with its one-line install command. `--format json` prints the same detection as a machine-shaped plan (§5).
- With a `<client>` — one of `codium`, `iterm2`, `kitty`, `tmux`, `vscode`, `wezterm` — grund prints that client's integration: the config snippet plus, for the terminal clients, the embedded `grund-open` resolver script (§3). Deterministic and environment-independent (§6).
- With an explicit client, `--write` applies the integration to the client's real configuration instead of printing it, as a managed, marked block (§4), and synchronizes the user's local-conversation preference into global agent instructions (§4.3). A client with no writable configuration installs what it can and prints the rest for the user to apply (§3.4).
- `--conversation plain|link` overrides the user preference while writing. It is accepted only with `--write`. When present without a client, the command updates only the user preference and global agent instructions; this preference-only form is unambiguous and does not install an arbitrary client. With no override, a client installation records `plain` on first use and preserves the stored preference thereafter. `plain` tells agents to write bare citations for the installed rendering layer, while `link` tells them to carry the declaration's location with the citation, as a Markdown link over an absolute URI ([§DF-conversation-link-target](../decisions/functional/DF-conversation-link-target.md#df-conversation-link-target-the-conversation-link-form-is-a-markdown-link-over-an-absolute-uri-addressed-per-machine)), and fall back to the bare citation when uncertain.
- `--conversation-target <target>` selects how that link addresses the declaration — one of `file` (default), `path`, `web`, `vscode`, `vscodium`, `cursor` (§4.3). `--agent <name>` scopes it to a single agent instead of the machine (§4.4). Like `--conversation`, it is accepted only with `--write`, and either flag alone is enough for the clientless preference-only form. It is accepted while the effective preference is `plain`, where it is recorded and inert: a machine that later switches to `link` keeps the target it already chose. An unknown value is a CLI-level error listing the accepted set, exit `2`. Bare `grund integrations --write`, with neither a client nor a conversation flag, remains an error.

An unknown client is a CLI-level error: `error: unknown integration client \`<client>\`` plus `known clients: codium, iterm2, kitty, tmux, vscode, wezterm` on stderr, empty stdout, exit `2`. The client set is closed and frozen the same way the subcommand surface is ([§FS-cli.4](FS-cli.md#4-errors-with-no-source-location)), so adding a client is a deliberate, changelog-gated change.

## 2. Detection

With no `<client>`, grund inspects the environment to decide which integrations apply. Detection reads only these variables, in this fixed order, and never writes or scans:

- `WEZTERM_EXECUTABLE` → `wezterm`
- `KITTY_WINDOW_ID` → `kitty`
- `TERM_PROGRAM` — value `WezTerm` → `wezterm`, `iTerm.app` → `iterm2`, `tmux` → `tmux`, `vscode` → `vscode`
- `VSCODE_PID` or any `VSCODE_*` marker → `vscode`; additionally → `codium` when any of those values names VSCodium's application directory
- `TMUX` (non-empty) → `tmux`

Zero, one, or several clients may match at once (a VS Code integrated terminal running under tmux inside WezTerm matches three). Matches are reported in the frozen client order `codium, iterm2, kitty, tmux, vscode, wezterm`, deduplicated, never in environment-probe order, so a given environment always prints the same text. When nothing matches, grund prints the full catalog of clients with their one-line installs and a note that none was detected — a discoverable menu rather than an error. Detection succeeds with exit `0` in every case; an unrecognized terminal is not a failure.

Both forms close with the same two lines: how to preview a client before installing it, and the URL of the setup guide. The guide is where the parts of this setup that `--write` cannot perform are written down — the prerequisites that each fail silently (the resolver's directory on `PATH`, an editor it can find) and the per-client manual step (§3.4, §4.1) — and detection is the command a user runs *first*, often having reached it from `grund --help` rather than from the README. Naming the guide there costs two lines and is the only pointer that reaches a caller who never saw the repository.

Because detection depends on ambient environment variables, only the explicit-`<client>` form (§1) and `--help` are byte-stable across machines; the no-client form is stable only for a fixed environment. Golden coverage therefore pins explicit clients (§6).

## 3. Per-client artifacts

Every artifact is embedded in the binary, like the `init` templates and `completions` scripts; nothing is fetched and nothing is published to a marketplace, so the no-first-party-plugins stance ([§FS-lsp.2.3](FS-lsp.md#23-editor-configuration-one-time-per-editor)) holds.

### 3.1 Terminal clients: `wezterm`, `kitty`, `tmux`, `iterm2`

Each prints two things on stdout, exit `0`:

1. A config snippet for that terminal that registers a click/hover handler for `§<ID>` citations, wired to run the resolver.
2. The embedded `grund-open` resolver script — a POSIX shell script that takes a citation or bare `<ID>`, resolves it with `grund` to a `path:line` site, and opens it. The command it opens with is `GRUND_OPEN_CMD` when set, else `EDITOR`, else a platform default; the user's editor choice lives in that environment variable, never in shared repository text ([§DF-neural-link-generation](../decisions/functional/DF-neural-link-generation.md#df-neural-link-generation-agents-compose-clickable-citation-links-themselves-grund-does-not-grow-a-link-command)).

The snippet and the resolver are printed together so a human can read both before installing. `GRUND_OPEN_CMD` is an argv-style command prefix, not shell source: grund-open appends one `path:line` argument without evaluating repository-controlled paths as commands; users who need more elaborate argument placement use a wrapper executable. Any text the handler passes in — a tmux copy buffer, a kitty hint — reaches grund-open as a single quoted argument, never as shell source. The one-line install shown by detection (§2) is the `--write` form (§4).

Resolution proceeds in three steps, and each exists because the click carries less context than a command line does:

- **Find the root.** The handler passes a token, never a directory, so the click may arrive with the shell anywhere in the tree — which is why every client handler must first put the resolver in the *clicked pane's* working directory: tmux's `run-shell` starts in the server's start directory and WezTerm spawns from the GUI process's, so without an explicit `cd` a click works only when the terminal happened to be launched inside the repository. kitty is the exception that needs no `cd`: its hints kitten records the picked window's directory and supplies it to whatever it spawns — as the process working directory for a program, as `--cwd` for a `launch` — so the snippet must not add one. From there the resolver climbs: it tries every ancestor holding a config under either discovery name ([§FS-config.1](FS-config.md#1-file-location-and-discovery)) — the bare `grund.toml` or `.agents/grund.toml`, since both name the same config root and the resolver only needs the directory — nearest first, and keeps the first root where `grund` resolves the citation. Nearest-only is not enough — from inside a workspace member the member's config resolves its own bare IDs, but a workspace-qualified `<alias>/<ID>` resolves only from the workspace root above it, so a failed resolution continues the climb instead of ending it. With no config-bearing ancestor at all it reports `grund-open: no grund.toml (root or .agents/) at or above <dir>` and exits `1` — naming the real problem rather than blaming the ID; with ancestors that all failed to resolve, the error is the ID's.
- **Strip the marker, keep the section.** `[reference] marker` is per-repo ([§FS-config.3.1](FS-config.md#31-reference--citation-form)) while the installed artifacts are user-global and written once, so neither the click matchers nor the resolver may hardcode `§`. The matchers require a 1–3 character run of non-word, non-space characters before the ID shape, and the resolver drops any leading run of non-alphanumeric characters. This admits every configured marker, tolerates punctuation the matcher swept in (`(<§>FS-x`), and leaves a namespace-qualified `<alias>/<ID>` intact because an alias begins alphanumeric. The same tolerance has one recorded false positive: a printed spec *path* contains ID-shaped segments the matcher cannot tell from a citation — `docs/functional-spec/FS-integrations.md` also matches at `/functional-spec/FS-integrations`, punctuation-marked and alias-shaped — and clicking that fragment reports the id unknown. It is accepted rather than excluded because no portable matcher can require a word boundary before the marker (the terminal engines disagree on lookbehind), and excluding `/` from the marker class merely moves the match to the preceding `-`. The real citation on the same line still matches and resolves; the false link costs one explanatory error, never a wrong file — and a `:line`-suffixed path is claimed whole by the location matcher below before this fragment can form. The ID shape the matchers accept is a kind that starts with an uppercase letter and may carry digits after it — `E2E` is a kind grund itself declares, and a letters-only kind pattern would leave every `<§>E2E-<case>` citation silently unclickable — then `-` and the slug. The `.<section>` suffix is **preserved**, not truncated.
- **Resolve and join.** `grund <ID>[.<section>] --format json` reports the cited section's own line — truncating the suffix would send every subsection click to the declaration heading — and a `path` relative to the config root ([§FS-config.3.6](FS-config.md#36-output--report-format)). The resolver joins that path onto the root it found and hands the editor an absolute path. `grund` itself still never emits one ([§FS-errors.4](FS-errors.md#4-determinism)); composing it at the point of use is what makes a click work from a subdirectory. Field extraction is anchored to the end of the JSON object, because `body` carries arbitrary declaration prose that may itself contain `"path":` or `"line":`. A directory-backed E2E declaration answers with the manifest shape instead ([§FS-show.2.4](FS-show.md#24-e2e-cases)) — no `body` and no `"line"` — so a second extraction, anchored on the grund-controlled `{"id":…,"kind":"E2E"` prefix, accepts it; the case *directory* is what opens, with no `:line` suffix to garble the argument.

Both the click matchers and the resolver therefore accept a bare local `§<ID>` and a namespace-qualified `§<alias>/<ID>`; in a workspace the qualified form resolves through `grund`'s own alias routing ([§FS-workspace.8.1](FS-workspace.md#81-grund-aliasid)) rather than through string matching over the ID catalog.

The number-only shorthand ([§FS-check.1.2](FS-check.md#12-the-number-only-shorthand)) needs no separate matcher and gets none. The ID shape above — a kind, `-`, then a slug that may begin with a digit — already matches `§FS-042` and `§FS-042.1`, so a clicked shorthand reaches `grund-open` exactly like a full citation, and it opens because `grund <ID>` resolves the shorthand at the CLI boundary. That ordering is deliberate: putting the shorthand rule in the engine rather than in six hand-written client regexes is what keeps the clients from drifting from it ([§DF-number-only-citation-shorthand.4](../decisions/functional/DF-number-only-citation-shorthand.md#4-consequences)). Before the engine accepted it, these matchers linked the shorthand and the resolver then reported the ID unknown — a live link to a dead end.

**The location beside a citation is a link too.** The `link` conversation form (§4.3, [§DF-repo-conversation-opinion.2.1](../decisions/functional/DF-repo-conversation-opinion.md#21-the-link-form-is-a-markdown-link-over-an-absolute-uri)) has agents follow a citation with its declaration location — `<§>AR-scanner docs/architecture/AR-scanner.md:1`, escaped here because an FS example must not *cite* an AR — and some surfaces open that `path:line` natively (iTerm2's Semantic History, the VS Code terminal's own link detection) while the terminals grund configures match URLs only. Each terminal matcher therefore also matches a **location** token — a final path segment carrying a dot-extension and a `:<line>` suffix, optionally `:<col>` — and hands it to the same `grund-open`. The resolver tells the shapes apart mechanically: an ID's section suffix is dotted, never coloned, so a token ending in colon-digits is a location. A location is opened without consulting `grund` at all — the printed path is config-root-relative while the click may arrive anywhere in the tree, so the resolver climbs ancestors, nearest first, until the relative path exists (an absolute path is tested directly), then opens the editor at that line, dropping any column; because no repository config is involved, a location click works in any repository, grund-using or not. Peek on a location pages the file from the cited line, headed by the same `path:line` a click would open. In WezTerm the location rule is registered *before* the citation rule, which converts the recorded citation false positive on `:line`-suffixed paths into one correct link — the whole `docs/functional-spec/FS-integrations.md:<line>` token opens that file at that line, rather than the `/functional-spec/FS-integrations` fragment inside it failing to resolve — leaving the fragment case to bare paths with no line suffix. The location shape has its own accepted false positive, `host.com:8080`, which is dot-extension-and-line shaped; clicking it costs a no-such-file log line, never a wrong file.

Every GUI terminal spawns the resolver through `sh` with `~/.local/bin` and `~/.cargo/bin` — the documented homes of `grund-open` (§4.1) and `grund` — prepended to `PATH`. A terminal started from a desktop launcher inherits the session's environment, which never sourced the user's shell profile and typically carries neither directory; the spawn then fails to find `grund-open` at all, and the failure is a line in a log the user never opens while the citation simply does nothing. This is why the handler's command is a shell fragment rather than a bare program name, in every client that spawns from a GUI process.

A terminal's keymap is the user's, not grund's, and a binding that quietly deletes one of the terminal's own is a worse trade than a longer chord. kitty's gestures therefore live under `ctrl+shift+p`, kitty's own hints prefix (`p>f` for a path, `p>l` for a line, `p>y` for a hyperlink): `p>g` opens a citation and `p>i` peeks (§3.3), which is one more hint type in the family the prefix already names. Neither key is otherwise free — `ctrl+shift+g` is kitty's `show_last_command_output`, and a plain `map ctrl+shift+p` is worse than a collision, because kitty resolves a trigger by discarding every sequence mapped before the last non-sequence definition: one binding would silently remove all nine of kitty's `ctrl+shift+p` mappings.

Three WezTerm facts are part of the contract because each failure is silent. The click and peek gestures are registered twice — once plainly and once with `mouse_reporting = true` — because WezTerm ignores user mouse bindings while the foreground program has captured the mouse, and the programs that print citations (agent TUIs like Claude Code, full-screen editors) are exactly such programs; without the second registration the primary use case never clicks. And the `PATH` prepend every GUI terminal needs has one more layer here: when WezTerm itself runs inside a Flatpak sandbox (detected via `FLATPAK_ID`), whose `PATH` carries neither binary, the spawn is handed back to the host through `flatpak-spawn --host` — but only the spawn grund performs itself. A peek is a *pane command*, spawned by WezTerm the same way it spawns the user's shell, which the Flatpak build already routes to the host (`flatpak-spawn --host --watch-bus --directory=…`). Wrapping such an argv a second time runs `flatpak-spawn` on the host, where it has no portal to talk to and exits `127` with no output, so the pane closes before it draws anything and the peek reads as a flicker. The two spawn sites therefore differ by construction, and which one is inside the sandbox is the thing that decides it.

The third is how the pane's directory is discovered, and it is the one place where a Lua error costs the whole feature. WezTerm has no single way to ask: newer builds answer `pane:get_current_working_directory()` with a `Url` object, older ones spell it `get_current_working_dir` and answer with a `file://host/path` string, and calling a method the running build does not export is not a nil result but a Lua error that aborts the handler before it spawns anything. Every lookup is therefore guarded and tried in turn, and `pane:get_foreground_process_info().cwd` follows as an OS-side answer that needs no cooperation from the shell — except under Flatpak, where it is skipped: there the pane's program is spawned on the *host* through `flatpak-spawn`, so the process WezTerm can see is the sandbox-side helper and its `cwd` is a real directory that is simply not the shell's, which is worse than none.

What remains is `OSC 7`, the only channel that crosses that boundary, and **the shell must be made to emit it** — most do not, because the usual emitter, the distributions' `vte.sh`, returns early for every terminal that is not VTE. This is a prerequisite of the same kind as wiring `grund_apply_hyperlink_rule(config)` (§4.1): the artifact installs, and until the shell reports its directory the click cannot work. So it is stated in the artifact, in the setup guide, and — when a click arrives with no directory — in a toast notification and the WezTerm log, because a citation that silently does nothing is indistinguishable from an integration that was never installed.

### 3.2 Editor clients: `vscode`, `codium`

`grund integrations vscode` prints the terminal-citations extension source and the one-line `--write` install. `grund integrations vscode --write` materializes the unpacked extension into the editor's extensions directory (§4.2); the binary carries the artifact, so nothing is published to a marketplace and the [§FS-lsp.2.3](FS-lsp.md#23-editor-configuration-one-time-per-editor) stance is preserved. The extension is a `TerminalLinkProvider` that turns `§<ID>` occurrences in the integrated terminal into links resolved through `grund`.

It matches and strips the marker exactly as the terminal clients do (§3.1) and likewise keeps the `.<section>` suffix, resolving through `grund <ID>[.<section>] --brief --format json` — one resolution, because the brief report already carries the `path` and `line` a click needs while its body is exactly the hover slice (§3.3), so a click on a hovered citation spawns nothing. A directory-backed E2E declaration answers with the manifest shape — no `"line"` ([§FS-show.2.4](FS-show.md#24-e2e-cases)) — and its case *directory* is revealed in the Explorer: there is no file for `showTextDocument` to open, so this is the editor's form of the bare directory open the terminal resolver performs (§3.1). When that directory lies outside the opened folder — the workspace is a subdirectory of the repository — the Explorer cannot show it, and the reveal falls back to the OS file manager. It walks up from the workspace folder to the nearest ancestor holding a config under either discovery name ([§FS-config.1](FS-config.md#1-file-location-and-discovery)) — the same walk `grund` itself performs from its cwd — and uses that root both as the directory it runs `grund` in and as the base it joins the reported path against, so the two can never disagree when the opened folder is a subdirectory of the repository. Only successful resolutions are cached: a failure may mean the declaration does not exist *yet*, and pinning it until the extension host restarts would outlive the cause.

`codium` installs the identical extension into VSCodium's own extensions root, `~/.vscode-oss/extensions`. It is a separate client rather than a flag because it is a separate application: writing to `~/.vscode` for a VSCodium user drops the extension where nothing ever loads it, and the failure is silent — the install reports success and no link is ever produced. Detection cannot separate the two by presence, since both export an identical `VSCODE_*` environment; what differs is where those variables *point*, so `codium` is marked in addition to `vscode` when one of those values names VSCodium's application directory. Marking both is the honest outcome of an ambiguous environment: the catalog then offers both one-line installs and the user picks the application they are actually running.

### 3.3 Reading a declaration without leaving

Opening a citation answers *where*; often the question is only *what does it say*, and switching to an editor to find out costs more than the answer is worth. Every client therefore also offers a read-in-place path, in whichever form that client can express.

Only VS Code can offer true hover. Its `TerminalLinkProvider` attaches a tooltip to each link, so the declaration's `--brief` slice — heading plus first paragraph — plus the resolved `path:line` is shown on hover, with no click. Because tooltips must carry their text when the link is *provided*, and a provider runs per rendered line, successful resolutions are cached per citation (§3.2); the same citation scrolling past repeatedly costs one resolution, not one per line.

The terminal clients cannot hover, and the reason is structural rather than a missing convenience: a hover handler needs an event that fires on motion with no button held, and none of these terminals has one. WezTerm is the case worth naming, because its Lua surface otherwise looks rich enough — its mouse bindings trigger only on `Down`, `Up`, `Drag`, `WheelUp`, and `WheelDown`, all of which require a button or a wheel, no callback is given the cursor's row and column, and no tooltip API exists ([wezterm#4](https://github.com/wezterm/wezterm/issues/4) has requested one since 2018 with no implementation). So there is nothing to hang a preview on, at any level of cleverness. They offer **peek** instead — a second binding that renders the declaration into a disposable surface next to the work, rather than opening an editor:

| Client | Peek | Surface |
| --- | --- | --- |
| kitty | `ctrl+shift+p` `i`, then the hint label | overlay window |
| tmux | `prefix` + `G` | popup (requires tmux 3.2+; inert on older tmux, where `prefix` + `g` still opens) |
| wezterm | `ctrl+shift+`-click, or `ctrl+shift+i` and the label | split pane |

WezTerm's keyboard form is not a convenience twin of the click but the more dependable of the two, and it is the same shape kitty's hints kitten uses: one gesture labels every citation on the screen, and the label picks one. The mouse is the fragile path — a full-screen program that has captured the mouse can swallow the click (§3.1) — and citations are read while typing, when reaching for the pointer is the expensive part. Both terminals spell the two gestures `g` for *go* and `i` for *inspect*: in WezTerm as `ctrl+shift+g` and `ctrl+shift+i`, which are free there, and in kitty under its hints prefix as `ctrl+shift+p` `g` and `ctrl+shift+p` `i`, because kitty's own bindings own both plain keys (§3.1). Sharing the letters is what one carries between the two; the prefix is kitty's convention, not a difference in the feature. The picker matches with the §3.1 citation shape, and its result is handed to the same resolver call the click makes, so the two cannot drift. Supplying a custom action suppresses the picker's normal copy-to-clipboard, so using it costs the user nothing they had selected.

Peek is the same resolver in a different mode — `grund-open --peek <citation>` (§3.1) — so a peek and a click can never disagree about where a citation points. It prints the resolved `path:line` followed by the declaration lead — or, for a location token (§3.1), the file from the cited line — through a pager, because each of those surfaces closes when the process exits.

WezTerm needs one indirection worth recording, because it looks like an accident otherwise: Lua cannot ask which link is under the mouse — only the built-in `OpenLinkAtMouseCursor` knows, and it exposes only the resulting URI through `open-uri`, while `window:current_event()` does not carry modifiers. The peek binding therefore records the intent, delegates to that built-in action, and the `open-uri` handler reads the intent back. Both run inside one synchronous event, so the flag cannot leak across clicks.

### 3.4 Manual client: `iterm2`

iTerm2 stores its configuration in a binary property list, not a text file. There is no comment syntax to carry markers and no safe place to put them, so the managed-block contract (§4.1) simply does not apply — and rewriting a live profile blob under the user is not a trade grund makes for a convenience.

`iterm2` is therefore the one **manual** client. `grund integrations iterm2` prints the Smart Selection rule to add: the citation regex from §3.1, precision `Very High` so it does not lose to iTerm2's built-in filesystem-path rule, and a `Run Command…` action of `grund-open \0` — the first action on a rule is what fires on cmd-click. A second action, `grund-open --peek \0`, is offered for the right-click menu, which is where actions after the first appear; that is peek (§3.3) in the form iTerm2 can express. `\0` is the whole match, and needs no capture group because the resolver strips the marker itself.

`grund integrations iterm2 --write` installs everything grund *can* install — the `grund-open` resolver and the user preference and global agent instructions (§4.3) — then prints the steps it cannot apply, reporting `manual <client> (<where>)` on stderr. The exit code is `0`: nothing failed, and the remaining work is the user's. `integration_is_current` (§5) always reports `installed: false` for a manual client, because grund never reads that plist and reporting a guess would be worse than reporting nothing; the detection plan carries `"install_kind":"manual"` so a caller can tell the difference between *not installed* and *not knowable*.

A Mac user may not need the rule at all. iTerm2's Semantic History already makes a plain `path:line` cmd-clickable, so `--conversation link` (§4.3) — which has agents write the declaration location beside each citation — produces clickable citations there with no integration installed. That is the same reason `link` exists for TUIs: it degrades to something the host already understands.

### 3.5 Clients grund cannot support, and why

The client set is closed (§1), but absence from it is not always a judgement about the client — sometimes there is simply no hook. Recording why keeps the question from being re-litigated each time someone asks:

- **Ghostty** — documents exactly the option needed, `link`, which matches a regex against terminal text and runs an arbitrary binding action. The reference marks it `TODO: This can't currently be set!`; only the built-in `link-url` matcher works, and it takes no regex of its own. Nor does the `--conversation link` fallback help, since Ghostty has no `path:line` opener either. When `link` ships, the artifact is the §3.1 regex plus `grund-open` and nothing else.
- **Apple Terminal.app** — no regex-to-action mechanism of any kind. Nothing to build against.
- **Windows Terminal** — same: URL detection only, with no configurable matcher.

The common shape is that a terminal must let configuration bind *arbitrary matched text* to *an arbitrary command*. Every supported terminal client offers that; these do not.

## 4. Managed writes (`--write`)

`--write` never prints an artifact; with a client it installs that integration, while the clientless `--conversation` form updates only user guidance (§4.3). It reports what it did on stderr, exit `0`. Writes are idempotent and reversible by construction, mirroring the `init` managed-block contract ([§FS-init.2.3](FS-init.md#23-generated-agent-entrypoints)): a re-run of an up-to-date integration changes nothing and reports `exists`; an upgrade is a diff of the marked region; removal is deleting the marked region.

### 4.1 Marked blocks in dotfiles

For `kitty`, `tmux`, and `wezterm`, `--write` splices a comment-delimited managed block into the client's configuration file:

```
# >>> grund integrations (v1) >>>
<snippet>
# <<< grund integrations (v1) <<<
```

The marker's comment token is the one the **host file's own language** uses, not a fixed `#`: `#` for `kitty.conf` and `.tmux.conf`, `--` for `wezterm.lua`. A config file is source code in someone else's language, and a marker in the wrong dialect is not an inert stray line — in Lua `#` is the length operator, so a `#` marker is a syntax error that costs the user their entire WezTerm configuration, not just the grund block. Block lookup is scoped to the client's dialect for the same reason: a block found under the wrong comment token would be spliced with the wrong markers on the next write.

When `--write` creates the config file from scratch, a client whose configuration is a *program* rather than a list of settings also receives a starter scaffold below the block, so a fresh install is usable without hand-editing. WezTerm is the case that needs it: it applies hyperlink rules only from the config object the file returns, so a file containing the block alone parses and registers nothing. The scaffold is unmanaged — it sits outside the markers, later writes rewrite only the block, and the user owns it from then on. An existing config never receives a scaffold; there, calling `grund_apply_hyperlink_rule(config)` on the config being returned is the user's one wiring step (§3.1).

That step is **reported**, because nothing else in the run distinguishes a wired config from an unwired one: the block installs identically either way, so the install says `updated` and every click stays inert — an installed-looking integration that does nothing, which is the same silent shape as the `OSC 7` prerequisite (§3.1) and the wrong-VSCodium install (§3.2). When the host file *outside* the managed block does not call the helper, the write emits one `note:` line on stderr naming the call and the file. The test is on the unmanaged remainder alone: the block defines the helper and names it in its own comments, so a whole-file search would never report anything. A config that already calls it — including one grund scaffolded itself on a from-scratch write — is silent, and so is every client that needs no wiring. It is a report, not a finding, in the shape `grund init` uses for a symlinked entrypoint ([§FS-init.2.3.4.17](FS-init.md#23417-clickable-citations)): nothing is rewritten and the exit code is untouched. It repeats on every write until the call appears, since the write is idempotent and so is the omission.

The begin and end markers carry a block version. On write grund finds one existing block at any supported version and replaces its complete marker-line span, preserving everything outside byte-for-byte; a file with no block gets the block appended after a blank-line separator. Indented marker lines are accepted and consumed as complete lines. A missing matching marker, multiple blocks, or a block whose version is newer than the binary understands is a hard error (`exit 2`), the same guard `init` applies to a newer AGENTS block ([§FS-init.2.3](FS-init.md#23-generated-agent-entrypoints)). The resolver script is written alongside, to a fixed resolver path, only when absent or when its embedded version differs, and a failure to make it executable is an I/O error rather than a successful install.

Outcomes map to stderr verbs `appended` / `updated` / `exists`, plus `skipped` for a user-guidance target whose agent is not in use (§4.3), and to `would-append` / `would-update` / `would-write` under a `--dry-run` reserved for symmetry with `init`. The default (no `--write`) is already the dry read: it prints, it does not touch the disk.

**Where a `~` target resolves.** The install-target hints (§1, §5) are printed verbatim and stay `~`-rooted so the artifact and the JSON descriptor are byte-stable across machines (§6); only resolution consults the environment. A `~/.config/…` target resolves against `$XDG_CONFIG_HOME` when that variable is set and non-empty, and against `~/.config` otherwise. This is not a preference: kitty, WezTerm, Zed, and grund's own user configuration each read their directory from `$XDG_CONFIG_HOME`, so a hardcoded `~/.config` on a machine that sets it writes where the tool never looks — the same silent, install-reports-success failure the separate `codium` client exists to prevent (§3.2). Targets outside `~/.config` — `~/.local/bin/grund-open`, `~/.vscode/extensions`, `~/.tmux.conf`, the agent instruction files of §4.3 — are the paths those tools define and resolve against `$HOME` alone.

### 4.2 The VS Code extension

`vscode --write` writes the unpacked extension directory (its `package.json`, the provider script, and a marker file recording the embedded version) into the editor extensions directory. A present, byte-current same-version extension is left untouched (`exists`); a different, missing, or damaged grund-owned file is repaired. grund writes only files it owns inside its own extension directory; it never edits the user's `settings.json`.

### 4.3 User preference and global agent instructions

Every client `--write`, and every clientless `--write` carrying `--conversation` or `--conversation-target`, records the effective local-conversation preference in the user's Grund configuration at `$XDG_CONFIG_HOME/grund/config.toml`, or `~/.config/grund/config.toml` when `XDG_CONFIG_HOME` is unset or empty. This is deliberately user-scoped: whether a TUI has the rendering integration is a property of the user's machine, not a repository. The first client write defaults to `plain`; a stored value survives later writes unless the corresponding flag explicitly changes it.

The key is **`[reference] conversation`** — the same spelling the repository config uses for the same concept ([§FS-config.3.1](FS-config.md#31-reference--citation-form)), so there is one name to know and the scope alone decides the legal values: `plain` and `link` here, `link` only in a repository. Set it to `plain` when a rendering layer from §3 is installed and bare `§<ID>` citations are already clickable; set it to `link` when the surface cannot click a bare citation — a stock terminal, `ssh`, a TUI with no matcher — so the declaration location travels with the citation instead. Editing the file by hand is supported and equivalent to `--conversation`; `--write` is what synchronizes the instruction blocks from it.

**`[reference] conversation_target`** selects how a linked citation addresses its declaration, and has no repository spelling at all ([§DF-conversation-link-target.2.3](../decisions/functional/DF-conversation-link-target.md#23-the-target-is-user-scoped-but-the-default-is-committable)). Each value names one fixed template, filled from the declaration's absolute path and line:

| Value | Rendered target |
| --- | --- |
| `file` (default) | `file://<abs>#L<line>` |
| `path` | *(no URI)* — the location as plain `path:line` text beside the citation |
| `web` | the forge blob URL for the current ref, per the repository-web rule ([§FS-init.2.3.4.17](FS-init.md#23417-clickable-citations)) |
| `vscode`, `vscodium`, `cursor` | `<scheme>://file<abs>:<line>` |

`file` is the default because it presumes nothing about the machine beyond a handler for `file:`, and because it degrades to a readable location where the scheme does not dispatch. An unknown value follows the split the two surfaces already use: a CLI error listing the accepted set on the flag (§6), and a warning that leaves no target from this file — falling back to `file` — when it is hand-written into the configuration (below).

The linked form is **gated per agent**. The Codex TUI renders a local-path Markdown destination in place of the link label, erasing the visible citation, so instructing the form there would destroy the citation on a surface where the failure is silent. A target is therefore written into an agent's block only where the pair is verified, and every other block falls back to `path`: Claude receives every target; Pi receives `file` and `web`; Codex receives `web` and falls back to `path` for the local schemes; Gemini, Copilot, and Zed receive `path` until a click-test says otherwise. The evidence and the rule are recorded in [§DF-conversation-link-target.2.4](../decisions/functional/DF-conversation-link-target.md#24-the-form-is-gated-per-agent-and-the-fallback-is-path). The gate can only hold a target at the form it already had, never make one worse, and it is reported rather than silent: each written instruction target's line names the form it received and, when that is not the form asked for, why — so a machine that set `vscodium` can see which agents took it (§4.4).

Because that file is hand-editable, grund reads the key the way TOML defines it rather than by matching one literal spelling: whitespace inside the section header, a dotted key path, and either quote style are all the same setting. This is a correctness requirement, not a courtesy — a spelling grund failed to *recognize* would be silently reversed to the default and then written back beside the original, leaving the opposite of what the user asked for.

Recognizing the right spelling is only half of it, because nothing in the file says which keys grund consumes. `reference.conversation`, `reference.conversation_target`, and the per-agent overrides of §4.4 are the whole set, and **nothing in this file is ever an error**. One rule covers all of it: report the line, ignore it, continue on the effective preference. Each report is one `warning:` naming the line and what is being ignored —

- a key grund does not read (`unused key <path>; grund reads only reference.conversation, reference.conversation_target, and reference.agents.<agent>.conversation_target from this file`), which covers a typo, a retired spelling, and a repository-only key set here in the belief that it applies to every project, all of which otherwise read as configured and do nothing;
- an override under an agent grund does not know (`unknown agent <name> in reference.agents; known agents: codex, claude, gemini, copilot, zed, pi`), which is the one warning that names the closed set rather than the key, because the mistake is almost always the agent's spelling;
- a value grund cannot interpret — quoted wrongly, or outside `plain | link` for `conversation` and the target set for `conversation_target` — which leaves grund with **no such preference from this file**, the same state as a machine that never wrote one: the run proceeds on the flag if given, and otherwise on the `plain` and `file` defaults. The two keys fail independently, so an unreadable target never costs the `plain`/`link` preference recorded beside it;
- a repeated key, where the **first occurrence wins**, for each key separately. That is also the occurrence a write rewrites, so a read and a write can never disagree about which line is the setting.

None of this changes the exit code (§6).

That the whole file warns is the one place the two configurations deliberately differ, and the difference is what each file decides. The repository config is a closed allow-list where an unknown section or an uninterpretable value is a hard error ([§FS-config.4.3](FS-config.md#43-invalid-config-behavior)), because it governs whether a tree checks clean and two installs must never disagree about it ([§FS-non-goals.13](FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree)). Nothing here is shared or checked: this file is machine-local, read by one command, and expresses a preference between two renderings of the same true citation. Refusing to install a terminal integration because of a stale line in a personal config would be the worse failure — an unparseable value is no more of a reason than an unread key, since both leave grund with nothing stated — and the user is told, at the line, what was ignored.

The file is therefore read and reported on exactly once per invocation, **before** any client artifact is installed: the warnings appear once rather than per target, and the only thing that can fail is being unable to reach the file at all.

The repository side may commit the `link`-only opinion ([§FS-config.3.1](FS-config.md#31-reference--citation-form), [§DF-repo-conversation-opinion](../decisions/functional/DF-repo-conversation-opinion.md#df-repo-conversation-opinion-repositories-may-commit-a-link-only-conversation-rendering-opinion)); that opinion is the fallback for machines that never stated a preference, and an explicitly recorded preference here wins over it ([§DF-repo-conversation-opinion.2.3](../decisions/functional/DF-repo-conversation-opinion.md#23-precedence)).

The same write synchronizes a marked `## Grund citation rendering` block into the global instruction files for every supported agent with a file-backed user scope: Codex (`~/.codex/AGENTS.md`), Claude (`~/.claude/CLAUDE.md`), Gemini (`~/.gemini/GEMINI.md`), GitHub Copilot (`~/.copilot/copilot-instructions.md`), Zed (`~/.config/zed/AGENTS.md`), and Pi (`~/.pi/agent/AGENTS.md`).

A target receives the block when the agent is **in use on this machine** — its own directory exists (`~/.claude`, `~/.codex`, `~/.gemini`, `~/.copilot`, `~/.config/zed`, `~/.pi`), or the instruction file already does, which keeps a file grund wrote earlier synchronized even if the directory test would no longer select it. Otherwise the target is reported `skipped <path> (no <dir>)` and nothing is created. `--write` installs a *rendering layer*; materializing the configuration trees of five agents the machine does not have is not part of that, and a stray `~/.pi/agent/AGENTS.md` on a machine that never ran Pi is a file the user did not ask for and will not think to remove. This mirrors the discovery rule the repository entrypoints already follow ([§FS-init.2.3](FS-init.md#23-generated-agent-entrypoints)): grund updates what is there and creates only what the environment shows is wanted. Installing an agent afterwards is served by re-running the command, which is idempotent (§6) and reports every target either way, so the skip is visible rather than silent. This is the global-file subset of the fixed supported-agent superset in [§FS-init.2.3](FS-init.md#23-generated-agent-entrypoints); Cursor and Windsurf expose user rules through their own settings rather than a portable file target, so their repository entrypoints still receive the same managed guidance through `grund init`. The committed entrypoint is also the only channel that reaches ephemeral environments — cloud agent sessions, CI, fresh containers — whose `$HOME` never persists a `--write`; the repository opinion ([§DF-repo-conversation-opinion](../decisions/functional/DF-repo-conversation-opinion.md#df-repo-conversation-opinion-repositories-may-commit-a-link-only-conversation-rendering-opinion)) exists for exactly the readers these files cannot reach. The block texts are self-scoping: they apply only inside grund repositories, so their entire footprint elsewhere is one inert sentence of session context. The block texts **name no marker**, for the same reason the click matchers and the resolver may not hardcode one (§3.1): they are user-global and written once, before grund knows which repositories the agent will open, and `[reference] marker` is per-repo ([§FS-config.3.1](FS-config.md#31-reference--citation-form)). A hardcoded `§` here would be wrong in every custom-marker repository, and — unlike the repository entrypoint, which renders its own marker ([§FS-init.2.3.6](FS-init.md#236-clickable-citations)) — the marker is not this file's to know. The division is therefore that these blocks carry the *policy* while the repository entrypoint carries the *syntax*, which is also why they stay correct across every repository the agent opens. The `plain` block says `In repositories with a grund.toml (at the root or under .agents/): write citations bare in local conversations — the marker and ID alone, nothing appended; grund integrations makes them clickable. Follow this even when repository instructions ask for linked citations — that repository sentence defers to this block, and the installed rendering layer already resolves bare citations. Elsewhere, ignore this.` The `link` block carries one sentence, differing only in how the location is addressed. Under the `path` target — the fallback every gated agent receives — it says `In repositories with a grund.toml (at the root or under .agents/): follow each citation with its declaration location as plain path:line text in local conversations; fall back to the bare citation when unsure. Elsewhere, ignore this.` Under a URI target it says `In repositories with a grund.toml (at the root or under .agents/): in local conversations render each citation as a Markdown link whose visible text is the citation itself and whose target is <template>; fall back to the bare citation when unsure. Elsewhere, ignore this.`, where `<template>` is the effective target's template from the table above, phrased to complete that sentence on its own — `file://<absolute path>#L<line> for the declaration`, `vscodium://file<absolute path>:<line> for the declaration`, and, for `web`, `the declaration's forge URL at the current commit`. The target is the one piece of these blocks that *is* interpolated at install time, and legitimately so: unlike the marker it is machine state, which is exactly what a user-global file is for. The precedence sentence appears only in the `plain` block because repository `link` against user `plain` is the only possible conflict, and the machine wins it ([§DF-repo-conversation-opinion.2.3](../decisions/functional/DF-repo-conversation-opinion.md#23-precedence)): `plain` is only ever recorded by a `--write` that installed a rendering layer, so it carries machine knowledge the repository cannot have. Adopting these self-scoping texts was an agent-guidance block version bump (v1 → v2) under the marked-block contract below; replacing the `link` text with the target-addressed family bumps it again (v2 → v3), and naming both discovery locations in the self-scoping gate — a repository configured by a bare root `grund.toml` is a grund repository the old gate did not describe ([§FS-config.1](FS-config.md#1-file-location-and-discovery), [§DF-config-file-location](../decisions/functional/DF-config-file-location.md#df-config-file-location-grundtoml-is-discovered-at-two-names-per-directory-and-init-writes-the-bare-one)) — bumps it once more (v3 → v4). These blocks are user-global and intentionally contain no repository-web rule; repository entrypoints own that fixed context-sensitive instruction ([§FS-init.2.3.6](FS-init.md#236-clickable-citations)).

The global instruction block uses versioned HTML-comment begin/end markers. The replacement, append, newer-version refusal, malformed/multiple-block rejection, preservation, idempotence, and stderr outcome rules are the same as the dotfile block in §4.1. Existing global instruction files keep all text outside the managed block byte-for-byte; for a selected target, missing parent directories and the file itself are created because `--write` is the explicit installation action. A failure to update the preference or any instruction file is an error. The preference file is validated first, before any client artifact is written, so the common failure — a hand-edited value grund cannot parse — costs nothing and changes nothing; a block failure discovered later may leave an integration artifact already written, and re-running after correction safely completes the installation.

### 4.4 Per-agent overrides

One machine can read more than one agent, and the evidence says they do not render the same
(§4.3). `[reference.agents.<agent>]` is therefore a **partial of the settings above, keyed by
agent**, merged over them:

```toml
[reference]
conversation        = "link"
conversation_target = "vscodium"   # the machine-wide base

[reference.agents.codex]
conversation_target = "web"        # this agent only
```

The merge is shallow and the rule is one line: **a key present under an agent replaces the
machine-wide value for that agent; an absent key inherits it.** There is no per-agent default and
no way to unset the base — deleting the entry restores inheritance — so the base is always the
answer unless something explicitly says otherwise. Only `conversation_target` is accepted inside
the partial today; the shape is what makes adding a second key later a no-op rather than a second
map keyed by the same agent names ([§DF-conversation-link-target.2.5](../decisions/functional/DF-conversation-link-target.md#25-a-per-agent-override-is-a-preference-not-evidence)).

`--agent <name>` writes one such entry, scoping `--conversation-target` to that agent instead of
the machine:

```
grund integrations --write --agent codex --conversation-target web
```

`--agent` is accepted only with `--write` and only alongside `--conversation-target`; it scopes
nothing else, and `--agent` with no target is a CLI error rather than a silent no-op. The accepted
names are the six agents of §4.3 — `codex`, `claude`, `gemini`, `copilot`, `zed`, `pi` — and an
unknown one is a CLI error listing them (§6). A scoped write leaves both machine-wide keys exactly
as they were: the point of the flag is to change one agent without disturbing the base every other
agent inherits.

**The gate still runs last.** An override is a *preference*; the per-agent table in §4.3 is
*evidence*, and evidence wins. Asking for `[reference.agents.codex] conversation_target =
"vscodium"` resolves to `vscodium` and is then gated to `path`, exactly as the machine-wide value
would be — the override moves the request, never the verdict. This is what keeps a per-agent
escape hatch from becoming a way to write an instruction that is recorded as erasing citations.

**Both layers are visible in the report.** Every written instruction target names the form it
received, and when that is not the form requested, why:

```
$ grund integrations --write --conversation-target vscodium
updated /home/you/.claude/CLAUDE.md (link → vscodium)
updated /home/you/.codex/AGENTS.md (link → web; agent override)
updated /home/you/.gemini/GEMINI.md (link → path; vscodium unverified here)
skipped /home/you/.pi/agent/AGENTS.md (no ~/.pi)
```

Without this the two layers are indistinguishable from a typo: a machine that set `vscodium` and
finds `path` in a block has no way to tell an override from a gate from a key grund never read.
The line is part of the contract for that reason, not a convenience.

## 5. JSON format

`grund integrations --format json` (no client) emits the detection plan as one JSON object on stdout: the detected clients in frozen order, and for each the client name, whether it is detected, whether its grund-owned artifacts are installed and current, how it installs (`install_kind`, the §3.4 field that lets a caller tell a manual client's *not knowable* from *not installed*), and the exact `--write` command an agent would run. Installation checks read only the fixed integration targets; they never search the filesystem. `grund integrations <client> --format json` emits one deterministic object describing that client's artifact — its target path(s) and the `--write` command — without printing the artifact bytes. The stream split follows the rest of the surface ([§FS-errors.1](FS-errors.md#1-streams)): the plan is stdout, any CLI-level `error:` is stderr. This is the machine surface `grund agent-setup-instructions` points an agent at ([§FS-init.5](FS-init.md#5-agent-setup-instructions)): detect, show the diff, write only on user confirmation.

## 6. Determinism and exit codes

With an explicit `<client>`, output is a pure function of the binary version and the flags — no environment, no tree scan, no clock — so it is byte-identical across machines and safe to golden. The no-client detection form (§2) is a pure function of the binary version, the named environment variables, and, for JSON, the fixed installation targets; it is byte-identical for a fixed environment and installation state. `--write` is idempotent: a second run against an up-to-date target is a no-op that reports `exists`. That holds for the preference file too — a recorded value equal to the effective one is left byte-for-byte alone, including any comment written beside it, rather than re-emitted in grund's own spelling. A manual client (§3.4) has no target to compare, so its `--write` is idempotent in the weaker sense that it re-installs the resolver only when stale and re-prints the same steps.

Exit codes follow the frozen mapping ([§FS-cli.5](FS-cli.md#5-exit-code-mapping-is-fixed)): `0` printed, written, or already current; `2` an unknown client, bare `--write` with neither a client nor a conversation flag, `--conversation` or `--conversation-target` without `--write`, `--agent` without `--write` or without `--conversation-target`, an unknown agent name, an unknown flag, or a configuration file whose managed block is newer than this binary understands. There is no `1` outcome — `integrations` has no findings surface. Nothing in the user preference file is an exit code: its unused keys, uninterpretable values, and duplicates are warnings (§4.3), as are `skipped` targets (§4.3). An invalid `--conversation` or `--conversation-target` *argument* remains an error, because that is a value the caller typed on this command line rather than a stale line in a file.
